# Calendar tooltip text and color handling

Calendar event tooltips build DOM nodes and put user-provided title, status,
assignee, label and description text into `textContent`. Tippy receives that
element with `allowHTML: false`; event removal destroys its tooltip instance.
Description tag stripping and the 100-character preview remain presentation
behavior, with no HTML parsing of the resulting preview.

Label and status create/update inputs accept CSS hex colors with 3, 4, 6 or 8
digits, case insensitive. The existing UI palettes and seed colors use supported
hex values. Named colors and `rgb(...)` input now receive validation errors.
Label creation still requires a color; status creation still permits omission
and keeps the database's default color and `isCompletion: false`. Partial
updates may omit color and keep the stored value.

Tooltips independently validate stored colors before assigning
`style.backgroundColor`. Missing or nonhex historical/restored values use
`#9ca3af`. This protects the rendering boundary without rewriting existing data
or preventing name-only updates to legacy rows. Backup restore writes are a
separate input path and can still preserve historical colors.

TEST_DATABASE_URL="$AUDIT_DATABASE_URL" pnpm --filter @pm/backend exec node --import tsx --test tests/integration/calendar-colors.test.mjs

Use a migrated disposable PostgreSQL database. The 21 frontend cases cover
literal markup, description/date display, neutral legacy-color fallback,
supported and rejected schema values, optional/default contracts, actual
FullCalendar/Tippy hover and event-removal cleanup. The three HTTP/database
tests exercise MEMBER create/update operations through compiled shared exports,
verify no row or status-broadcast changes for invalid colors, and preserve
legacy name-only updates. Fixtures contain passive literal markup and invalid
semantic colors. Each database test run removes its own records and storage.

Local checks passed: frozen install, all 61 unit/frontend tests, all 162
PostgreSQL integration tests, typechecks and production build. The build still
reports its existing large-chunk warning.

A local production browser check used Chromium 141.0.7390.37 on Ubuntu 26.04.1
with Playwright's Ubuntu 24 fallback build. It completed real password login,
loaded the authenticated calendar route with real API/database fixtures,
hovered both legacy and ordinary events, verified literal text and computed
swatch colors, and switched to Week view. The document used the application's
production CSP, including `script-src 'self'`. Screenshots showed the expected
literal fields and neutral/normal swatches. There were no JavaScript page errors;
console output included pre-login refresh 401s and the existing external Google
stylesheet blocked by CSP. This was headless desktop Chromium on local HTTP,
not cross-browser, mobile, or production-deployment coverage.

This change covers the calendar tooltip boundary in FE-001. Backup asset export
authorization (SEC-009/A12), other content renderers, and broader calendar
editing/browser release gates remain separate work.
