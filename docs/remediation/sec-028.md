# Backup restore parse budget

Backup preview and restore parsed `backup.json` with `JSON.parse` and then
validated it against `BackupFileSchema`. Zod reports a separate issue for every
invalid element. A file such as `{"metadata":{},"projects":[{},{},…]}` costs
about 22 bytes of heap per byte to parse, and about 100 bytes per byte once
every element has its issue. An empty task reports five issues. Text like this
deflates about 1,000:1, so a 2.5 KB ZIP could abort a server process with a
256 MiB heap. On a default heap a ZIP of a few tens of KB was enough. The
crash takes the server down for every workspace. The same happened with a
plain `.json` upload, which only needs the full file uploaded. The routes
require workspace ADMIN, but any signed-in user can create a workspace and is
its ADMIN. The SEC-025 archive budget did not help here: `backup.json` passed
its 512 MiB per-entry limit easily.

## Limits

`backup-json.ts` now measures `backup.json` before `JSON.parse` sees it. The
measurement is one pass over the bytes, allocates nothing, and refuses the file
if it exceeds any of these limits:

| Limit | Value | Largest measured export |
|---|---|---|
| UTF-8 bytes | 32 MiB | 17.4 MB (16.6 MiB) |
| Tokens: `{`, `[`, `,` and `:` outside strings, plus one | 2,000,000 | 787,482 |
| Nesting of objects and arrays | 128 | 12 |

Heap use depends on how many values the file holds, not on its size alone.
The token count is an upper bound on the values and member names
`JSON.parse` can create. It exceeds their number by exactly one for each empty
object or array. Exports average about 22 to 24 bytes per token.

The measured export is the PR 88 workspace plus a busy channel, built through
the real routes and exported over HTTP:

- 4 projects with 6,000 tasks, 12,000 subtasks and 6,000 comments;
- one channel with 20,000 messages;
- 2 wiki spaces with 500 pages and 1,512 embedded images, using SEC-009 upload
  names.

Its `backup.json` was 17,427,502 bytes, with 787,482 tokens and a depth of 10.
A server with a 256 MiB heap previewed it and then restored it. All 1,512
restored images matched their source bytes, and all 6,000 tasks and 20,000
messages came back. The integration test's smaller export (3,000 tasks, 3,000
messages, 300 pages, 600 images) has a depth of 12.

The depth limit also matches the database layer. Prisma's query engine stores
at most 123 levels of nesting in one JSON column. That puts a wiki page's
content at depth 128 in `backup.json`. A deeper file could not be restored, and
it used to fail with a 500 halfway through the restore transaction.

Validation now stops at the fifth problem. The response still lists up to five
problems, as before. Zod's message for an invalid enum value quoted the
uploaded value, so the response could repeat up to five strings from the
upload. It now names only the allowed values.

## What this bounds

At the limits, the most expensive file a restore can be asked to parse holds
400,000 minimal projects plus one 22 MiB string. The string has one character
above U+00FF, so V8 stores the whole source text with two bytes per character.
The real preview route answers it in a process with a 336 MiB heap, including
the app. It needs 256 MiB without the string. The most expensive invalid files
the limits admit get their 400 with a 128 MiB heap.

Measured floors (the smallest `--max-old-space-size` at which the preview route
answered; the app alone runs in 64 MiB):

| File at the limits | Heap |
|---|---|
| 400,000 projects, two-byte string padding to 32 MiB | 336 MiB |
| 400,000 channels, the same padding | 288 MiB |
| about 180,000 tasks, the same padding | 256 MiB |
| 1,000,000 `{}` in a page's content, the same padding | 224 MiB |
| one 32 MiB two-byte string | 160 MiB |
| 1,000,000 empty projects or tasks (invalid, 3 MB) | 128 MiB |

Node's default heap on 64-bit Linux is about half of the memory it sees, up to
4 GiB. It was 1,747 MiB on the 3.3 GiB test host. A host with 1 GiB of memory
therefore gets a heap of about 512 MiB, more than one upload can use.
Parsing and validating at the limits blocks the event loop for about 0.8 s.
The measured export takes about 0.15 s.

## Where the limits apply

- **ZIP uploads.** The declared size of `backup.json` is checked against the
  byte limit before the entry is inflated. Over the limit, the response is the
  SEC-025 message "the archive exceeds the restore limits", and the log reason
  is `json-size`.
- **Plain `.json` uploads, and `backup.json` after inflation.** Both go through
  the same `parseBackupJson`. Preview and restore share it. A refusal is a 400
  with the fixed message "Invalid backup file: the backup data exceeds the
  restore limits". The server logs one of the reason codes `json-size`,
  `json-tokens` or `json-depth` at warn level. It never logs file content.
- **Export.** Export measures its own `backup.json` with the same limits after
  building it. An export that restore would refuse gets the SEC-025 400, which
  asks the admin to select fewer projects, channels or wiki spaces. So every
  export Werkyn produces can still be restored.

## Behavior changes

- A `backup.json` over 32 MiB, 2,000,000 tokens or depth 128 is refused.
  Before, files up to the 512 MiB archive entry limit were parsed if the server
  had enough memory.
- Exports over the same limits are refused. Large workspaces must be exported
  in parts, for example one busy channel at a time. A restore adds to the
  workspace, so the parts can be restored one after another.
- Content nested deeper than the database accepts gets a 400 before any write.
  Before, it failed with a 500 during the restore.
- Validation errors list at most the first five problems, as before. Enum
  errors no longer quote the uploaded value.

## Tests

`tests/backup-json.test.mjs` runs in `pnpm test`. It covers:

- token counting, checked against a census of the parsed values;
- strings that contain structural characters, escapes and multi-byte UTF-8;
- each limit at its boundary, with its reason code;
- validation stopping at five problems;
- enum messages that do not quote the upload;
- the ZIP check on declared size before inflation;
- the export budget at and one below each limit.

It also parses the review's 4 MiB reproduction and the most expensive invalid
files the limits admit in a child process with a 128 MiB heap, where all of
them get a 400. The validation the routes ran before aborts that child.

`tests/integration/backup-json-budget.test.mjs` starts the real app in child
processes with a 1 GiB data segment, and uploads to preview and restore:

- **Hostile uploads, 256 MiB heap.** The review's 4 MiB and 24 MiB files as
  ZIPs (4,235 and 24,623 bytes), the 24 MiB file as plain `.json`, 750,000
  empty tasks as a 2,466-byte ZIP and as plain `.json`, and invalid channel
  types. On the previous code each of the five amplifying uploads aborted the
  process (SIGABRT, JavaScript heap out of memory), and the enum error quoted
  the upload. Now each gets a 400, nothing is written, and the same process
  then restores a legitimate backup.
- **Each limit, 256 MiB heap.** Files exactly at the byte, token and depth
  limits are accepted. A file at the depth limit restores and stores its
  content. One byte, token or level more gets a 400. So do the most expensive
  invalid files under the token limit.
- **The worst accepted files, 384 MiB heap.** The most expensive valid files
  under the limits preview successfully.
- **A realistic export, 256 MiB heap.** The test builds and exports a workspace
  with 3,000 tasks, 6,000 subtasks, 3,000 comments, 3,000 messages, 300 pages
  and 600 images, using SEC-009 upload names, over HTTP. It previews and
  restores it, then compares every task, message, page and image with the
  source.

`tests/integration/backup-zip-restore.test.mjs` checks that an export whose
`backup.json` is exactly at reduced limits succeeds. One byte, token or level
less refuses the export.

## Remaining limits

The limits bound one request. Each restore in progress keeps its parsed
backup until its transaction ends, and there is still no limit on concurrent
backup requests (B03/P03). The upload is still buffered whole, and export still
builds the whole `backup.json` before measuring it. Parsing is synchronous, as
before. The public backup documentation does not mention these limits yet.
