# Task order and dependency-graph invariants (DAT-012)

## Problem

Order and graph writers read the state they depended on without excluding each
other, under READ COMMITTED:

- Task create, duplication, template instantiation and status changes chose
  "last position in the column" (max + 1) without a lock, so two of them could
  take the same position. Subtask and column creation did the same.
- A move read the column, then renumbered it. A second move that read the
  column before the first committed overwrote it, losing the first move. Moves
  and bulk updates locked task rows in different orders and could deadlock
  (one of them got a 409).
- Bulk status changes, bulk unarchive and column deletion moved tasks without
  giving them positions, so the destination had duplicate positions even
  without any concurrency.
- The dependency cycle check ran before, and outside, the insert: A blocked by
  B and B blocked by A, added together, both passed and stored a cycle.
- Two column updates could each mark a different column as the completion
  column; two deletes of the last two columns could each see two columns left
  and remove both; two deletes of non-empty columns each moved their tasks into
  the other and deadlocked.
- Column and subtask reorders accepted lists with duplicate or missing IDs,
  which left two items on one position.
- Lists sorted by position and creation time only, so rows with equal values
  had no defined order.

## Invariants

1. The active (non-archived) tasks of a column have distinct positions. The
   board order is position, then creation time, then id, a total order even for
   rows written earlier that share a position. Gaps are allowed: deleting or
   archiving a task leaves one. A move renumbers the columns it touches to
   0..n-1; every other writer places tasks after the column's highest active
   position. An archived task's position does not count; it gets a new one when
   unarchived.
2. The dependencies inside a project never form a cycle.
3. A project has at most one completion column, and never loses its last
   column.
4. Columns of a project and subtasks of a task have distinct positions; a
   reorder must list each of them exactly once.

## Serialization

Every writer that changes task order, columns or dependencies takes the
project's order lock first, `SELECT … FROM "Project" … FOR NO KEY UPDATE`
(`packages/backend/src/utils/task-order.ts`), and keeps it until commit:

| Writer | Change |
| --- | --- |
| Task create, duplicate, template instantiation (API and recurring scheduler) | position after the column's last active task |
| Task move | renumbers the source and destination columns |
| Task update with a `statusId` | reads the task's column again under the lock, then places it last in the new column |
| Archive / unarchive | an unarchived task goes last in its column (unarchiving an active task no longer moves it) |
| Bulk update (any field) | moved or unarchived tasks go after the destination's active tasks, in their previous board order (column position, position, creation time, id); tasks already there stay |
| Task delete, bulk delete | deletes rows other writers renumber, and their dependencies |
| Subtask create, subtask reorder | position after the last subtask; a reorder must list every subtask once |
| Dependency add / remove | the cycle check and the insert in one transaction |
| Column create, update, reorder, delete | column positions, the completion column, the "last column" check; a delete appends the column's tasks to the target column in board order |

Under READ COMMITTED each statement after the lock sees everything the
previous holder committed, so the position, column order, cycle check or count
a writer reads stays true until it commits.

`FOR NO KEY UPDATE` conflicts only with other holders, with project updates
(rename, archive) and with project deletion. It does not conflict with
`FOR KEY SHARE`, the mode of foreign-key checks and of the reference checks in
`task-references.ts`, so writers that do not change order (comments,
assignments, labels, custom-field values, field edits without a status change)
are not serialized by it.

Lock order: the project row is the first lock of each of these writers, which
keeps the Project-first order of [DAT-005](dat-005.md#lock-order). A column
delete takes the order lock before its column. The recurring scheduler holds
the project row `FOR KEY SHARE` and its schedule row before it instantiates the
template; instantiation then strengthens the project lock, which PostgreSQL
grants a holder without queueing it behind other waiters. As a result, the two
cycles DAT-005 listed for concurrent deletes of non-empty columns and for moves
against bulk updates no longer occur: both sides now wait for the same lock.

## Retries

`withProjectOrder` runs the work in a READ COMMITTED transaction (5 s to get
a connection and start, 10 s in all). When PostgreSQL aborts it to break
a deadlock (40P01) or for a serialization failure (40001, P2034), it runs the
work again, up to three attempts in all, with a short jittered pause, and
logs each retry at warn level with the project id, the attempt and the
database code (not the query), so contention stays visible when the retry
succeeds. An
expired transaction (P2028) has used its whole wait and is not retried. When no
attempt succeeds, the error reaches the error handler, which answers with the
existing retryable 409 "The request conflicted with a concurrent change; try
again" (`isRetryableDatabaseError`). Nothing from an aborted attempt is kept,
and the work has no side effects outside the transaction; broadcasts and
notifications run in the controllers after it returns. Called with a
transaction client (the scheduler), it takes the lock in that transaction and
leaves retrying to the caller.

### Bounded lock waits

Prisma's 10 s transaction timeout does not interrupt a statement that is
waiting for a lock: the statement keeps waiting, and its pooled connection
stays taken, until the holder lets go. Measured before this bound, five creates
queued behind a project row held for 12 s all waited the full 12 s and then got
the 409. Meanwhile the five-connection pool was exhausted, so requests for an
unrelated project could not even authenticate (401 after the pool's 10 s wait).

Every order transaction therefore bounds its lock waits at
`ORDER_LOCK_TIMEOUT_MS` (5 s), well below the transaction timeout and the
pool's 10 s connection wait:

- The project-lock statement runs under a transaction-local `statement_timeout`
  of 5 s, restored right after. Waiting for the project row can take two lock
  waits in a row (a place in the row's queue, then the holder's transaction),
  and `lock_timeout` restarts for each one.
- Every later lock wait in the transaction is capped by a transaction-local
  `lock_timeout` of 5 s.

A request that hits the bound has written nothing, since its transaction is
rolled back. That means either timeout on the project-lock statement (57014 or
55P03), or a later lock timeout (55P03). It is answered with 503 "The project
is busy. Try again in a moment." (`ProjectBusyError`), the same status the
refresh-token and password-change paths use for a lock timeout. It is not
retried, because the lock is still held.

A statement canceled at any other point, by a database-wide
`statement_timeout` or a manual cancel, keeps its own error and is not
reported as contention.

In a caller's transaction (the scheduler) the bound applies as well. The
scheduler sees `ProjectBusyError` for the project lock, or the database error
for a later wait, counts the occurrence as failed, and generates it on a later
run.

Measured with this bound, in the same scenario: all five queued creates got
the 503 after about 5.05 s and stored nothing. The unrelated project's read and
create got a connection as soon as those were released and succeeded after
about 5.07 s. While a held project fills the pool, other projects' requests
still wait up to that bound for a connection. `withWorkspaceLock` (outside this
change) has the same unbounded wait.

The remaining deadlock is workspace deletion against a writer that checks
assignees ([DAT-005](dat-005.md)); the writer side is now retried, and after the
deletion commits it gets a 404.

## API behavior changes

- `PATCH /projects/:pid/statuses/reorder` and `POST /tasks/:tid/subtasks/reorder`
  answer 400 "The order must list every status column of the project exactly
  once" / "… every subtask of the task exactly once" for duplicate or missing
  IDs. Unknown IDs keep their previous answers (404 for columns, 400 for
  subtasks). The web app always sends complete lists; a list made stale by a
  concurrent create is now refused instead of corrupting the order.
- A move no longer answers 409 "The task was moved at the same time": it reads
  the task's column after taking the lock and moves the task from wherever it
  is now.
- Task lists add `id` as the last sort key; subtask lists add creation time and
  id; column lists (the status list, reorder answer, project detail and backup
  export) add id, and so do the column choices: the first column for a new
  task, a deleted column's target and the column that inherits completion.

## Existing rows

No migration. Rows written before this change may share a position; the total
board order shows them deterministically, and the next move, bulk move or
column delete that renumbers the column repairs it, as does a complete column
or subtask reorder.

## Not covered

- `PATCH /projects/:pid/custom-fields/reorder` still accepts duplicate or
  incomplete lists (custom-field module, handled with the custom-field work).
- Order writes of one project now queue. Each waiting request holds a pooled
  database connection for up to 5 s (see "Bounded lock waits"). A project held
  longer than that answers 503 to its queued writers.
- The web app does not refetch its column or subtask list after a refused
  reorder (frontend follow-up).

## Tests

`packages/backend/tests/integration/task-order-graph.test.mjs` sends real HTTP
requests over TCP to the app against PostgreSQL. Barrier cases hold a row lock
on a separate control connection to park the first request inside its
transaction, check in `pg_stat_activity` that the second request waits behind
the first, and then release it: opposite dependency adds, a dependency add and
a removal, two task creates, two subtask creates, two moves in one column, a
move against a bulk update whose row order would deadlock, two deletes of
non-empty columns, two completion-column updates and two column creates. A
forced deadlock (confirmed in `pg_stat_database.deadlocks`) checks that the
aborted move is retried and succeeds. A project row held for 12 s, with as
many creates queued on it as the pool has connections, checks the bound. The
creates must get the 503 between 4 s and 9 s and store nothing, and the
unrelated project's read and create must succeed within 9 s. Single-request cases cover bulk status
changes, bulk and single unarchive, column deletion and the reorder checks.
Free-running cases fire requests together without a barrier: dependency adds
around a loop, bursts of creates, duplicates and template instantiations,
deletes of the last two columns, and a mixed workload of creates, moves, bulk
updates and status changes. Each case checks that every column's active tasks
have distinct (where stated, contiguous) positions, that no dependency cycle
exists and that there is one completion column.

`packages/backend/tests/task-order-retry.test.mjs` checks the retry policy:
which errors are retried, the attempt limit, and that each attempt sets the
wait bound, locks the project and restores the statement timeout. It also
checks that a lock or statement timeout becomes the 503 and is not retried,
and that a caller's transaction is used as is.

```bash
pnpm --filter @pm/shared build
TEST_DATABASE_URL="$AUDIT_DATABASE_URL" pnpm --filter @pm/backend test:integration
```
