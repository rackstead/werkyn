# File share-link manager authorization

Updating or deleting a Drive share link now requires a current membership in the
link's requested workspace and either its creator or that workspace's ADMIN role.
VIEWER, removed members, noncreators and admins from other workspaces cannot manage
the link. Supplied or stale role strings do not override the database membership.
Both controllers carry the workspace/user context, and the service scopes its
lookup and mutation to that workspace before changing a link.

Manager authority follows the link independently of its source files. A current
creator or same-workspace admin can disable or delete an expired link, a link whose
file access has changed, or an empty link after source deletion. The merged source
metadata filters still omit foreign and trashed sources from responses. Deleting
a link removes its sharing relations without deleting source files or stored bytes.

Run the intended-permission HTTP/PostgreSQL regressions against a migrated disposable
database:

```sh
TEST_DATABASE_URL=<disposable-url> pnpm --filter @pm/backend exec node --import tsx --test tests/integration/share-link-management.test.mjs
```

Fixtures cover creator/admin success, noncreator/file-owner/foreign/viewer denials,
removed membership, role demotion and forged/stale contexts. Denials preserve link,
source and relation rows and perform no storage, notification or event operations.

This is SEC-002's manager boundary. Explicit-share grants and read-list consistency
(SEC-013), attachment policy (SEC-006), public password grants, credential revisions,
hash-free DTOs and token hardening (SEC-001) remain separate. Source authorization,
active-content response policy and existing password update behavior are preserved.
Checks use current membership on subsequent operations; they do not serialize
membership revocation with an operation already admitted.
