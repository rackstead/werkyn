# P02b: cursor tie-breakers and bounded lists

P02a measured two problems this change fixes (see `p02a.md`, follow-ups 2, 5,
6, 7 and 8):

- **Cursor pages without LIMIT.** With Prisma's `cursor` and an ORDER BY on a
  column that several rows can share, Prisma leaves LIMIT out of the SQL and
  trims the rows in memory: an older chat history page read 12,235 rows to
  return 50. Rows with equal sort values also had no defined order, so a page
  boundary inside such a group could repeat or skip rows. Chat history,
  threads and message search were fixed separately (`chat-cursor-pagination.md`,
  `chat-search-pagination.md`); this change covers the remaining lists.
- **Lists without a bound.** My tasks, time reports, the workspace activity
  total and the channel list's members read and returned every row.

## Cursor lists: a unique tie-breaker

Each list keeps its sort and adds the row ID as the last ORDER BY column, in
the same direction:

| Endpoint | Order |
| --- | --- |
| `GET /api/chat/:wid/bookmarks` | `createdAt DESC, id DESC` |
| `GET /api/wiki/pages/:pgid/versions` | `createdAt DESC, id DESC` |
| `GET /api/workspaces/:wid/files/shared-with-me` | `createdAt DESC, id DESC` |
| `GET /api/tasks/:tid/comments` | `createdAt DESC, id DESC` |
| `GET /api/workspaces/:wid/files` (folders, root, search, trash) | `isFolder DESC`, the sort column, `id`, all in `sortOrder` |
| `GET /api/chat/:wid/channels/:channelId/members` (newly paged) | `joinedAt ASC, id ASC` |

With a unique last column Prisma's `cursor` emits `LIMIT limit + 1`. The
exception is a nullable sort column: for the drive listing sorted by `size`,
Prisma still reads every following row and trims them in memory, so that sort
builds the "rows after the cursor" condition itself (`filesAfterBySize` in
`files.service.ts`). Null sizes keep PostgreSQL's default placement: last when
ascending, first when descending. Writing the same condition out for the
`uploadedBy` sort was measured and rejected: the relation filter added two
joins to an already large query and planning went from 3 to 18 ms.

**Cursor compatibility.** Cursors are still the raw ID of the last row of the
previous page, so every cursor an earlier version handed out is still valid
and continues after that row. Before this change, rows sharing the cursor
row's sort value came back in no particular order, so a cursor issued inside
such a group may continue in the new order: some rows of that group can be
skipped or repeated once, at that one boundary. Every later page is exact.
Answers to cursors that are not in the list are unchanged and checked by one
ID lookup with the list's own filters before the page query:

- an unknown ID, or a row outside the list (another user's bookmark, another
  page's version, a file in another folder, a share or comment of someone
  else), gives an empty page, as the in-memory trimming did;
- for task comments only, an unknown ID restarts at the first page and a
  comment of another task gives an empty page, as before.

A row that stops matching between two requests (a bookmarked message deleted,
a file moved) is no longer a valid cursor and gives an empty page, the same
rule as chat history and search. The lookup and the page query are two
statements. If the cursor row leaves the list in the milliseconds between
them, that page is empty (row deleted) or starts one row late (row still
stored but filtered out, because Prisma's `skip: 1` then skips a real row);
the size sort, which does not use Prisma's cursor, starts at the right row. Pages
are not a snapshot; rows written between requests can appear or not, but rows
that existed before are neither repeated nor skipped.

## Bounded lists

Defaults apply when a client sends no paging parameters, so existing clients
get a bounded first page and an indicator that more exists.

### My tasks: `GET /api/workspaces/:wid/my-tasks`

- Pages of `limit` tasks (default 100, maximum 200) in the existing order,
  project name then position, with the project ID and task ID added as
  tie-breakers. Tasks of two projects with the same name no longer interleave.
- The response adds `nextCursor`, `null` on the last page. The cursor is an
  opaque string that carries the last row's sort values (not just its ID), so
  completing, unassigning or moving that task between requests does not end
  the list early. A malformed cursor returns 400.
- New optional filters, with the task list's meaning: `dueAfter` and
  `dueBefore` (inclusive `YYYY-MM-DD`; tasks without a due date are left out)
  and `completed` (`false`: outside completion columns; `true`: in them). The
  comparison is the database's string order, which is date order for the
  `YYYY-MM-DD` values the API stores.
- The task objects are unchanged.

### Time reports: `GET /api/workspaces/:wid/time/reports`

- Group and summary totals (hours, costs per currency, unrated hours, skipped
  entries) still cover every matching entry and are computed exactly as before.
- Each group lists at most `entryLimit` entries (default 20, 0 to 500) and one
  response at most 5,000 entries across its groups. Groups keep their order
  (that of their first entry); when the 5,000 are used up, later groups list
  fewer entries or none.
- Each group adds `entryCount` (all its entries), `hasMoreEntries` and
  `nextEntryCursor` (the ID of its last listed entry; `null` when it lists
  none or is complete).
- `GET /api/workspaces/:wid/time/reports/entries` returns the next entries of
  one group: the report's filters plus `groupKey` (the group's `key`), `cursor`
  (`nextEntryCursor` or the previous page's `nextCursor`; omit it to start at
  the group's first entry) and `limit` (default 100, maximum 500). Entries are
  in report order, `date`, `createdAt`, then ID, priced as in the report. A
  cursor that is not an entry of that group with those filters gives an empty
  page. Admins only, like the report.
- `GET .../time/reports/export` ignores `entryLimit`: the CSV still lists
  every entry.

The report reads the entry columns of every matching entry once, without
joins, and then looks up member, project and task names by ID for the listed
entries and the group labels only. Before, the names were loaded for every
entry of the range.

### Workspace activity: `GET /api/workspaces/:wid/activity`

- Pages are unchanged (`page`, `limit` up to 100) and now ordered
  `createdAt DESC, id DESC`, so equal timestamps no longer repeat or skip rows
  between pages. The task activity list (`/api/tasks/:tid/activity`) uses the
  same order.
- `pagination.total` counts at most 1,000 rows. Above that it reports 1,000 and
  `pagination.totalCapped: true`; `totalPages` follows `total`.
- `pagination.hasMore` says whether another page follows; it is exact at any
  depth.

The exact count of every visible activity row was most of the request's time
(P02a). The capped count is a raw `count(*)` over a `LIMIT 1001` subquery with
the same visibility condition; Prisma's `count` with `take` adds an
`ORDER BY id` that makes PostgreSQL read every row first.

### Channel members

- `GET /api/chat/:wid/channels`: each channel lists its first 10 members by
  join time (then ID). `_count.members` stays the full count, so
  `members.length < _count.members` means more exist. A DM has at most eight
  members, so DM lists are complete; the web client uses `members` only for
  DMs.
- `GET /api/chat/:wid/channels/:channelId/members`: pages of `limit` members
  (default 100, maximum 200) with `nextCursor`, `null` on the last page.

## Web client

- **My tasks widget:** the first page, then **Load more tasks**. The overdue
  box uses its own query (`dueBefore` = yesterday, `completed=false`), so it
  shows every overdue task regardless of how many list pages are loaded; it
  shows `N+` and **Load more overdue tasks** when that query has more pages.
- **Upcoming dates widget:** asks for open tasks due today through seven days
  ahead (`dueAfter`, `dueBefore`, `completed=false`) with **Load more**.
- **Timesheet task picker:** **Load more tasks** at the end of the list.
- **Time reports:** an expanded group shows its listed entries and
  **Load more entries (N more)** while the group has more.
- **Channel settings:** the member count comes from the channel; the list
  loads 100 at a time with **Load more members**. The "Add members" search
  hides only members already loaded; adding someone who is already a member is
  a no-op, as before.

Reading the table:

- **Bounded lists:** my tasks reads 72% fewer rows and returns 100 tasks
  (142 KB) instead of 841 (1.15 MB), 3.2 times faster. The activity count cap
  removes 98% of the rows read, 7 to 8 times faster. The channel list returns
  324 member rows instead of 2,308, 94 KB instead of 605 KB, 3.5 times faster.
  The report still reads every entry of the 90 days for its totals (154,528
  rows, unchanged) but no longer loads names for all of them or returns them:
  2,840 entries (858 KB) instead of 17,731 (5.1 MB), 2.8 times faster.
- **Cursor pages:** the page query now returns at most `limit + 1` rows: 51
  instead of up to 1,336 for a deep admin drive search page. Rows read follow
  the scan the query needs (the drive search is a sequential `ILIKE` scan, R18
  item 1), so they change little. In this fixture the other cursor lists are
  short (at most 169 files per folder, 31 bookmarks, 30 shares, 4 comments,
  3 versions per item), so the one-row cursor lookup costs more than the rows
  it saves: p50 is 1 to 2.5 ms higher on those second pages (the shared-with-me
  lookup repeats the file read-access condition). First pages are unchanged.
  The saving grows with the list; on main an older chat history page read
  12,235 rows to return 50 (P02a).
- **Planning:** writing the keyset condition out for every drive sort was
  measured first. It doubled planning time for the name sort (3 → 5.4 ms) and
  raised it to 18 ms for the uploader sort (two extra joins), so only the
  nullable size sort uses it; the others use Prisma's cursor with the ID
  (planning 5.9 to 7.8 ms, execution 14 to 16 ms, against 3 + 20 to 22 ms on
  main for the same search page).

## Remaining R18 items

Not changed here:

1. **Search:** title, description and chat content `ILIKE '%term%'` scans
   (pg_trgm needs a privilege decision).
2. **Board payload:** the largest board is 10,789 tasks and 20.9 MB.
3. **Task move renumbering:** one UPDATE per task in the column.
4. **Unread counts:** one COUNT per channel; other `_count` includes on lists.
5. **Notification visibility plans** that change with unrelated indexes.
6. **API key `lastUsedAt` writes** (throttling not measured).
7. **Shared by me** (`/files/shared-by-me`) still returns every share and link;
   it ignores `cursor` and `limit`.
8. **Time report totals** still read every matching entry (narrow columns); a
   SQL aggregation would need the per-entry currency rounding in SQL.
9. **Timesheet entries** (`/time/entries`) and the **DM and channel lists**
   themselves are not paged; they are bounded by the date range and the
   caller's channels.
10. **Offset pages** elsewhere (task list, projects) keep their sorts; the task
    list already ends in `id`.

## Tests

- `tests/integration/cursor-tiebreak-pagination.test.mjs` (22 tests):
  bookmarks, versions, shared-with-me, comments, the drive listing (every sort
  column in both directions, folders, null sizes, search) and channel members.
  Each list is walked at several page sizes over rows with equal sort values;
  walked again while two rows with the cursor row's sort value (one ID before
  it, one after) arrive after each of the first pages; continued from listed
  IDs as old cursors; and asked with unknown and out-of-scope cursors. A
  separate Prisma client records the page SQL and checks `LIMIT limit + 1`.
- `tests/integration/bounded-lists.test.mjs` (15 tests): my-tasks defaults, order, ties,
  inserts between pages, filters, long project names and validation; report
  defaults, exact totals against `entryLimit=500`, the entries endpoint from
  each group's cursor and from the start, inserts between pages, scope,
  the 5,000-entry response limit and the complete CSV; the activity total cap
  and offset pages over equal timestamps; channel list member previews.
- On main (9b9cf4d) the same two files fail 35 of 37 tests: the page queries
  have no LIMIT, a walk at one row per page skips a row of a group with equal
  timestamps (bookmarks: 9 of 10 rows returned), and the new parameters and
  fields do not exist. The two that pass check null-size placement and a
  search walk; the latter failed in an earlier main run, because main returns
  equal names in no fixed order.
- Web client: `paged-lists.test.tsx` (load more in both dashboard widgets, the
  overdue box, the timesheet picker, report groups and channel member pages)
