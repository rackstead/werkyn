# Environment validation, log redaction, health probes and shutdown

Startup now rejects configuration that the server could not use correctly, with one
message per variable that never repeats the supplied value (enumerated settings list
their allowed choices):

- `PORT`, `SMTP_PORT` and `DEX_INTERNAL_PORT` must be whole numbers from 1 to 65535;
  `MAX_FILE_SIZE` must be a positive whole number of bytes.
- `COOKIE_SECURE` and `SMTP_SECURE` accept only `true` or `false`. Values such as `1`
  or `TRUE` were previously read as `false` without warning.
- `FRONTEND_URL` must be an absolute http(s) URL without credentials, query or
  fragment; a trailing slash is removed. With `FRONTEND_URL=https://host/`, the
  derived Dex issuer and callback were `https://host//dex...`; they are now
  `https://host/dex...`. Update any upstream identity provider that registered the
  double-slash callback. `CORS_ORIGIN` is a comma-separated list of
  http(s) origins; entries are trimmed and normalized, and `*` is rejected.
- `DATABASE_URL` must be a PostgreSQL connection URL with a host and database name.
  `COOKIE_DOMAIN` must be a bare domain name.
- `COOKIE_SAMESITE=none` requires secure cookies, because browsers discard insecure
  SameSite=None cookies. Production still defaults `COOKIE_SECURE` to `true` when it
  is unset.
- An empty value (`PORT=`, `FRONTEND_URL=`) means "use the default". Required
  variables that are empty are reported as missing.

The local HTTP install in `docker-compose.yml` keeps working: it sets
`COOKIE_SECURE=false` explicitly with `http://localhost` URLs. A production server whose
`FRONTEND_URL` uses https but whose cookies are not Secure still starts and logs a
warning. The production signing-secret checks are unchanged.

The CSP `upgrade-insecure-requests` directive uses the same validated
`COOKIE_SECURE` boolean as refresh and share cookies. Production includes it when
the flag is unset, empty or whitespace; explicit `true` also includes it. Explicit
`false` keeps the local HTTP install working, and development/test defaults omit
the directive. Other CSP directives keep their existing values.

`tests/integration/csp-cookie-config.test.mjs` runs each configuration in a separate
process, starts the real HTTP application and checks CSP against actual login and
logout cookie flags. It also checks unchanged directives and invalid-startup
controls. These loopback checks cover configuration and response headers; they do
not exercise an HTTPS browser deployment.

The shared logging policy removes known credential fields and URL grants. Request
URLs in access logs keep their path and harmless query parameters, but these values
are replaced with `[REDACTED]`: link tokens
in reset, verification, invitation and public-share paths (API and browser routes),
and credential-like query parameters such as `token`, `code`, `state` and `hmac`.
Authorization, cookie and API key headers, and fields such as `password`, `token` and
`pass`, are censored in structured logs. The same applies to messages, error messages
and the standalone startup/mail logger. Messages that pino takes from an error, as
in `log.error(err)`, are redacted too.
An explicitly undefined structured `msg` also uses that redacted error fallback;
defined structured messages and explicit message arguments keep their selection.

Structured URL fields use the same policy: `source` (including the installed
`@fastify/reply-from` Dex proxy's "fetching from remote server" log), `url` and
the mailer's `previewUrl`. Structured `msg`/`message` fields and serialized error
messages, stacks and those URL fields are sanitized as well. This preserves the
host/path, harmless query parameters, request IDs, status and error context in
JSON and development pretty logs, at every enabled log level. Sanitization makes
a log-only copy; upstream request targets, bodies and headers keep the existing
proxy behavior. It does not recursively inspect arbitrary nested objects or
replace field-specific serializers and credential redaction.

`tests/proxy-log-redaction.test.mjs` exercises the actual proxy and logger with a
bounded loopback upstream, synthetic OIDC/Dex query credentials (including
percent-encoded and mixed-case names), success, upstream 500 and disconnected
upstream responses. It checks exact forwarded targets, body bytes and allowed
headers, retained safe context, error serialization, reset/invite/public-link URL
fields, caller immutability and both pretty transports. The synthetic callback
code probe covers the proxy passthrough; it does not establish exposure from an
external identity provider. The earlier real mock-Dex flow observed raw
state/nonce/challenge in structured `source`, but no authorization code there.

This change does not remove credentials from historical logs or copies held by
log collectors, backups or operators. Retention and incident cleanup remain
operator work. Future structured URL fields need the shared policy or their own
serializer.

There are now separate probes:

- `GET /api/live` is liveness. It answers while the process is serving and does no
  database work.
- `GET /api/ready` is readiness. It returns 200 only when the database answers and
  every migration shipped with the build has been applied. Otherwise it returns 503
  with `database` and `migrations` check states (`unavailable`, `pending`, `failed`
  or `unknown`).
- `GET /api/health` stays for existing monitors and still reflects whether the
  database is reachable: 200 `ok`, or 503 `unavailable` instead of the previous 500.

Clients do not cache the probes. `/api/live` and `/api/ready` do not count against
the client rate limit; `/api/health` keeps the normal limit it always had. Database
work is bounded instead: concurrent probes share one evaluation with one three-second
deadline for all of its steps, and its result is reused for one second. Details are
logged on the server, not returned.

On SIGTERM or SIGINT, the server stops three steps in order: the blob-cleanup worker,
then Dex, then the HTTP server. A failure in any step is now logged, the later steps
still run, and the process exits with status 1. Each step has its own budget (blob
cleanup 1 s, Dex 5.5 s, enough for Dex's SIGTERM-then-SIGKILL stop). A stalled cleanup
batch therefore cannot keep Dex from being signalled. All of shutdown is limited to
eight seconds, under Docker's ten-second stop timeout, and the deadline log names the
step that hung. A repeated signal more than a second after the first forces
exit. An immediate duplicate, such as one Ctrl+C delivered by both the terminal and
the runner, is ignored. A startup failure is logged through the application logger.

Run `pnpm --filter @pm/backend test` for the configuration, redaction, probe and
shutdown tests. The readiness test against a migrated database is in
`tests/integration/health-readiness.test.mjs`.

Not included here: authenticated `?token=` access JWTs are still accepted on any route
(the PDF preview uses them). The URL is redacted in logs, but browser history and
proxies can still record it. Scheduler timers are not drained on shutdown (OPS-005).
Production frontend documents and assets no longer count against the API rate
limit (OPS-011). Fingerprinted build assets are immutable; HTML and unhashed
public files revalidate. Upload/private paths keep their existing quotas and
response isolation. See `static-asset-delivery.md` for the scope and checks.
