# Consistent task mutation permissions

An existing task can be edited by its workspace ADMIN, or by a current workspace
MEMBER who is both a project member and an assignee of that task. VIEWERs cannot
write even when they have an assignment. Rights come from current database
membership; a caller-supplied role cannot widen them.

The same parent-task policy now covers direct edits, moves, label additions and
removals, dependencies, all subtask mutations and custom-field values, including
clearing a value. Bulk updates validate every selected task before any updates or
activity writes. A MEMBER may change their own assignment while preserving every
other assignee. Archive, unarchive and delete require ADMIN through direct and
bulk service entry points.

Self-assignment and self-removal remain available to project MEMBERs without an
existing task assignment. Project discussion remains available without task
assignment under the existing comment policy. Creating and duplicating a task
retain their existing project-member workflows, with current workspace-role
checks; member creation still includes its creator among the assignees.

The regression suite uses actual Fastify/JWT/Prisma/PostgreSQL and temporary
storage. It checks unassigned-member alternatives, mixed-batch rejection without
partial mutations, current role/assignment changes, caller role mismatches,
VIEWER/project-outsider/foreign-ADMIN denial, and valid member/ADMIN task and
subtask lifecycles. Denial snapshots cover rows, relationships, activity and
notifications, with no project broadcasts.

Use only an explicitly designated, migrated disposable PostgreSQL database.
Referenced-resource integrity, existing corrupt relationships, ordering and graph
concurrency, general membership-revocation serialization, and frontend permission
affordances remain separate work. The checks establish permission at admission;
they do not claim that every write is serialized against concurrent membership
changes. No schema, dependency or migration change is included.
