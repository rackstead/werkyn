# Attachment source and target access

Attachments require both current source-file read access and access to their actual
task or comment project in the requested workspace. Linking a file does not grant
file access to other discussion participants. Explicit file/folder shares and
direct/group team access remain independent current read paths and are rechecked
for lists and downloads after revocation.

Attachment writes follow discussion participation: current workspace MEMBERs with
project membership and current workspace ADMINs can link readable files without
being task assignees. VIEWERs can read only when both source and target permit it.
Deleting a link requires the current uploader or same-workspace ADMIN, plus current
target write authority. This permits removal of stale sources without granting
source reads. Removing a link does not delete or transfer ownership of its file.

Only the declared `task` or `comment` target type is resolved. Missing, foreign or
inaccessible targets deny before attachment rows or storage operations, including
when IDs coincide across tables. Supplied role strings cannot replace current
workspace/project membership. No source-file grant promotes project membership.

Lists omit existing unreadable, trashed, folder or missing/empty-path sources.
Readable rows use current source metadata instead of cached attachment names and
paths. Genuinely null-file rows, including Prisma `SetNull` deletion, retain a
generic “Unavailable file” placeholder for target-authorized cleanup: no cached
source name, path, identifier or size is returned. The UI marks these unavailable
and disables downloads. Downloads return intentional 404 for missing sources and
never fall back to cached storage paths. Deleted targets remain inaccessible;
historical orphan cleanup belongs to the separate lifecycle work.

```sh
TEST_DATABASE_URL=<disposable-url> pnpm --filter @pm/backend exec node --import tsx --test --test-concurrency=1 tests/integration/attachment-access.test.mjs
```

The suite checks current source and target rights, typed ID collisions, legitimate
unassigned participation, explicit/folder/direct/group grants and revocation,
independent copies, VIEWER and stale roles, uploader/admin deletion, null-source
privacy, current metadata and denial without row, storage, notification or event
changes. Component coverage checks unavailable downloads and legitimate cleanup
and downloads. Harmless document/media fixtures retain forced attachment downloads
with an octet-stream MIME type, including inline query aliases.

Public-share passwords (SEC-001), concurrent/admitted-read revocation, historical
data repair, durable blob/orphan cleanup and graph serialization remain separate.
This change preserves existing attachment response protection; it does not add the
Drive endpoint's sandbox/private-no-store helper or claim a broader SEC-017 closure.
Chat `message` attachments remain unsupported by the task/comment schema. File
usage counts remain source-authorized numeric totals without target details.
Browser, lifecycle, load and performance gates are not established by these tests.
