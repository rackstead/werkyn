# Realtime sockets end with their sign-in session

DAT-006 (PR #80) made realtime revoke membership changes immediately and
close a socket when the access token that opened it expires. Access tokens
did not say which sign-in session they belonged to, so nothing tied an open
socket to a session. Logout, a password change or reset, a password login that
replaces the account's other sessions and refresh-token reuse revoked the
refresh-token family, but every socket opened with that session's access
tokens stayed open and kept receiving events until the token expired (up to
15 minutes), and a client could open new sockets with the token in the
meantime.

## Session claim

Every access token now carries `sid`, the id of the refresh-token family
(`RefreshTokenFamily.id`) it was issued for. Login, registration, OIDC sign-in
and refresh all sign it: a new session's token names the new family and a
refreshed token names the family the presented cookie belongs to.
`startRefreshSession` returns the family id with the first refresh token.

## Socket authentication

A socket authenticates with its first message (`{"type":"auth","token":...}`).
After the signature and expiry check, the server looks the session up:
the family must exist, belong to the token's `sub` and not be revoked. A
deleted account's families are deleted with it, so this also covers the
account. The socket is then bound to that session until it closes; it still
closes at the token's `exp` as before.

Close codes on `/api/ws`:

| Code | Reason | When |
| --- | --- | --- |
| 4002 | Authentication failed | invalid signature, expired token, no `exp` |
| 4004 | Session expired | the token expired while the socket was open, or the token names no session (`sid` missing) |
| 4005 | Session revoked | the token's session has ended, at authentication or later |

A client that receives 4004 or 4005 should refresh once and reconnect with
the new access token instead of retrying the old one. The bundled frontend
(`WebSocketClient`, `RealtimeProvider`) holds every reconnect, including the
one on tab focus, until that single refresh settles. A new token rebuilds the
client. If the refresh fails after 4005, the provider expires the session with
the auth store's `expireSession(generation)`. That is a local sign-out that sends
nothing to the server, and tabs that have already moved on to a later sign-in
ignore it. It is skipped if the identity changed or another tab supplied a new
token meanwhile. After 4004 a failure may be transient (network, busy), so the
client resumes its reconnect backoff and leaves sign-out to the HTTP 401 path.
A close that follows the provider's own disconnect on an identity change is
ignored.

## Ending a session

Each operation that revokes families calls `endSessions(familyIds)` right
after its transaction commits and before it responds. That closes every
socket bound to one of those families with 4005 and leaves the account's other
sessions alone unless the operation revoked them too:

| Operation | Sessions ended | Sockets closed |
| --- | --- | --- |
| Logout | the cookie's family | that session's sockets only |
| Password change | every family of the account, including the caller's (SEC-027) | all of the account's sockets |
| Password reset | every family of the account | all of the account's sockets |
| Password login | the account's other families | their sockets; the new session's are unaffected |
| Refresh-token reuse | the reused token's family | that session's sockets only |
| OIDC sign-in, registration, refresh rotation | none | none |

A refused password change, a superseded (409) or busy (503) refresh and a
logout with an unknown cookie end nothing.

There is no account deletion, deactivation or instance-role change endpoint.
`disconnectUserSockets(userId)` closes every socket of an account and is kept
for one. Workspace, project and channel membership changes do not end the
session; they drop the affected subscriptions (DAT-006, PR #80).

### Revocation racing authentication

The session lookup and the revocation run concurrently. Each authentication
registers itself while its lookup is in flight, and `endSessions` marks the
in-flight authentications of the ended sessions as well as closing registered
sockets. An authentication checks the mark after its lookup and registers the
socket in the same synchronous step, so for a lookup that read the session
before the revocation committed:

- if the socket was registered before `endSessions` ran, `endSessions` closes it;
- otherwise the mark is set and the authentication refuses it with 4005.

A lookup that starts after the commit reads the revoked family and refuses
the socket. No order leaves a socket open on an ended session in this process.

## Access tokens without `sid`

Tokens issued before this change have no `sid`. They stay valid over HTTP until
they expire, at most 15 minutes after deployment, exactly as before; HTTP does
not look sessions up for any access token (SEC-011). They cannot open a socket:
a socket opened with one could not be closed with its session, which is the gap
this change closes. The server answers 4004 rather than 4002 so that a client
refreshes at once and reconnects with a session-bound token instead of
retrying with backoff until its token expires. A deployment restarts the
process and closes every existing socket anyway, so no socket opened before
the change survives it.

## Validation

`packages/backend/tests/integration/realtime-session-end.test.mjs` uses real
TCP WebSocket clients, the real HTTP handlers and PostgreSQL:

- two sessions of one user plus another user: logout of session A closes A's
  two sockets with 4005 and nothing else; B and the other user keep receiving,
  A's token can no longer open a socket and B's can;
- password change (through the route, with session A's token) and password
  reset close both sessions' sockets; a refused change closes nothing; a
  sign-in after the change opens a socket;
- a password login closes the other sessions' sockets and the new session can
  connect;
- refresh-token reuse closes only the reused family's sockets;
- a token without `sid` gets 4004 on the socket and still 200 over HTTP;
  unknown, foreign and deleted-account sessions get 4005;
- a deterministic race: the session lookup reads the live session, the logout
  commits and responds, then the lookup resumes and is refused with 4005, and
  nothing is delivered;
- 30 logouts racing socket authentications with 0–14 ms offsets, covering both
  "registered then closed" and "refused at authentication": every socket ends
  with 4005;
- each session-ending case measures when the close frames arrive relative to
  the request and its response.

The existing realtime tests mint session-bound tokens.

## Not covered

- Issued access tokens still work over HTTP until they expire after logout,
  a password change or reset (SEC-011). The `sid` claim makes an early check
  possible; adding it changes every authenticated request and is separate.
- Multi-node deployments: revocation and the race guard are in-process.
  Realtime state already lives in one process; another backend instance would
  not close its sockets until their access tokens expire (at most 15 minutes),
  although new sockets there are refused because the lookup reads the
  database.
- Personal API keys cannot open sockets (WebSocket authentication requires an
  access token), so their revocation has no realtime effect.
