# Custom-field values follow their field definition

## The problem

`setFieldValue` checked only the JSON type of a value (and, more recently,
that a DATE was a real calendar date). A URL field accepted any string,
including `javascript:` and `data:` URLs, and the task and list views
rendered every stored value as a link. A SELECT or MULTI_SELECT field accepted values that were not among its
options, and a MULTI_SELECT accepted the same option twice. A required field
could be cleared. Creating a select field rejected an empty options list, but
an update could empty it, add duplicate options, or give options to a text
field. Renaming or removing an option left the old value on every task that
had it (DAT-013).

## Value rules

Every value write goes through `PUT /api/projects/:pid/tasks/:tid/custom-fields/:fieldId`.
This covers the web app, personal API keys and any other REST client, since
they all reach the same handler. The value is checked by
`checkCustomFieldValue` in `@pm/shared`, against the field definition as it is
committed when the write runs:

| Type | Accepted value |
| --- | --- |
| TEXT | a string |
| NUMBER | a finite number |
| CHECKBOX | `true` or `false` |
| DATE | a real `YYYY-MM-DD` date between 1900 and 2999 |
| URL | an absolute `http://` or `https://` URL with a host, no whitespace or control characters, at most 2048 characters |
| SELECT | one of the field's option values, exactly as written |
| MULTI_SELECT | a list of the field's option values, each at most once |

`null`, blank text and `[]` mean "no value". They delete the stored value.
Empty strings and empty lists are no longer stored.

A rejected value gets a 400 that names the field:

```json
{
  "statusCode": 400,
  "error": "Bad Request",
  "message": "\"Spec\" must be an http or https URL, such as https://example.com, without spaces",
  "details": [{ "field": "value", "message": "\"Spec\" must be an http or https URL, such as https://example.com, without spaces" }]
}
```

A value of the wrong JSON shape (an object, or a list of non-strings) is
still rejected by the request schema with `"message": "Validation failed"`
and `details[].field` set to `value`. The web app shows the `message` of
either response in its error toast.

Task creation, quick add, templates, the recurrence scheduler and bulk edits
never write custom-field values; they do not accept them in their request
bodies. The only other writer is backup restore (below).

## Required fields

A required field rejects an empty value: `null`, blank text or `[]`. This
applies whether or not the task already has a value, so a
required value can be changed but not cleared. `false` (CHECKBOX) and `0`
(NUMBER) are values, not empty values.

Required is not enforced when a task is created. Quick add, the full create
dialog, template instantiation, the recurrence scheduler, task duplication,
bulk edits and backup restore create tasks without custom-field values, and
none of them can supply one. Recurring tasks run unattended. A task therefore
starts with its required fields empty, and someone fills them in afterwards.
Rejecting the task instead would make templates and recurring schedules stop
working as soon as a project adds a required field.

Making a field required later does not check or change existing tasks.

## Option definitions

- SELECT and MULTI_SELECT fields need at least one option on create and on
  update. Each option value appears once, and must not be blank.
- Other types have no options. A request that gives them options is
  rejected.
- The type of a field cannot change. A PATCH with a different `type` gets a
  400 ("create a new field instead"). Sending the current type is accepted.

An option's `value` is its identity: stored values name options by value.
`PATCH /api/projects/:pid/custom-fields/:id` with `options` replaces the whole
list, and stored values are migrated in the same transaction:

- `renameOptions: [{ "from": "Mid", "to": "Medium" }]` moves every stored
  `Mid` to `Medium`. `from` must be a current option and `to` an option in the
  new list. Each option can be renamed once. Renames apply all at once, so two
  options can swap names, and several options can merge into one (a
  MULTI_SELECT list then keeps the merged option once).
- An option that is neither kept nor renamed is removed. A SELECT value that
  names it is deleted. A MULTI_SELECT list loses it, and is deleted when
  nothing is left.
- This also applies to required fields: the field then shows as empty on
  those tasks.
- Every task whose value changed gets a `custom_field_changed` activity entry
  with `reason` `option_renamed` or `option_removed`, written by the person who
  edited the field. Clients receive `task_updated` (bulk) as well as
  `custom_field_updated`.
- The response reports what changed:
  `{ "data": <field>, "meta": { "migratedValues": 1, "clearedValues": 1 } }`.

Renaming the field itself never touches values (they refer to the field by
ID), and deleting a field deletes its values, as before.

Stored values of another shape than the field type, written before these
checks, are left alone by a migration; the report below lists them.

## Concurrency

A value write and an options edit for the same field are serialized. After
the Project row (`FOR KEY SHARE`, as in `utils/task-references.ts`), a value
write holds the CustomField row `FOR SHARE` while it checks and stores the
value. Value writes for one field do not wait for each other. An options
edit holds the row `FOR NO KEY UPDATE`, then locks the tasks that have a value
for the field (`FOR KEY SHARE`, by ID) and only then reads and migrates the
values. Either the value write commits first and the edit migrates it, or the
edit commits first and the value is checked against the new options. Locking
the tasks before the values keeps a concurrent task deletion from deadlocking
with the migration's activity entries. A value write that waits longer than
its transaction timeout (5 s) for a large migration gets the retryable 409.

## Backup restore

Preview and restore apply the same rules through `planCustomFieldRestore`, so
the preview's warnings match what the restore does:

- An unknown field type rejects the backup with a 400 in preview and restore
  (preview used to accept it, and the restore then failed with a 500).
- Select options are kept when well formed, once each; each field that lost
  options gets a warning. Other types are restored without options.
- A value that does not pass `checkCustomFieldValue`, or a second value for
  the same field of a task, is skipped with one warning per field. Empty
  values are skipped silently, as is a value whose field is not in the backup.
- Required fields are not enforced, as for any task created without values.

## Existing data

Rows written before this change can still break these rules. Run the read-only
report first:

```sh
DATABASE_URL=... node packages/backend/dist/scripts/custom-field-value-report.js [--json] [--limit=N] [--workspace=ID]
```

It runs in one `READ ONLY` transaction and prints IDs and reason codes only,
never names or values. Every sample names the repair it proposes:

| Key | Proposed repair |
| --- | --- |
| `custom_field_options` | `rewrite_options` (PATCH each well-formed option once), `add_options` (a select field without options) or `drop_options` (set options to NULL on a non-select field) |
| `custom_field_value_empty` | `delete` the row |
| `custom_field_value_type` | `delete` the row after review |
| `custom_field_value_date` | `delete`, or rewrite it with the intended date |
| `custom_field_value_url` | `delete`; the task view no longer renders it as a link |
| `custom_field_value_option` | `delete`, or restore/rename the option first if the value should be kept |
| `custom_field_value_repeated` | `dedupe`: rewrite the list keeping the first occurrence |

The exit status is 0 when clean, 2 when issues were found and 1 on error. No
automatic repair ships with this change: review the report, repair through
the API (options, values) or with reviewed SQL, and run the report again until
it is clean.

Until then, the task view and the list view show a stored URL value as a link
only when it is an http(s) URL. Other values are shown as plain text.
