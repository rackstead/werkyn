# Account email delivery and seed safety

Without SMTP settings, the server used to create an Ethereal account in every mode,
including production. Ethereal is nodemailer's public test inbox, so verification and
password-reset links were sent to an external test service, and any failure was logged
as a generic error.

Ethereal is now used only when `NODE_ENV=development`. In production and test, if
neither Admin > Email nor `SMTP_HOST` is configured, account email is not sent. The
server logs that delivery is not configured and how to configure it: an error in
production, a warning otherwise. Database settings still take precedence over
`SMTP_*` environment variables.

Every verification or password-reset send now returns `sent`, `not_configured` or
`failed`, and increments process-local counters (`getMailDeliveryStats`). A failed
send logs the mail kind, transport source and the SMTP `code`, `responseCode` and
command verb. Only known diagnostic codes/verbs and integer SMTP response codes
from 200 through 599 are retained. Upstream error text, response text and arbitrary
error fields are dropped, including database-read errors during transport fallback.
SMTP servers can echo recipients, credentials or message contents in any of these
fields. Callers' HTTP responses are
unchanged. Password reset still answers generically whether or not mail was delivered.

`SMTP_FROM` and Admin > Email's From Address accept one address (`sender@example.com`)
or a mailbox with a display name (`Werkyn <sender@example.com>` or
`"Werkyn, Team" <sender@example.com>`). Unicode display names and escaped quotes or
backslashes inside quoted display names are supported; addresses use the shared
email-address validator. Lists, groups, comments, control characters and line breaks
are rejected. The frontend uses this same contract and allows named mailboxes.

Empty account-mail sender settings retain their fallback order: stored From Address,
then `SMTP_FROM`, then `noreply@example.com`. Admin test mail uses the sender belonging
to the selected SMTP transport (database host first, otherwise environment), then
`noreply@<SMTP host>`. That generated sender must also be a valid mailbox: an IP or
single-label SMTP host requires an explicit From Address for an admin test.
Nonempty invalid legacy settings block delivery with `EADDRESS`; they never silently
select another sender. Correct and save them in Admin > Email. Every sender is
validated immediately before sending and passed to the mail library as a mailbox
object, so its address is not reinterpreted by the library's free-text parser.

Admin test failures return safe configuration guidance and bounded diagnostic
metadata instead of SMTP reply text. Authentication failures point to credentials;
sender/recipient rejections point to SMTP permissions; connection failures point to
host, port and TLS settings. Admin permissions and password masking are unchanged.

The sender follow-up's before-fix tests reproduced accepted ambiguous senders and
SMTP reply/private-field leaks using synthetic data, loopback SMTP and captured
production JSON logs. Earlier CRLF testing found no added headers or recipients;
the rejected input could change the envelope sender. This is not a claim of header
injection. Focused tests also cover actual admin HTTP responses, persisted settings,
permissions, password masking, named senders and fallback delivery.

`pnpm db:seed` creates an instance admin and other accounts with a published
password. It now refuses (exit status 1) when:

- `NODE_ENV=production`. This is checked before the script connects to the database.
- The database contains accounts or workspaces that the seed did not create. This
  also applies with `SEED_FORCE=true`, so force mode never deletes or mixes with real
  data. A seed address alone does not prove the seed created an account. It counts
  as seed data only while it still has the published seed password; a real account
  registered as `bob@test.com`, or a demo account whose password was changed, blocks
  force mode.

On an empty database it seeds. If the seed's own data is already present, it skips
(exit 0), and `SEED_FORCE=true` replaces that data. Force mode clears whole tables,
including anything the demo accounts created later. It runs only when every account
is a verified demo account, so that data belongs to accounts with a published
password.

Run `pnpm --filter @pm/backend test` for the mail and seed-decision tests.
`tests/integration/seed-guard.test.mjs` runs the real seed script against a database
that contains another account, or a real account at a seed address, and checks that
nothing is written or deleted.

Not included: delivery counters are not exposed through an API, and there is no
retry queue for failed mail. The public website guide (werkyn.com) still describes
the Ethereal fallback for an empty `SMTP_HOST` and needs a matching update. Password length/KDF policy and login-attempt or
enumeration cost are owned by the authentication work. Force mode still clears only the tables it
listed before. With data in tables it does not clear, such as files or chat, a
reseed can stop partway, but it never touches non-seed data.
