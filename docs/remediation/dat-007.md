# Recurrence calendar arithmetic

Monthly recurrences moved the month forward before clamping the day. Advancing a
day-31 schedule from January 31 overflowed through February into March, and from
March 31 through April into May, so the schedule only ran in 31-day months. Days
29 and 30 skipped February the same way. Initialization had the same defect: a
schedule created or edited on the 31st with an earlier configured day (for
example October 31 with day 15) got its first run a month late. Biweekly
schedules were initialized like weekly ones, from whatever week the schedule was
saved in, so their two-week phase depended on the save date instead of the start
date.

## Date policy

`startDate`, `endDate` and `nextRunDate` are calendar dates (`YYYY-MM-DD`) with no
time of day or zone. "Today" is the current UTC date in both the recurrence
service and the recurring-task scheduler, and all arithmetic uses UTC date
methods, so the host time zone has no effect. A schedule's occurrences are the
dates on or after `startDate` that match:

- DAILY: every day.
- WEEKLY: `dayOfWeek` every week (0 = Sunday).
- BIWEEKLY: the first `dayOfWeek` on or after `startDate`, then every 14 days.
  Changing the weekday keeps the same two-week cycles.
- MONTHLY: `dayOfMonth` every month, clamped to the month's last day. The
  configured day is reapplied each month, so day 31 runs on Jan 31, Feb 28 (Feb 29
  in leap years), Mar 31, Apr 30, and December rolls into January.

Creating a schedule, or editing its frequency or day, sets `nextRunDate` to the
first occurrence on or after the later of `startDate` and today. Editing only
`endDate` or `isActive` leaves `nextRunDate` alone. After the scheduler generates a
task it advances `nextRunDate` to the next occurrence. Catch-up is unchanged: each
scheduler tick generates at most one overdue occurrence per schedule.

## Existing rows

No data migration is included. Every `nextRunDate` the old code stored is a valid
occurrence of its schedule, and the scheduler continues correctly from it.
Occurrences that were already skipped are not backfilled. Two kinds of stored
rows may still differ from what the new code would compute:

- A MONTHLY row created or edited near the end of a month may hold a first run
  one month later than intended. If that date is still in the future, the month
  before it will be skipped once. To find these rows, compare an active MONTHLY
  row's `nextRunDate` with `calculateNextRunDate` evaluated today. Saving the
  schedule's `dayOfMonth` again recomputes it.
- A BIWEEKLY row created with a past start date or edited under the old code may
  be on the opposite week from its start date. The scheduler keeps the stored
  phase until the schedule's frequency or day is next edited. That edit re-anchors
  it to `startDate` and can move the next run by one week.

## Tests

`packages/backend/tests/recurrence-dates.test.mjs` checks both date functions
with a mocked UTC clock against an independent day-by-day calendar oracle. It
covers every configured day of month over four years, every BIWEEKLY start
weekday and target weekday, the named month-end, leap-year and December cases,
and several host time zones. `tests/integration/recurrence-calendar.test.mjs`
creates and edits schedules over HTTP against PostgreSQL. It then runs the real
scheduler on simulated days from January 2027 through March 2028, asserting one
generated task and broadcast per occurrence, no second run from a repeated tick,
and the stored `nextRunDate` after each step.

```bash
pnpm --dir packages/backend test
pnpm --filter @pm/shared build
TEST_DATABASE_URL="$AUDIT_DATABASE_URL" pnpm --filter @pm/backend test:integration
```

## Out of scope

The scheduler's durability problems remain separate work (DAT-010): a lost
occurrence after a failed task creation, duplicates across workers or crashes,
and the absence of a per-occurrence key. Without that key, editing a schedule's
frequency or day on a day when the new schedule has an occurrence can generate
that occurrence again, even if a task was already generated earlier that day.
This was already true before this change. The same work owns the catch-up policy
after a schedule is paused and then reactivated. Real-calendar date checks and
the day each frequency requires on edits are covered in
[contract-validation.md](contract-validation.md).
