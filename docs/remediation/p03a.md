# P03a: request timeouts and bounded uploads

`server.ts` set `requestTimeout` and `headersTimeout` to 0 after the server
started listening, to keep large uploads from being cut off. That disabled the
only protection Node gives against slow clients, for every route: a client
could open connections and send its headers, or a JSON body, one byte at a
time for as long as it liked. No socket idle timeout was set either, so a
client that stopped reading a download kept its connection, open file and
buffers forever.

The general upload routes had their own problems:

- **Drive uploads over `MAX_FILE_SIZE` were stored truncated.** The multipart
  parser stops a file at its size limit without an error, and the storage
  write used the same limit, so a 1,048,577-byte upload with a 1 MiB limit was
  answered 201 and stored as 1,048,576 bytes.
- **An aborted Drive upload left its partial file behind.** The parser
  destroys the file stream without an error when the client leaves, so the
  storage write never settled: the handler hung, the file stayed open, and
  the partial file (no database row, nothing queued for cleanup) was never
  removed.
- **A stalled upload was held forever**, with its partial file, on Drive and
  wiki uploads.
- **A Drive upload declared as an image was read back whole into memory** to
  make its thumbnail, whatever its size (`MAX_FILE_SIZE` is 10 GB by
  default). Wiki uploads (up to 25 MiB) were collected in memory and then
  copied into one buffer.

## Timeouts

`buildApp()` now configures the HTTP server (`src/plugins/request-limits.ts`),
and `server.ts` no longer overrides it.

| Setting | Value | Before | What it bounds |
|---|---|---|---|
| `headersTimeout` | 30 s | disabled | Request line and headers, from the first byte (or from the connection opening when nothing is sent). |
| `requestTimeout` | 120 s | disabled | The whole request, body included. Fastify recommends 120 s for servers that may run without a proxy. |
| Socket idle (`connectionTimeout`, `server.timeout`) | 120 s | none | No bytes moving in either direction on an active request or response. Node skips one expiry while a write is pending, so a client that stops reading a download is dropped after 120 to 240 s. |
| `keepAliveTimeout` | 72 s | 72 s (Fastify default) | An idle keep-alive connection. Now explicit; above the 60 s idle timeout of common load balancers. |
| `connectionsCheckingInterval` | 5 s | 30 s (Node default) | How often the header and request deadlines are checked, so a slow client is cut off within 5 s of its deadline instead of 30 s. |
| Upload idle | 60 s | none | A streamed upload (Drive, wiki, avatar) that receives no bytes, before or during its file. Same value as backup transfers. |

A client cut off by the header or request deadline gets Fastify's usual
`408 Client Timeout` response and its connection is closed.

### Routes that opt out

A route opts out in its `config.timeouts`, and each opt-out is replaced by a
bound of the route's own:

| Route | Request timeout | Socket idle | Own bound |
|---|---|---|---|
| `POST /api/workspaces/:wid/files/upload` (Drive) | exempt | applies | 60 s upload idle (408), `MAX_FILE_SIZE` (413) |
| `POST /api/uploads` (wiki media, avatars) | exempt | applies | 60 s upload idle (408), 25 MiB wiki / 5 MiB avatar (413) |
| Backup preview and restore | exempt | suspended until the response starts | 60 s transfer idle and 1,088 MiB cap (B03), admission limits |
| Backup export | applies (small JSON body) | suspended until the response starts | 10-minute export deadline, 60 s download idle (B03) |

- **Uploads** are exempt from the whole-request deadline only. Node reports
  the deadline as a client error; the server ignores it for a request that is
  still streaming on an exempt route (Node has already stopped tracking that
  request), and handles every other client error as Fastify does by default.
  Headers must still arrive within 30 s, and an upload that stops moving is
  answered 408 after 60 s.
- **Backup routes** may wait their turn in the exclusive section, or build an
  export for up to 10 minutes, without sending a byte, so the socket idle
  timeout is suspended from the start of the request until its response
  starts, and restored then: a client that stops reading a backup response
  is dropped like any other.
- **WebSockets** need no opt-out. Node stops tracking a connection's deadlines
  when it is upgraded, and the WebSocket library clears the socket timeout.
  Realtime keeps its own 5 s authentication and 30-minute idle limits.
- **Downloads, previews, thumbnails, public share downloads and static files**
  need no opt-out. A GET has no body, so its request is complete once its
  headers arrive; a slow but steady reader keeps bytes moving and is never
  idle. Only a client that stops reading is dropped.

## Uploads

Drive, wiki and avatar uploads go through `receiveUpload()`
(`src/utils/upload-stream.ts`), which waits for the file part (408 if the
client stalls first) and returns the file as a bounded stream:

- The parser's own limit is set one byte above the route's, so one byte over
  the limit reaches the meter, which refuses it at once with **413** instead
  of the parser ending the file silently. A file the parser cuts short anyway
  is refused too.
- No bytes for 60 s: **408**, and the connection is closed (the client is not
  sending).
- A disconnect, or a multipart body that is cut short or malformed: **400**
  (previously a 500, or a hang).

Drive files and wiki media are streamed to storage. `saveStream` now uses
`stream.pipeline`, so it applies backpressure, fails at once if its source
ends early or was already destroyed, and removes the partial file only after
it has been closed, so a file opened late cannot be left behind. Every
refused, stalled or aborted upload leaves no stored file, no `File` row and
nothing in the `BlobCleanup` queue. Avatars are still read into memory, up to
5 MiB, because the image type is detected from the whole file before
anything is written; they were already bounded by that limit.

Drive thumbnails are made only for images up to 32 MiB
(`THUMBNAIL_SOURCE_MAX_BYTES`). Larger images are stored without one, as
undecodable images already are, instead of being read whole into memory.

Storage containment (PR30) and upload admission (PR32) are unchanged: the
same path checks, membership and role checks run before any byte is read.

Every upload route was checked for truncation:

| Route | Over its limit, before | Now |
|---|---|---|
| Drive files | 201, stored truncated to the limit | 413, nothing stored |
| Wiki media, avatars (`/api/uploads`) | 413 (buffer limit and truncation check) | 413, streamed |
| Backup preview and restore | 413 (B03, PR109) | unchanged |
| Task attachments, chat | no upload route: attachments link Drive files, chat has no file upload | n/a |

## Backup export admission

`backup-transport.test.mjs` failed intermittently on main (3 of 60 runs of
the test on its own here; about one in nine full runs was reported): right
after an export's response ended, the test
found the export's admission still held. The controller released it when the
download stream closed, and that happens only after the file read that finds
the end of the archive, which can finish after the client already has every
byte. The admission is now released by `onLastByte()` as the archive's last
chunk is handed to the response, in the same synchronous step, so no client
can have the whole file while the admission is still held. Until then it is
held, as PR111 requires; a download that is abandoned or fails first still
releases it when its stream closes.

## Measurements

Peak RSS of a fresh server process (256 MiB heap, default 10 GiB
`MAX_FILE_SIZE`), one process per scenario
(`tests/integration/upload-memory.test.mjs`). About 40 MiB of each figure is
the first request's warm-up.

| Scenario | Before | After |
|---|---|---|
| Drive upload, 256 MiB, `application/octet-stream` | +39 MiB | +37 MiB |
| Drive upload, 256 MiB, declared `image/png` | +259 MiB | +41 MiB |
| 4 concurrent wiki uploads of 24 MiB | +121 MiB | +41 MiB |

Timeouts, measured over TCP with short test limits (headers 0.8 s, request
1.5 s, socket idle 1.2 s, upload idle 0.8 s, checked every 0.1 s;
`tests/integration/request-limits.test.mjs`):

"Before" is main. In production, `server.ts` disabled both deadlines there;
the test builds the app without `server.ts`, so Node's default 60 s header
deadline still applied on main, and those connections were still open when
the test gave up.

| Client | Before | After |
|---|---|---|
| Opens a connection and sends nothing | kept open | closed after 0.85 s |
| Sends its headers one byte per 100 ms | kept open | 408 after 0.85 s |
| Sends a JSON body one byte per 100 ms | kept open | 408 after 1.6 s |
| Stops reading a 32 MiB download | kept open | dropped after 2.4 s |
| Stalls halfway through a Drive or wiki upload | kept open, partial file kept | 408 after 0.8 s, nothing left |
| Disconnects halfway through a Drive upload | 512 KiB partial file left | nothing left |
| Downloads 4 MiB at 1 MiB/s (4.2 s) | completes | completes |
| Uploads 768 KiB to Drive and to the wiki over 3.8 s each | completes | completes |
| Uploads a backup slowly, then exports after waiting 3.9 s for its turn | completes | completes |
| Holds an authenticated WebSocket for 3.5 s, then pings | answered | answered |

Without each route's opt-out, the matching slow-but-steady case fails: Drive
and wiki uploads and backup previews get a 408 at the request timeout, and a
waiting export is dropped at the idle timeout.

  has the last byte, once, and never for an abandoned stream.

## Remaining limits

- The limits are per process and not configurable by environment variable.
- A client that keeps sending or reading a few bytes a minute is never idle,
  so it is only bounded by the request timeout (non-upload routes) or not at
  all (uploads and downloads); limiting transfer rates belongs in a reverse
  proxy.
- After a 413, the rest of an oversized body is not read; the connection is
  closed by the socket idle timeout if the client keeps it open.
- Avatars are buffered up to 5 MiB for type detection, and thumbnail decoding
  is still bounded only by sharp's pixel limit.
