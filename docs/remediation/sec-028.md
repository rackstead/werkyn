# Backup restore parse budget

Backup preview and restore parsed `backup.json` with `JSON.parse` and then
validated it against `BackupFileSchema`. Zod reports a separate issue for every
invalid element. A file such as `{"metadata":{},"projects":[{},{},…]}` costs
about 22 bytes of heap per byte to parse, and about 100 bytes per byte once
every element has its issue. An empty task reports five issues. Text like this
deflates about 1,000:1, so a 2.5 KB ZIP could abort a server process with a
256 MiB heap. On a default heap a ZIP of a few tens of KB was enough. The
crash takes the server down for every workspace. The same happened with a
plain `.json` upload, which only needs the full file uploaded. The routes
require workspace ADMIN, but any signed-in user can create a workspace and is
its ADMIN. The SEC-025 archive budget did not help here: `backup.json` passed
its 512 MiB per-entry limit easily.

## Limits

`backup-json.ts` now measures `backup.json` before `JSON.parse` sees it. The
measurement is one pass over the bytes, allocates nothing, and refuses the file
if it exceeds any of these limits:

| Limit | Value | Largest measured export |
|---|---|---|
| UTF-8 bytes | 24 MiB | 17,427,502 bytes (16.6 MiB) |
| Tokens: `{`, `[`, `,` and `:` outside strings, plus one | 1,100,000 | 787,482 |
| Objects: `{` outside strings | 150,000 | 51,547 |
| Nesting of objects and arrays | 128 | 10 (12 in the test export) |

Heap use depends on how many values and objects a file holds, not only on its
size:

- **Tokens.** The token count is an upper bound on the values and member names
  `JSON.parse` can create. It exceeds their number by exactly one for each
  empty object or array. Exports average 22 to 24 bytes per token, so 24 MiB
  of export holds about 1.1 million tokens. The densest measured export
  reaches the token limit at 23.2 MiB, so in practice the byte limit and the
  token limit allow about the same amount of data.
- **Objects.** A validated object is the most expensive value. Exports average
  about 340 bytes per object. A file of minimal objects, such as
  `{"project":{"name":""}}`, would otherwise fit hundreds of thousands of them
  into the token limit.
- **Bytes.** Text with any character above U+00FF is stored with two bytes per
  character, both as the source text and as the parsed strings.

The measured export is the PR 88 workspace plus a busy channel, built through
the real routes and exported over HTTP:

- 4 projects with 6,000 tasks, 12,000 subtasks and 6,000 comments;
- one channel with 20,000 messages;
- 2 wiki spaces with 500 pages and 1,512 embedded images, using SEC-009 upload
  names.

A server with a 256 MiB heap previewed it and then restored it. All 1,512
restored images matched their source bytes, and all 6,000 tasks and 20,000
messages came back. Larger workspaces must be exported in parts. How close the
two measured exports come to each limit:

| Export | Bytes | Tokens | Objects | Depth |
|---|---|---|---|---|
| 6,000 tasks, 20,000 messages, 1,512 images | 69% (1.44×) | 72% (1.40×) | 34% (2.9×) | 8% (12.8×) |
| 3,000 tasks, 3,000 messages, 600 images (integration test) | 26% (3.9×) | 26% (3.8×) | 14% (7.4×) | 9% (10.7×) |

The depth limit also matches the database layer. Prisma's query engine stores
at most 123 levels of nesting in one JSON column. That puts a wiki page's
content at depth 128 in `backup.json`. A deeper file could not be restored, and
it used to fail with a 500 halfway through the restore transaction.

Validation now stops at the fifth problem. The response still lists up to five
problems, as before. Zod's message for an invalid enum value quoted the
uploaded value, so the response could repeat up to five strings from the
upload. It now names only the allowed values.

## What this bounds

The limits are sized so the most expensive file they accept parses and
validates within a 224 MiB heap, including the app. That leaves at least
32 MiB of a 256 MiB heap for other work. A 256 MiB heap is Node's default with
512 MiB of memory. The worst cases fill the object or token limit with minimal
valid elements, and spend the remaining bytes on one string with a character
above U+00FF.

The most expensive shape is one array of distinct short strings in a field
that validation checks element by element, such as a task's `assignees` or
`labels`. Zod holds a result for every element until it finishes the array.
The same strings spread over many tasks need about 50 MiB less. With the first
token limit of 1,500,000, one such array needed a 256 MiB heap and aborted at
240 MiB. The token limit is now 1,100,000.

Measured floors are the smallest `--max-old-space-size`, in steps of 16 MiB
from 160 MiB, at which a fresh server process answered the preview. The
previous column is for 1,500,000 tokens, measured in steps of 32 MiB except
the two string arrays and the split assignees.

| File at the limits | Heap now | Previously |
|---|---|---|
| 1,100,000 distinct strings in one task's `assignees`, padded to 24 MiB with a two-byte string | 224 MiB (aborts at 216) | 256 MiB (aborts at 240) |
| the same in one task's `labels` | 224 MiB (aborts at 216) | 256 MiB (aborts at 240) |
| the same strings in tasks of 10,000 assignees each | 176 MiB | 192 MiB or less |
| about 100,000 minimal tasks, the same padding | 176 MiB | 192 MiB |
| 74,998 minimal projects, the same padding | 176 MiB | 192 MiB |
| about 122,000 pages in one parent chain, the same padding | 160 MiB or less | 192 MiB |
| about 122,000 messages, the same padding | 160 MiB or less | 192 MiB |
| 549,970 distinct member names in one object, the same padding | 160 MiB or less | 192 MiB |
| about 150,000 user references (preview lists one mapping each), the same padding | 160 MiB or less | 160 MiB |
| about 150,000 `{}` and 400,000 `[]` in a page's content, the same padding | 160 MiB or less | 160 MiB |
| channels, spaces or subtasks at the object or token limit, the same padding | 160 MiB or less | 160 MiB |
| the most expensive invalid files (150,000 `{}` plus `[]` up to the token limit) | 160 MiB or less, answered 400 | 128 MiB |

Each string-array file survived at 224 MiB in all six preview runs and aborted
at 216 MiB in all four runs that tried it. Their restore behaves the same as
their preview: 224 MiB passes and 208 aborts.

The integration test previews eight of these files one after another in one
256 MiB server process: tasks, projects, pages, user references, member names,
content objects, `assignees` and `labels`. In the test process, the
user-reference preview's 15 MB response stayed alive until the next request,
so a sequence needs more heap than its most expensive file. Node's default heap
is about half of the memory it sees, up to 4 GiB. It was 1,747 MiB on the
3.3 GiB test host.

For production, give the server an old-space heap of at least 384 MiB. That
means 768 MiB of memory with Node's default, or `--max-old-space-size=384`. A
256 MiB heap survives any single upload the limits accept, with at least
32 MiB to spare for everything else the server holds at that moment.

Parsing and validating at the limits blocks the event loop for at most about
0.4 s. The measured export takes about 0.15 s.

## Where the limits apply

- **ZIP uploads.** The declared size of `backup.json` is checked against the
  byte limit before the entry is inflated. Over the limit, the response is the
  SEC-025 message "the archive exceeds the restore limits", and the log reason
  is `json-size`.
- **Plain `.json` uploads, and `backup.json` after inflation.** Both go through
  the same `parseBackupJson`. Preview and restore share it. A refusal is a 400
  with the fixed message "Invalid backup file: the backup data exceeds the
  restore limits". The server logs one of the reason codes `json-size`,
  `json-tokens`, `json-objects` or `json-depth` at warn level. It never logs
  file content.
- **Export.** Export measures its own `backup.json` with the same limits after
  building it. An export that restore would refuse gets the SEC-025 400, which
  asks the admin to select fewer projects, channels or wiki spaces. So every
  export Werkyn produces can still be restored.

## Behavior changes

- A `backup.json` over 24 MiB, 1,100,000 tokens, 150,000 objects or depth 128
  is refused. Before, files up to the 512 MiB archive entry limit were parsed
  if the server had enough memory.
- Exports over the same limits are refused. Large workspaces must be exported
  in parts, for example one busy channel at a time. A restore adds to the
  workspace, so the parts can be restored one after another.
- Content nested deeper than the database accepts gets a 400 before any write.
  Before, it failed with a 500 during the restore.
- Validation errors list at most the first five problems, as before. Enum
  errors no longer quote the uploaded value.

## Tests

`tests/backup-json.test.mjs` runs in `pnpm test`. It covers:

- token and object counting, checked against a census of the parsed values;
- strings that contain structural characters, escapes and multi-byte UTF-8;
- each limit at its boundary, with its reason code;
- validation stopping at five problems;
- enum messages that do not quote the upload;
- the ZIP check on declared size before inflation;
- the export budget at and one below each limit.

It also parses the review's 4 MiB reproduction and the most expensive invalid
files the limits admit in a child process with a 128 MiB heap, where all of
them get a 400. The validation the routes ran before aborts that child.

`tests/integration/backup-json-budget.test.mjs` starts the real app in child
processes with a 1 GiB data segment, and uploads to preview and restore:

- **Hostile uploads, 256 MiB heap.** The review's 4 MiB and 24 MiB files as
  ZIPs (4,235 and 24,623 bytes), the 24 MiB file as plain `.json`, 750,000
  empty tasks as a 2,466-byte ZIP and as plain `.json`, and invalid channel
  types. On the previous code each of the five amplifying uploads aborted the
  process (SIGABRT, JavaScript heap out of memory), and the enum error quoted
  the upload. Now each gets a 400, nothing is written, and the same process
  then restores a legitimate backup.
- **Each limit, 256 MiB heap.** Files exactly at the byte, token, object and
  depth limits are accepted. A file at the depth limit restores and stores its
  content. One byte, token, object or level more gets a 400. So do the most
  expensive invalid files the limits admit.
- **The worst accepted files, 256 MiB heap.** Eight of the most expensive valid
  files the limits admit preview one after another in the same process,
  including one `assignees` and one `labels` array of distinct strings at the
  token limit.
- **A realistic export, 256 MiB heap.** The test builds and exports a workspace
  with 3,000 tasks, 6,000 subtasks, 3,000 comments, 3,000 messages, 300 pages
  and 600 images, using SEC-009 upload names, over HTTP. It previews and
  restores it, then compares every task, message, page and image with the
  source.

`tests/integration/backup-zip-restore.test.mjs` checks that an export whose
`backup.json` is exactly at reduced limits succeeds. One byte, token, object or
level less refuses the export.

## Remaining limits

Update: concurrent backup requests are now limited and take turns parsing, and
uploads are staged on disk; see `b03-backup-transport.md`.

The limits bound one request. Each restore in progress keeps its parsed
backup until its transaction ends, and there is still no limit on concurrent
backup requests (B03/P03). A server whose heap is below 256 MiB, or that holds
much more live data than the test process, has less margin than measured here. The upload is still buffered whole, and export still
builds the whole `backup.json` before measuring it. Parsing is synchronous, as
before. The public backup documentation does not mention these limits yet.
