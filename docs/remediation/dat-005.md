# Referenced-resource integrity (DAT-005)

Task data references rows that belong to a project (status columns, labels,
custom fields, other tasks) or to a workspace (members). The database only has
independent foreign keys, so it accepts a reference to any existing row, including
one in another project or tenant. The application must resolve each supplied ID
inside the authorized project before writing.

## Write paths

Every writer below resolves all referenced IDs before its first write and rejects
the whole request if any one is missing, empty, belongs elsewhere, or is repeated. Missing
and foreign IDs get the same response, so the error does not reveal whether an ID
exists in another project. A rejected request writes no rows, activity, events or
notifications.

| Writer | References validated |
| --- | --- |
| Task create | status in the project; labels in the project; assignees with project access; no duplicates |
| Task update / move | status in the task's project (already enforced; kept) |
| Bulk update | task IDs unique and in the project; status; labels; assignees; all before any write |
| Add assignee | user has project access (previously any workspace member) |
| Add label / dependency, custom-field value | same project (already enforced; kept) |
| Duplicate task | copies only the status, labels, assignees and subtask assignees still valid in the project; an invalid status falls back to the first column |
| Subtask create / update | assignee has project access |
| Template create / update | status, labels and assignees as for task create |
| Template instantiation | explicit `statusId` / `assigneeIds` overrides are validated and rejected; values stored in the template are copied only while still valid (columns get deleted and members leave) |
| Time entry create / update | a task's project must equal the entry's project; changing either reference re-checks it |
| Rate set | user is a current member of the workspace |
| Status delete | moves only the project's own tasks; refuses (409) while a task from another project still points at the column |
| Chat DM / member add | current workspace members (already enforced by the chat authorization fix) |

"Project access" uses the same rule as project reads: a current workspace member
who is a workspace ADMIN or a member of the project. Rejections return 400 except
where the route already returned 404 (labels, custom fields, rates) or 409 (status
delete).

Template list, detail, create and update responses likewise carry only the stored
status, labels and assignees still valid in the project. The task dialog and the
template editor resubmit what they were shown, so editing or instantiating a
template never sends a stale ID that the writers now reject.

## Existing rows

Rows written before this change may still be inconsistent. Until they are repaired,
task responses (`GET /tasks/:id`, project task lists, my tasks, search, update,
move warnings) drop labels, custom-field values and dependencies whose target lives
in another project, and replace a foreign status column with a placeholder named
"Unavailable status" that keeps only the ID already visible as `statusId`.
Dependency counts ignore cross-project links. Removing a cross-project dependency
does not copy the other task's title into the activity log.

## Detecting and repairing legacy data

`packages/backend/src/scripts/reference-integrity-report.ts` lists every broken
relationship. It runs all queries in a single `READ ONLY` repeatable-read
transaction, so it cannot change data, and prints IDs only (no names, titles or
values). It is not run automatically.

```bash
# from packages/backend, against the database to inspect
DATABASE_URL=postgresql://... npx tsx src/scripts/reference-integrity-report.ts --limit=100
# or, in the production image
DATABASE_URL=postgresql://... node packages/backend/dist/scripts/reference-integrity-report.js --json
```

Exit status is 0 when clean, 2 when issues were found and 1 on error. Each issue
names the proposed repair:

| Check | Proposed repair |
| --- | --- |
| `task_status_project` | move the task to the lowest-position column of its own project |
| `task_label_project` | delete the task-label row |
| `custom_field_value_project` | delete the value row |
| `task_dependency_project` | delete the dependency row (also self-dependencies) |
| `task_assignee_access` | `not_workspace_member`: delete; `no_project_access`: add to the project or delete |
| `subtask_assignee_access` | clear the subtask assignee, or add the user to the project |
| `time_entry_workspace` | clear the foreign task/project reference, keeping the hours |
| `time_entry_task_project` | set the entry's project to the task's project |
| `user_rate_workspace` | delete when the user never logged time in the workspace; keep for a former member's historical reports |
| `task_template_reference` | rewrite the stored lists to their valid subset (instantiation already ignores the rest) |
| `recurring_template_project` | delete or recreate the recurring configuration |
| `chat_member_workspace` | delete the channel membership |

Recommended order: take a backup, run the report, review the samples with the
workspace owners (assignee and rate repairs involve a policy choice), apply the
repairs in one transaction per check, and rerun the report until every check is 0.
Only then add structural constraints (for example composite foreign keys such as
`Task(projectId, statusId) -> StatusColumn(projectId, id)`); adding them first
would fail the migration on any remaining row. Constraints are intentionally not
part of this change.

## Tests

`packages/backend/tests/integration/referenced-resource-integrity.test.mjs` uses
real HTTP requests and PostgreSQL. It covers every combination of a sibling-project,
other-tenant, missing and duplicated status, label, assignee, task, dependency,
custom-field and subtask reference on task create, bulk update, single-task
writers, subtasks, templates and instantiation, time entries and rates, with
valid equivalents. Each rejection is checked against a snapshot of every affected
table plus captured broadcasts. It also seeds legacy cross-project rows to check
that reads do not expose them, that duplication does not copy them, that status
deletion refuses to relink them, and that the report finds them without writing.

```bash
pnpm --filter @pm/shared build
TEST_DATABASE_URL="$AUDIT_DATABASE_URL" pnpm --filter @pm/backend test:integration
```
