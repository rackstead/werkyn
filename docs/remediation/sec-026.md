# Single-use password-reset and email-verification tokens

`resetPassword` checked the token's `usedAt` and expiry, hashed the new password
and only then opened the transaction that changed the password, set `usedAt` and
revoked the account's refresh families. The update of `usedAt` was
unconditional, so every request that had passed the check before the first one
committed also succeeded: two (or more) concurrent submissions of one reset link
each returned 200, the last one decided the password, and each revoked the
sessions again, including a session the user had just opened with the password
set by the first reset.

Email verification had the same shape: the token was checked, the account was
marked verified and the token was deleted in three separate statements. A second
concurrent use (or one whose token a resend replaced meanwhile) wrote the
account before its delete failed, and was then answered with the generic
`Resource not found` instead of the invalid-token error. Because email addresses
cannot be changed and marking an account verified is idempotent, this did not
grant anything beyond the first use, but the outcome was not atomic.

## Behavior

- **Password reset.** The request still checks the token before hashing the
  password, so an unknown, used or expired token is refused cheaply. The
  transaction then claims the token with one conditional statement before it
  touches anything else:
  `UPDATE "PasswordResetToken" SET "usedAt" = now WHERE id = ? AND "usedAt" IS NULL AND "expiresAt" > now`.
  Under READ COMMITTED, a request that reaches the row while another
  transaction holds it waits and then re-evaluates the condition against the
  committed row, so exactly one request claims the token. Every other request
  updates nothing, re-reads the token and gets the same error as a later reuse:
  `410 Reset token has already been used`, `410 Reset token has expired`, or
  `404 Invalid reset token` if a new forgot-password request replaced it. It
  changes neither the password nor any session. The winner changes the
  password and revokes every refresh family in the same transaction, as
  before. If the winner rolls back, the token is unused again and a waiting
  request can claim it.
- **Email verification.** The transaction claims the token by deleting it with
  `DELETE ... WHERE id = ? AND "expiresAt" > now`; only the request whose delete
  removed the row marks the account verified. The others get
  `404 Invalid verification token` (or `410` if it expired) and write nothing.
  A link for an account that is already verified still succeeds once, as
  before.
- **Expiry during a lock wait.** A claim can wait for another transaction that
  holds the token row (at most the 8 s `lock_timeout` from SEC-011). A token
  that expired during that wait is refused after the claim and the transaction
  rolls back, so the token stays unused.
- **Busy links.** A reset or verification whose lock wait reaches the
  `lock_timeout`, or whose transaction exceeds its budget, is rolled back,
  including its claim, and answered
  `503 This link is busy. Try again in a moment.` The token stays usable and
  the same link can be submitted again. The detection is the one refresh
  rotation uses (`isBusy`: 55P03 or P2028).

## Lock order

Both transactions start with `limitLockWaits` and use the same budget as the
refresh-family transactions. The reset locks the token row, then the user row
(the password update), then the families in id order, which keeps the
user-before-family order documented in `sec-011.md`. Nothing locks a reset or
verification token while holding its user row: forgot-password, resend and the
daily cleanup delete tokens in single statements outside any transaction, and
creating a token only takes the `KEY SHARE` foreign-key lock on the user, which
is compatible with the reset's `NO KEY UPDATE`.

## Validation

`packages/backend/tests/integration/single-use-auth-tokens.test.mjs` runs the
application over HTTP against PostgreSQL with a separate actor pool and a
bounded two-connection control pool. Barriers are real row locks on the token,
observed through `pg_stat_activity`: any implementation must write that row to
consume the token, so all concurrent requests have read it as usable before any
of them can consume it. The tests cover:

- four concurrent resets with one token: one 200, three 410, the stored password
  is the winner's, both pre-existing sessions are revoked, and the winner's
  password signs in afterwards;
- a reset that passed its token check and was delayed until after another reset
  used the token and the user signed in again: 410, password and new session
  kept;
- three unsynchronized bursts of six resets: one 200 each;
- a token that expires while its reset waits on the token row: 410, nothing
  changed;
- used, expired and unknown tokens, and a single legitimate reset through
  forgot-password (all sessions revoked, old password refused, token reuse
  refused);
- a reset blocked on the token row, and one blocked on the user row after its
  claim, past a shortened lock timeout: 503 while the lock is still held,
  nothing changed, and the retry succeeds;
- four concurrent verifications with one token, a verification whose token is
  removed while it waits, one whose token expires while it waits, one blocked
  past the lock timeout (503, retry succeeds), and single-use, reuse, expiry,
  unknown-token and already-verified cases.

On the previous code 10 of the 13 fail, including four 200s from four
concurrent resets and six from six; the three busy cases answered 500.

```sh
TEST_DATABASE_URL=<disposable-url> pnpm --filter @pm/backend exec node --import tsx --test --test-concurrency=1 tests/integration/single-use-auth-tokens.test.mjs tests/integration/refresh-family-atomicity.test.mjs
```

## Out of scope

- Reset and verification tokens are still stored in plaintext rather than as
  hashes.
- A successful reset does not invalidate other unused reset tokens of the same
  account; forgot-password already deletes them before issuing a new one, but
  two simultaneous forgot-password requests can leave two valid tokens.
- Workspace invitations are covered by SEC-007 and OIDC state by its own
  conditional delete; neither is changed here.
