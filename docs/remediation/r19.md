# R19: thumbnail decoder allowlist and transform admission

Drive thumbnails are the backend's only native image decoding. Avatars and
wiki media are sniffed with `file-type` and stored or served as bytes
(`private-upload-media.md`); chat and task attachments are never decoded. The
Drive path is in `packages/backend/src/modules/files/`:
- `thumbnails.ts`: what the server process does, which is admission and
  the deadline;
- `thumbnail-workers.ts` and `thumbnail-worker.ts`: the memory-limited
  decoder processes;
- `thumbnail-decode.ts`: the only module that imports sharp, loaded only
  by those processes;
- `thumbnail-checks.ts`: the pure JavaScript checks and the estimate.

Before this change, PR144's signature check sent JPEG, PNG, GIF, WebP, TIFF
and every HEIF brand to sharp with its default options. The decoder chosen by
libvips could still differ from the format checked, there was no estimate of
decode memory beyond sharp's 268-megapixel limit, and every upload decoded at
once. Measured on main (`28fd599`), one upload of each of these, all under
the 32 MiB source cap:

| Input | Bytes | Peak RSS growth | Time |
|---|---:|---:|---:|
| AVIF, 10000 x 10000 | 2,153 | 1,752 MiB | 1.3 s |
| AVIF, 6000 x 6000 | 1,017 | 630 MiB | 0.5 s |
| Interlaced RGBA PNG, 16000 x 16000 | 995,382 | 1,067 MiB | 2.1 s |
| Interlaced RGBA PNG, 10000 x 10000 | 388,870 | 438 MiB | 0.8 s |
| GIF, 10000 x 10000 | 67,726 | 434 MiB | 0.3 s |
| Progressive JPEG, 10000 x 10000 | 587,079 | 295 MiB | 0.2 s |

An AVIF with a `clap` crop, a grid or an overlay reports a smaller size than
it decodes. The 10000 x 10000 AVIF above, cropped or composed to 64 x 64,
still needs 1,740 MiB. A 144-byte animated WebP with a 16383 x 16383 canvas
needs 1,160 MiB. The first version of this change estimated from the
reported size and charged WebP 1.5 bytes per pixel, so it admitted all of
these. The independent review found them, and they are now charged for
what is decoded (see below).

sharp runs each transform on a libuv worker thread, so four uploads like the
first could decode at once and need about 7 GiB. Those four threads are also
the ones file I/O, password hashing and compression use; in the concurrent
runs below, a 1 ms `fs.stat` waited up to 1.1 s. In the Alpine image (musl)
sharp also gave each transform one libvips thread per CPU.

## Decoder worker processes

Five reviews of the checks below each closed one native path and found
the next: decoder sizes, AVIF item structure, `iloc` repetition, PNG text
inflation, then metadata copies that were never charged. The checks mirror
how libvips, libheif, libpng, libjpeg and libwebp treat each container
feature, and each sharp upgrade can change that. In the server process,
one input the checks missed could take the whole backend down: a 2 KiB AVIF
and a 477 KB PNG each OOM-killed a 1 GiB container.

So the decoding now runs in separate processes with a hard memory limit,
and a decode that needs more ends only its worker. The checks stay: they
refuse most bad files in milliseconds, before any native code, and keep
CPU time bounded, but they are no longer what keeps the server alive.

- **A pool of long-lived workers.** There is one worker per transform turn
  (`maxActive`, 2 on four or more CPUs), started with the server.
  `thumbnail-workers.ts` runs the pool and `thumbnail-worker.ts` is the
  process. The server checks the first 64 bytes, takes a turn and sends
  the worker the stored file's path. The worker then:
  - opens the file without blocking and reads it only if it is a regular
    file of at most 32 MiB;
  - runs every check in `thumbnail-decode.ts` and `thumbnail-checks.ts`;
  - decodes, and answers with the WebP or the reason there is none.

  The server never loads sharp or libvips.

  The worker answers over a socket at its fd 3, in length-prefixed frames
  (`thumbnail-protocol.ts`), not over Node's IPC channel. Node's IPC
  channel parses a message of any size before the receiver sees it. The
  server reads both declared lengths before it buffers anything:
  - a header must be at most 64 KiB, and a thumbnail at most 16 MiB;
  - a worker that declares more, sends a header that is not JSON or
    answers unasked is killed, and its decode reported as `crashed`;
  - a thumbnail must then be a WebP, and only known outcomes and bounded
    details are kept.

  So a worker taken over through a decoder bug can make the server hold
  at most one 16 MiB frame, and can store only a WebP as the thumbnail.
- **The limit: RLIMIT_DATA of 512 MiB per worker.** This counts the
  worker's heap, anonymous mappings and thread stacks (writable private
  memory), but not the address space V8 reserves. Node cannot set it for
  a child, so on Linux each worker starts as
  `/bin/sh -c 'ulimit -d 524288 || exit 125; shift; exec node …'`, which
  sets the soft and hard limits without privilege. An allocation past the
  limit fails. libheif, libvips and libwebp report that as a decode error,
  and glib aborts the worker. Either way only that thumbnail is lost.
- **Small workers.** Each worker runs with:
  - one libuv thread (`UV_THREADPOOL_SIZE=1`) and one V8 helper thread
    (`--v8-pool-size=1`), since each thread's stack counts against the
    limit;
  - on glibc only (musl ignores them), two malloc arenas, and every block
    of 128 KiB or more mapped and returned when freed.

  A ready worker uses about 41 MiB of the 512 against 90 MiB with Node's
  defaults. Without the malloc settings, glibc kept 250–330 MiB after a
  few near-budget decodes, and 30 of 48 admitted files then failed in
  the same worker. With them, 96 of 96 succeeded in one worker, and it
  settled at 147–160 MiB. A worker still over 192 MiB after a decode is
  replaced anyway.
- **The OOM killer's first choice.** Each worker raises its own
  `oom_score_adj` to 1000, which needs no privilege. If the container
  still runs out of memory, for example two workers near their limits on
  a small host, the kernel kills a worker, not the server. Docker kills
  only the chosen process (`memory.oom.group` is 0).
- **Defence in depth, not a sandbox.** A worker gets only these variables:
  `PATH`, `TMPDIR`, `TZ`, `LANG`, `LC_ALL`, `NODE_ENV` and the settings
  above. It does not get the server's environment (database URL, JWT and
  cookie secrets), so they never leak into a worker by accident. The
  workers still run as the server's user, though. Code that takes over a
  worker through a decoder bug could read `/proc/<server>/environ` and
  the storage directory, as it could in the server process before this
  change. Isolating that would need a separate user or a seccomp or
  Landlock profile, which this change does not add.
- **Crashes.** When a worker exits during a decode (out of memory, a
  signal or any crash), the upload still returns 201 without a thumbnail
  and the turn is released. The outcome is `crashed`, logged as a warning
  with the exit status or signal. The worker is replaced at once: the
  crash is the input's doing, and the worker proved it starts.
- **Back-off, per workspace.** A crash also holds back the next
  thumbnails of the workspace whose upload caused it: 1 s after the
  first, doubling up to 60 s, until one of its thumbnails succeeds.
  Uploads meanwhile are stored at once without one (`busy`):
  - the wait is checked before an upload queues for a turn, and again once
    it gets one, so an upload already waiting when another crashed does
    not decode;
  - a success clears the wait only if no other upload from the workspace
    crashed after that decode started.

  A restart costs about as much CPU as decoding an ordinary photo, so one
  workspace cannot turn a stream of crashing uploads into a stream of
  restarts. Other workspaces are not held back. At most 10,000
  workspaces are remembered, and the longest-unseen is forgotten first.
- **Back-off, per worker, for start failures.** A worker counts a failure
  when it:
  - exits before it reports ready;
  - does not report ready within 30 s, and is killed (Node can hang at
    start under too small a limit);
  - exits while idle, for example when the kernel picks it under memory
    pressure.

  The second failure in a row waits 0.5 s before the restart, and each
  further one doubles that, up to 30 s. A completed decode, or 30 s alive,
  clears the count. Meanwhile, an upload that finds every free worker
  waiting is stored without a thumbnail at once. So a broken environment
  causes neither a restart loop nor waiting uploads.
- **The deadline kills.** An upload still waits at most 12 s after
  admission, as before. Its worker is then killed (`SIGKILL`) and
  replaced. The turn returns once the killed worker has exited, so a turn
  always covers a worker's memory, and a slow decode no longer holds a
  turn beyond the deadline.
- **Shutdown.** Stopping the thumbnail workers is the first shutdown step
  (500 ms):
  - the pool closes each worker's channel, on which the worker exits;
  - any worker still running after 250 ms is killed;
  - an upload still waiting for a worker is stored without a thumbnail.

  A worker also exits by itself when the server dies, since its channel
  closes. Node reaps its own children, so none is left a zombie, even as
  PID 1 in the container.
- **Without a limit.** On another platform, or with no `/bin/sh`, workers
  start directly without a limit and the server logs a warning. If the
  server already runs under a lower hard data limit, `ulimit` cannot
  raise it: the wrapper exits 125, and the pool starts workers directly,
  where they inherit the lower limit, and says so. The pool also logs the
  limit each worker reports, and the score above still applies on Linux.
  In those cases a crash still ends only the worker, and the checks are
  again the only memory bound, as before this change.
- **For tests only,** `WERKYN_TEST_THUMBNAIL_MEMORY_CHECKS=off` makes the
  workers skip the container checks and the estimate, so that tests and
  the container proof can show the limit holding on its own. It is
  ignored unless `NODE_ENV` is `test`.

What was tried to set the limit, measured on the glibc host (Node 22.16)
and in the production image (Node 22.23.4, Alpine 3.24, uid 10001):

| Mechanism | glibc host | Production image |
|---|---|---|
| RLIMIT_DATA through `sh -c 'ulimit -d …; exec node …'` | works (dash) | works (busybox ash sets soft and hard) |
| `prlimit --data` | works | not installed (busybox has no `prlimit`) |
| A cgroup v2 child group with `memory.max` | – | `/sys/fs/cgroup` is mounted read-only without extra privileges |
| RLIMIT_AS | sharp cannot even load under 1 GiB: V8 and libvips reserve more address space than that | same |
| `--max-old-space-size` | bounds only the JavaScript heap: the 2 KiB AVIF still reached 1.8 GiB | same |

So `ulimit -d` in a shell is the mechanism. It is reliable in the shipped
container and needs no capability, `--privileged` or extra package.

## Which bytes are decoded

A thumbnail is attempted only when the declared type is `image/*`, not SVG,
and the stored file is at most 32 MiB, as before. The declared type and file
name only decide whether to try. The bytes decide what is decoded, and five
checks must agree:

1. **Signature** (`thumbnailFormat`). This is checked on the file's first 64
   bytes before the upload waits for a transform turn, so other content
   never takes a queue place. It is checked again on the whole file once
   admitted. Fixed bytes at fixed offsets:

   | Format | Signature | `file-type` result | libvips format | Loader |
   |---|---|---|---|---|
   | JPEG | `FF D8 FF` | `image/jpeg` | `jpeg` | `VipsForeignLoadJpegBuffer` |
   | PNG, APNG | PNG signature, then a 13-byte `IHDR` chunk | `image/png`, `image/apng` | `png` | `VipsForeignLoadPngBuffer` |
   | WebP | `RIFF` .... `WEBP` + `VP8 `/`VP8L`/`VP8X` | `image/webp` | `webp` | `VipsForeignLoadWebpBuffer` |
   | GIF | `GIF87a` or `GIF89a` | `image/gif` | `gif` | `VipsForeignLoadNsgifBuffer` |
   | AVIF | `ftyp` box with major brand `avif`, ordinary 32-bit size that fits the file | `image/avif` | `heif` | `VipsForeignLoadHeifBuffer` |

   Everything else is stored with no thumbnail and reaches neither the
   detector nor sharp: SVG and SVGZ, PDF, TIFF and BigTIFF, HEIC/HEIF
   (`heic`, `heix`, `hevc`, `hevx`, `mif1`, `msf1` and other brands), JPEG
   2000, JPEG XL, JPEG-LS, BMP, ICO, PSD, Radiance, PPM, archives and text.
   HEIC is not supported: the bundled libheif has no HEVC decoder. The AVIF
   sequence brand `avis` is refused too: `file-type` reports it as
   `image/avif`, but libvips 8.18 cannot load it. AVIF bytes declared
   `image/heic` are still thumbnailed.
2. **Detector.** The `file-type` result must be the same family, which
   rules out, for example, JPEG-LS (`FF D8 FF F7`).
3. **Container.** Each format's structure is read in JavaScript before any
   native call:
   - **JPEG:** more than 100 scans (start-of-scan markers) is refused.
     libjpeg reads every scan of a progressive JPEG before libvips' timeout
     can act. A valid 7000 x 7000 file with 2,647 scans decoded for 12 s or
     more and held its turn throughout; 100 scans take 0.7 s. Encoders write
     about 10.

     The marker walk must reach EOI cleanly, or the file is refused. That
     rules out a stray byte or a TEM or restart marker between segments, a
     short segment, and a file that ends first. libjpeg skips such bytes
     with only a warning and decodes every scan after them, so a walk that
     stopped there would undercount. A single stray byte after scan 99 let
     the 2,647-scan file through in the second version.
   - **AVIF:** only one simple shape is accepted (`checkAvif`), rather than
     a model of what libheif would decode:
     - one `ftyp` (first) and one `meta`, with only `mdat`, `free` or `skip`
       beside them;
     - in `meta`, one each of `hdlr` (`pict`), `pitm`, `iloc`, `iinf` and
       `iprp` (one `ipco` and one `ipma`), plus at most one `iref`, `idat`
       and `dinf`;
     - items of type `av01`, `Exif` or `mime` only, with unique IDs, and
       only `auxl` and `cdsc` references;
     - a primary `av01` item, and at most one other `av01` item, which must
       be the primary's alpha plane (an `auxl` reference to it and an alpha
       `auxC`);
     - exactly one associated `ispe` on each `av01` item, the alpha's equal
       to the primary's;
     - an `iloc` (version 0 to 2) entry for each item and no other, with
       these rules:
       - data in the file inside an `mdat` box (construction method 0) or in
         `idat` (method 1);
       - no external data reference or extent index;
       - one to four non-empty extents per item, no two extents overlapping,
         so all item data together is never more than the file;
       - at most 1 MiB of Exif or XMP per item.

     Anything else is stored without a thumbnail. That includes grid,
     overlay and identity items, gain maps, thumbnails or depth items, two
     `meta` boxes (libheif decodes the last), and an alpha item without its
     own `ispe` (libheif decodes it at its full coded size). It also covers
     item extents that repeat the file: libheif concatenates an item's
     extents before decoding, and libvips copies Exif and XMP while reading
     the header. A 33.5 MB file whose primary listed the file 31 times
     needed +1,922 MiB, and one whose XMP item listed it 15 times needed
     +1,472 MiB, before the budget was checked. Offsets are read as 64-bit
     values and compared with the file, so no arithmetic overflows. Each
     extent's `mdat` box is found by binary search over the data boxes,
     built once, so a file with hundreds of items and thousands of `mdat`
     boxes, within the entry limit, is checked in milliseconds.

     The primary's `ispe` is its coded size, used for the estimate and the
     pixel limit, so a `clap` crop cannot hide what is decoded. An `ispe`
     that understates the coded size, on the primary or the alpha, is
     refused by libheif before it decodes.
   - **WebP:** the RIFF chunks decide the cost: lossless (`VP8L`), alpha
     (`ALPH` or the VP8X flag) or animated (`ANIM`/`ANMF` or the VP8X flag).
     The VP8X canvas size is used when it exceeds the reported size. Only
     chunks within the RIFF container's declared length are read, as
     libwebp does; trailing bytes are ignored and a truncated container is
     refused. `ICCP` chunks are summed (see below).
   - **PNG:** every chunk is walked to `IEND`. libpng inflates `zTXt`,
     compressed `iTXt` and `iCCP` while libvips reads the header, up to
     50 MB per chunk, before the budget is checked. A 477 KB file with ten
     49 MB `zTXt` chunks needed 2.3 GiB and OOM-killed a 1 GiB container.
     The walk inflates them with `zlib.inflateSync` and `maxOutputLength`
     against one shared limit of 4 MiB per file, and at most 64 compressed
     chunks are inflated, since each is a synchronous zlib call (65,000
     one-byte `zTXt` streams took 194 ms). Raw `tEXt`, `iTXt` and `eXIf`
     share a second 4 MiB limit. A malformed stream, a chunk that overruns
     the file, a missing `IEND`, or any of these limits exceeded refuses the
     file.

   **ICC profiles, every format.** The embedded profile is measured before
   any native call:
   - JPEG: the APP2 `ICC_PROFILE` segments;
   - PNG: the inflated `iCCP`;
   - WebP: the `ICCP` chunks;
   - AVIF: the `colr` `prof`/`rICC` properties.

   A profile over 4 MiB refuses the file. libvips copies the profile while
   reading the header and lcms builds transforms from it, about 9 bytes of
   memory per profile byte, so the estimate also charges 9 x the profile
   size. Two near-budget images with 32 MiB profiles had reached about
   1 GiB together.

   **Other metadata, every format.** libvips or its codecs also keep
   other metadata while reading the header, before the estimate is made.
   It is now measured in the same walks and charged at what it was
   measured to cost, with headroom:

   | Format | What is kept | Measured, glibc / musl (bytes per byte) | Charged |
   |---|---|---|---|
   | JPEG | every APP1 (Exif, XMP), non-ICC APP2 and APP13 (Photoshop/IPTC) segment: libjpeg saves them and libvips copies them | 2.0 / 2.3 | 3 |
   | WebP | the first `EXIF` and `XMP ` chunks, copied by libvips (all are counted) | EXIF 3.0 / 3.0, XMP 5.2 / 4.1 | 6 |
   | PNG | `tEXt`, `iTXt` and `eXIf`, inflated where compressed: copied by libpng and libvips, and returned by sharp | 7–9 / 6–7 | 10 |
   | AVIF | the largest Exif item plus the largest XMP item (libvips reads each in turn and keeps the last) | 5–10 / 4–6 | 12 |

   COM, APP0, APP14 and other APPn segments cost nothing measurable
   (libjpeg does not keep them), nor do GIF comment and application
   extensions (libnsgif ignores them).

   libvips takes any APP2 segment longer than 14 bytes whose first 11
   bytes are `ICC_PROFILE` as part of the profile, whether or not the NUL
   that ends the tag follows. The walk now does the same: a 6.55 MB
   profile under a tag without its NUL had escaped the 4 MiB cap and the
   9 x charge.

   Two near-budget JPEGs, each padded to 32 MiB with metadata, had reached
   956–983 MiB of a 1 GiB container. Each is now charged for its metadata,
   so each stays within its 384 MiB estimate.

   Each check reads at most 4,096 boxes or JPEG markers (65,536 WebP or
   PNG chunks, since encoders split PNG data into small `IDAT` chunks), and
   at most 2^20 escaped bytes in JPEG entropy-coded data. A file with more
   is stored without a thumbnail. A crafted 32 MiB file of tiny entries is
   therefore rejected in milliseconds; without the bound, a 32 MiB WebP of
   empty chunks blocked the event loop for 208 ms.
4. **Loader allowlist.** When a worker loads `thumbnail-decode.ts`, it
   blocks every libvips loader (`sharp.block({ operation: ["VipsForeignLoad"] })`)
   and unblocks only the five buffer loaders above, for the whole worker
   process. The server process never loads sharp.
   Even if a polyglot passed the first two checks, libvips cannot pick its
   SVG, TIFF, PDF, UltraHDR, Radiance, Magick or any other loader. UltraHDR
   JPEGs decode as ordinary JPEGs, and a GIF header followed by SVG markup
   reaches only the GIF decoder, which rejects it.
5. **Header.** libvips reads the header (`metadata()`) with the same options,
   and its format must match the signature.

## Decoder options

Every decode, the header read included, uses explicit options, so that
nothing depends on sharp's defaults:

| Option | Value | Effect |
|---|---|---|
| `failOn` | `"warning"` | Truncated or invalid pixel data aborts the thumbnail (sharp's default for untrusted input). |
| `limitInputPixels` | 268,402,689 (0x3FFF squared) | Width x height of the first frame; unchanged from sharp's default. |
| `limitInputChannels` | 4 | RGBA or CMYK. Down from sharp's default of 5, since TIFF is no longer decoded. |
| `unlimited` | `false` | Keeps libpng's and libheif's own safety limits. |
| `sequentialRead` | `true` | Streams formats that allow it. |
| `pages` | 1 | Only the first frame of an animated GIF or WebP, or the primary AVIF image. A 5,000-frame GIF costs the same as one frame. |
| `autoOrient` | `false` | EXIF orientation is still not applied, as before. |
| `timeout` | 10 s | libvips stops a transform that runs longer. |

The output is unchanged: a WebP at most 400 pixels wide, quality 80, without
enlargement. sharp also uses one libvips thread per transform
(`sharp.concurrency(1)`) and no libvips operation cache (`sharp.cache(false)`),
so decoded images are not kept after a transform.

## Decode memory budget

Some formats cannot be decoded row by row: the whole image, or its JPEG
coefficients, are in memory at once. Before decoding, `estimateDecodeBytes`
estimates the working memory from the header. A transform whose estimate is
over **384 MiB** gets no thumbnail and is never decoded.

The formulas use p = width x height, c = channels and b = bytes per sample
(1 for 8-bit, 2 for 16-bit). For AVIF, p is the largest coded size of any
item. For WebP, p is the larger of the reported size and the VP8X canvas.
Each formula has at least 20% headroom over what was measured (sharp 0.35.5,
libvips 8.18.7, glibc x64; the Alpine/musl image matches within 3%):

| Format | Estimate | Measured | Largest image within the budget |
|---|---|---|---|
| AVIF | p x (16 + 2cb) | 17.5 B/px (8-bit RGB), 24.4 B/px (10-bit RGBA) | 18 MP 8-bit RGB, 12 MP 10-bit RGBA |
| Interlaced PNG | 1.5 x pcb | 4.4 B/px (RGBA), 9.4 B/px (RGBA16) | 89 MP RGB, 67 MP RGBA |
| Progressive JPEG | 2.5 x pc | 3.1 B/px (4:2:0), 6.1 B/px (4:4:4), 8.2 B/px (CMYK) | 53 MP RGB |
| GIF | 7 x p | 4.6 B/px | 57 MP |
| WebP, animated | 12.5 x p | 10.2 B/px (4000², lossy frames with alpha), 8.4 B/px (7860²), 5.1 B/px (canvas with 1 x 1 frames) | 32 MP |
| WebP, lossless or alpha | 5.5 x p | 4.0 B/px (lossless, more than 16 colours; 2 colours pack to 0.5), 2.0 B/px (lossy with 64-level alpha) | 73 MP |
| WebP, lossy | 2 x p | 0.03 B/px (196 MP) | 201 MP |
| Baseline JPEG, non-interlaced PNG | pcb / 4 | 0.02 B/sample (256 MP RGB JPEG), 0.12 B/sample (256 MP RGBA16 PNG) | the pixel limit; 201 MP for RGBA16 PNG |
| Any format with an ICC profile | + 9 x the profile size | 7–9 x | the profile is at most 4 MiB, so at most +36 MiB |

Ordinary photos are well inside the budget: a 24-megapixel JPEG peaks at
30 MiB, and a 12-megapixel AVIF is estimated at 268 MB. Images refused for
memory are mostly malicious or unusual: very large AVIFs, interlaced PNGs,
progressive JPEGs and lossless or animated WebPs. With two transforms at
once, decoding stays under about 768 MiB.

## Admission

`thumbnailAdmission` is a semaphore, one per process, shared fairly between
workspaces:

- **At most 2 transforms at once**, and at most half the CPUs: 1 on one to
  three CPUs, 2 on four or more. Each uses one libvips thread, so thumbnails
  never hold more than two of libuv's four default threads.
- **At most 8 uploads wait** for a turn. When the queue is full, an upload
  from a workspace that holds at least two fewer turns (active plus waiting)
  than the busiest workspace takes that workspace's newest place. The
  displaced upload is stored without a thumbnail. Otherwise the new upload
  gets no thumbnail straight away.
- **A freed turn goes to a workspace with the fewest active transforms**,
  oldest waiter first. One workspace cannot keep another's uploads from
  being admitted.
- **A waiting upload gives up after 5 s** and is stored without a thumbnail.
- **Only allowlisted signatures wait.** The first 64 bytes are checked
  before a turn is requested, so SVG, TIFF, PDF or random bytes declared
  `image/*` are answered at once and never take a queue place. That read
  asks storage for those 64 bytes only. If it takes more than 2 s, the
  stream is destroyed and the upload goes on without a thumbnail.
- **An admitted upload stops waiting 12 s after admission**, whether the
  worker's file read or the decoder is slow (libvips' own timeout is 10 s).
  The worker is then killed and replaced. Its turn stays taken until the
  killed worker has exited, so a turn always covers a worker's memory, but
  no longer than that.

The limit on slow admitted work is per format: with at most 100 JPEG scans,
the slowest admitted input measured is the 100-scan 7000 x 7000 JPEG at
0.7 s. Before the scan limit, two 2,647-scan JPEGs held both turns for 12 s
or more, and other workspaces' uploads waited 5 s and got no thumbnail.
Since the deadline now kills, no input holds a turn past 12 s, however
long libjpeg or a header parse would take.

So the upload response is held at most 2 s (first bytes), plus 5 s (queue),
plus 12 s (transform) longer, and a thumbnail problem never fails the upload. A skipped thumbnail is not retried: the file
stays without one, as undecodable images already did. The Drive web client
uploads at most three files at a time, so one user does not fill the queue;
several users uploading images at the same moment can.

Outcomes are counted in `thumbnailOutcomes`: `created`, `busy`,
`unsupported`, `over-budget`, `failed`, `timed-out` and `crashed` (the
worker exited during the decode). Every omission except `unsupported` is
logged as "Thumbnail omitted": `crashed` as a warning, with the worker's
exit status or signal, the others at info level. The log line
carries the outcome, workspace and file id and, where known, the format,
dimensions, memory estimate or decoder error. `unsupported` is logged at
debug level. No metrics endpoint exposes the counters.

## Behaviour changes

- TIFF uploads are stored without a thumbnail (PR106 made them thumbnails).
- HEIF/HEIC brands other than AVIF no longer reach the detector. HEIC and
  HEVC never produced a thumbnail with the bundled codecs. An AVIF whose
  major brand is the generic `mif1`/`msf1` (libavif and libheif write
  `avif`) is now stored without one.
- Images over the memory budget lose their thumbnail. These are:
  - AVIFs over about 18 megapixels of coded size;
  - interlaced PNGs over 67 to 89 megapixels;
  - progressive JPEGs over about 53 megapixels;
  - GIFs over about 57 megapixels;
  - lossless or alpha WebPs over 73 megapixels, animated WebPs over 32
    megapixels of canvas, and lossy WebPs over 201 megapixels.
- AVIFs outside the simple shape described above are stored without a
  thumbnail. That covers grids, overlays, gain maps and extra image items.
  Cropped AVIFs are charged for their full coded size.
- JPEGs with more than 100 scans, or whose markers do not lead cleanly to
  EOI, are stored without a thumbnail. Such JPEGs already failed under
  libvips' `failOn: "warning"`, but only after a full decode.
- Images with an embedded ICC profile over 4 MiB are stored without a
  thumbnail. Real profiles are kilobytes; sharp's CMYK profile is 0.9 MiB.
- PNGs whose compressed text and `iCCP` inflate to over 4 MiB in total,
  whose plain text is over 4 MiB, or whose chunks are malformed or have no
  `IEND`, are stored without a thumbnail.
- During a burst of more than 10 image uploads in one process, the uploads
  beyond the queue are stored without a thumbnail. Each workspace keeps a
  share of the queue.
- AVIF sequences (`avis`) are refused before detection. libvips could not
  load them before either.

## Limits of this change

- The estimates were measured for sharp 0.35.5 and libvips 8.18.7, on glibc
  x64 and in the Alpine/musl production image. They must be measured again
  when sharp is upgraded.
- Running turns are not preempted. Admitted work is bounded per format by
  the budget and the scan limit, not by a share of time.
- The limits apply per process and are not configurable. Several backend
  processes multiply them.
- The checks bound which decoders run and how much they are given. They do
  not make the allowlisted codecs (mozjpeg, libpng, libwebp, libnsgif,
  libheif with aom) free of bugs.
- libvips' timeout acts while pixels are processed. If a header parse hangs,
  the upload still finishes after 12 s, but its turn stays taken until the
  parse ends.
- The loader block applies to the whole process. Any future sharp use in the
  backend gets only these five loaders.
- Skipped thumbnails are not regenerated later.
