# FE-014: explicit API retry policy

The API client's response hook throws `ApiError` for an application error. In
the installed ky 1.14.3, that custom error follows the generic error retry path
rather than the `HTTPError` status policy. Default GET, PUT and DELETE requests
therefore dispatched three times even for terminal errors such as a 404 or edit
conflict. The production QueryClient could repeat a failed query once more.
An error after a mutation was applied could repeat its side effects.

The default API transport and QueryClient now make one attempt. This applies to
terminal application errors, network failures, timeouts and transient server
errors, including safe reads. A failed request remains available for the user
to retry explicitly. This policy does not add a retry timer or consume
`Retry-After`; normal polling, explicit refetches and refetch-on-focus behavior
remain separate triggers.

An authenticated 401 still permits one session refresh and one replay with the
renewed token. A signed-out 401, or a 401 from the refresh endpoint, does not
start this flow. The replay has no transport retries and no authentication
response hook. Its errors retain `ApiError` status, message, field details,
machine code and current edit state. A failed replay cannot restart the outer
request's retry/refresh cycle, including when a caller supplies retry options.
Identity generation, abort and expected-author guards still cover the original
dispatch, refresh and replay; the auth store still deduplicates refreshes.

The existing chat-send exception supplies an idempotency key, a limit of two
retries and its own transient-error classification. Its server contract makes
repeating a send return the stored message. Other mutations have no automatic
retry. The invite-admission request's explicit `retry: 0` remains in place.
New retry overrides need a bounded attempt count, identity guards and an
operation-specific reason that repeating an ambiguous result is safe.

This fixes the confirmed finite application-error retries. The earlier
hypothesis of an infinite recursive 401 refresh hook was refuted for this same
installed ky version and is not the defect addressed here. Auth-store refresh
contention retries, session policy and backend behavior are outside this change.

The regression suite uses a loopback HTTP server and the actual exported API
defaults. It checks GET/PUT/DELETE/POST/PATCH dispatch counts, terminal and
transient errors, server-applied mutations followed by an error or lost
connection, bounded authentication replay, structured errors, keyed retries,
real refresh deduplication and the production QueryObserver's retry behavior.
The existing identity tests also run with the real retry defaults.

Before the fix, real default GET 404 dispatched three times, PUT 409 and a
DELETE with a lost response each applied three server operations, and one
production QueryObserver 404 dispatched six times. A PUT authentication replay
that failed with 503 or a lost response could dispatch six times; a replay 401
returned a raw `HTTPError`. The corrected 111-case matrix passes with one
default dispatch/operation, at most two dispatches for authentication recovery,
and preserved structured errors. Production PUT/DELETE mutation observers each
report one error callback and one applied operation. The keyed retry exception
still permits three dispatches while applying one operation.
