# Refresh-token families

Refresh rotation previously deleted the presented token in one transaction and
created its successor afterwards, outside it. Reuse detection deleted the
family's tokens without any lock or durable record, so a replayed token could
revoke a family while a legitimate rotation was between those two steps, and
that rotation then created a valid successor in the revoked family. Logout,
password change, password reset and the session replacement on password login
had the same gap: each deleted the tokens it could see, and a successor created
a moment later survived. Two simultaneous refreshes of one cookie failed with a
500 (unique or missing-row errors), and the rotated-token check could then
revoke the session of a user who merely had two tabs open.

## Families

`RefreshTokenFamily` (migration `20261028150000_add_refresh_token_families`) is
one sign-in session: `id`, `userId`, `createdAt`, `revokedAt` and
`revokedReason` (`reuse`, `logout`, `login`, `password_change`,
`password_reset`). Every `RefreshToken` references its family through a
composite foreign key on `(familyId, userId)`, so a token can neither exist
without a family nor belong to another user's family. Deleting a user deletes
its families and tokens. `RotatedRefreshToken` records keep their `familyId`
without a foreign key; a record whose family no longer exists is rejected with
401 and nothing else.

`packages/backend/src/modules/auth/refresh-sessions.ts` owns every write:

- `createRefreshSession` creates a family and its first token in one nested
  write (registration, password login and OIDC sign-in).
- `rotateRefreshToken` runs one READ COMMITTED transaction: it finds the
  presented token's family, locks the family row (`SELECT ... FOR UPDATE`),
  rejects a missing or revoked family, re-reads the token under the lock and
  then, in the same transaction, records the rotated hash, deletes the old token
  and creates the successor. An expired token (`expiresAt` at or before now) is
  deleted and rejected. Outcomes are returned rather than thrown so that a
  revocation or expired-token deletion commits.
- `revokeRefreshFamily` (logout) and `revokeUserRefreshSessions` (password
  login, password change and reset) take the same row locks, set `revokedAt`
  once and delete the family's active tokens. User-wide revocation locks the
  user's families in id order.

Because every mint and every revocation of a family holds its row lock, a
revocation that arrives during a rotation waits for it to commit and then
deletes its successor, and a rotation that arrives after a revocation sees
`revokedAt` and mints nothing. No interleaving leaves an active token in a
revoked family.

Password login keeps its existing behavior of replacing the user's other
sessions. It now does so in one transaction with the new session, holding the
verified password hash `FOR SHARE`: a concurrent password change or reset
either commits first (the login is rejected with 401) or waits and then revokes
the login's new family.

## Concurrent use policy

Tabs share one refresh cookie. Within a tab the store already deduplicates
refreshes, but two tabs can send the same cookie at once (simultaneous page
loads, or every tab's access token expiring together). The rules are:

| Presented token | Result |
| --- | --- |
| Active, family not revoked, not expired | 200, one successor (`Set-Cookie`) |
| Rotated less than 30 s ago (`REFRESH_REUSE_GRACE_MS`), family not revoked | 409, nothing minted or revoked |
| Rotated 30 s ago or more | 401, whole family revoked (`reuse`) |
| Any token of a revoked or missing family | 401 |
| Expired active token | 401 (`Refresh token expired`), token deleted |
| Unknown | 401 |

The grace window never mints: a replayed token gets nothing either way, and
reuse is detected once the window has passed. A stolen token used first by an
attacker still wins one successor, as with any rotation scheme; the victim's
next use of the old token after the window, or the victim's next password
login, revokes it.

The frontend (`packages/frontend/src/stores/auth-store.ts`) treats 409 as
"another tab won": it waits 250, 750 and 1500 ms, returning success as soon as
the winning tab's `BroadcastChannel` message has delivered the new access token
and otherwise retrying with the browser's (now replaced) cookie. If every retry
is still superseded it reports failure as before.

Logout revokes the cookie's whole family, whether the presented token is the
current one or an already rotated one; an unknown cookie is a no-op (204).
Database errors are no longer swallowed by logout. The endpoint still requires
an access token.

## Credentials outside the family

These semantics are documented here and unchanged:

- Access tokens are HS256 JWTs valid for 15 minutes and are not looked up on
  use. Logout, password change, password reset and family revocation do not
  invalidate an access token already issued; it works until it expires. The
  WebSocket connection also authenticates with it (see DAT-006 for realtime
  session expiry).
- Personal API keys (`wk_...`) are looked up on every HTTP request. Revocation
  and expiry take effect on the next request. They are independent durable
  credentials: logout, password change, password reset and refresh-family
  revocation do not revoke them; the owner revokes them in Settings. Deleting
  the user deletes them.
- Refresh tokens expire seven days after their own issue, so an active session
  slides indefinitely while it keeps refreshing. There is no absolute session
  lifetime.

## Validation

`packages/backend/tests/integration/refresh-family-atomicity.test.mjs` runs the
application against PostgreSQL with separate actor and control connection
pools. Barriers are real database locks observed through `pg_stat_activity`: a
row lock on the presented token (any rotation must change that row), and a
trigger that makes the INSERT of a family's (or user's) next token wait on an
advisory lock held by the control transaction. The tests cover two overlapping
refreshes (one 200, one 409, one active token), a four-request burst, reuse
revocation racing an in-flight rotation, logout, password change, password
reset and login each racing an in-flight rotation, a reset racing a login with
the old password, revocation/refresh storms, the grace boundary on both sides,
expiry on both sides, logout scope, the composite foreign key and cleanup. On
the previous code 15 of 16 fail, including surviving successors after reuse,
logout, password change, reset and login. `auth-store-refresh.test.ts` covers
the frontend retry.

Cleanup (`cleanupExpiredTokensAndAttempts`) removes families that have no
tokens left, a week after their revocation or, if never revoked, a week after
creation.

## Out of scope

- Immediate revocation of issued access tokens and open WebSockets (DAT-006).
- Revoking API keys on password change or reset.
- An absolute session lifetime.
- Password-reset token double use: the reset token's `usedAt` is checked
  before, not inside, the reset transaction.
