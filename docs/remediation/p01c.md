# P01c: windowed Drive folder views (R17)

A Drive folder loads 50 entries per request and asks for the next page when
the end of the list scrolls into view. Nothing was ever taken out of the
page again: after scrolling through a folder of 5,000 entries the list (or
grid) held 5,000 rows, each with a context menu, an actions menu, a
checkbox, a star button and a drag-and-drop registration. Every page that
arrived, every selection click and every refresh rendered all of them again.

The project List is P01b; this note covers the Drive folder views only.

## What changed

- **Only entries near the view are rendered** (`FileListView`,
  `FileGridView`, `hooks/use-drive-window.ts`). The views use
  `@tanstack/react-virtual` against the Drive page's scroller (the element
  that already scrolled the folder). Rows or lines of cards outside the view
  and a few beyond it are replaced by gaps of the same height. The data,
  paging, sort and selection are unchanged: they still cover every loaded
  entry.
- **Every row has one height.** List rows are one line (long names, uploader
  names and dates are cut off with an ellipsis) and grid cards all have the
  size line (empty and hidden for folders). The row height is measured from
  two adjacent rendered rows, so a place in the list follows from an index
  and no row is measured on its own.
- **The list table has a fixed layout.** Column widths come from the header,
  not from whichever rows are rendered. This also fixes a layout bug on main:
  one long file name made the name column as wide as the name, pushing size,
  owner, date and the actions menu out of view (a 944 px view scrolled
  sideways over 1,638 px of table in the fixture). The table keeps a minimum
  width of 36 rem, so on a narrow screen it scrolls sideways as before.
- **The entries in view stay where they are when the list changes above
  them** (`KeepInView`, `lib/steady-entry.ts`). See below.
- **Kept rendered whatever the scroll position:** the first and last rows
  (Tab into the list from above reaches the first entry; Shift+Tab from below
  the last), the row that last held focus and its neighbours (a menu opened
  from it keeps its trigger; arrow keys move on from it), and the entry being
  dragged (dnd-kit keeps its node and data while the view scrolls during the
  drag, so the drop moves that file).
- **Arrow keys** move focus by index (`[data-index]`) instead of to the next
  DOM sibling, which may now be a gap.
- **Share status is asked for near the view, in groups of up to 200
  entries** (`hooks/use-file-share-status.ts`). Main asked for every loaded
  entry in one URL; past about 600 entries the server answered 431 (request
  header too large), so no entry in the folder showed its share icon, and
  every page that arrived sent the growing URL again. Now:
  - the views report the entries in view, and once scrolling settles (a
    second without a change, and no sooner than four seconds after the
    last time; at once for a listing or a view just shown,
    `useSettledEntries`) the entries from 50 before them to 50 after them
    that are in no group yet start a group, filled with the entries in no
    group that follow, up to 200. Pages that arrive while the view stays put
    are asked for only as far as they are in view, so the pages loading
    below a view at the end of the loaded entries wait for the next settle.
    Skimming or jumping through a long folder therefore asks for share
    status a few times a minute at most, and reading on from a settled view
    finds about four pages already asked for;
  - a group keeps its members once formed, and an entry that leaves the
    list leaves its group: an entry added near the top asks only for
    itself, an entry that comes back is asked for afresh, and a group asked
    again keeps showing its earlier answer until the new one arrives;
  - only groups near the view are kept fresh (a refocused window, a share
    change); the others are asked again when the view comes near them;
  - a share or link change asks again only for the groups holding the files
    changed (the share dialog names a deleted link's files; otherwise they
    come from the cached link lists, and only when they are unknown is every
    group of the workspace asked again);
  - a request refused with 429 is asked again after the server's
    Retry-After, twice at most.
- **A next page that fails to load no longer replaces the folder**
  (`hooks/use-next-page-retry.ts`, `drive-page.tsx`). Main showed "Failed to
  load files" in place of every entry already loaded when any page request
  failed (a 429 from the server's per-address request limit, for example).
  The entries now stay listed and usable, and below them the view says it
  could not load more and offers "Try again". A failure that may pass (a
  429 from the request limit, a timeout, a server error, no answer) is
  also asked again on its own after the wait the server asks for
  (Retry-After, as the API client reads it into `ApiError.retryAfter` for
  the sign-in backoff, and exposed to frontends on other origins by the
  same CORS setting; otherwise 2, 4, 8 ... up to 60 seconds), five times at most, starting
  over for another folder, search or sort. While it waits, the end of the
  list coming into view does not repeat the request. A refresh that fails with entries loaded keeps them
  too, with "Couldn't refresh this folder" and "Try again" below them. The
  full-page error remains for a folder whose first page fails.
- `handleDragEnd` ignores a drop whose dragged entry has no data instead of
  sending a move for an undefined file.

## Keeping the entries in view in place

Without windowing, Chromium's scroll anchoring keeps the rows in view still
when rows above them are added or removed (not when a row's element moves
from below the view to above it; see Validation). With gaps standing in for the rows
above, it does not: the gap grows or shrinks and every row below it moves.
P01b's review found the consequence in the List: a click made just after a
refresh lands on another row. It also found that the browser clamping the
scroll position at the end of a list that got shorter was taken for the user
scrolling.

`KeepInView` is a class component around the rendered rows, because React
calls its `getSnapshotBeforeUpdate` right before it applies a change to the
DOM:

1. Before the change it records each entry in view (by file id) with its
   index and its top **in the scroller's content**, and the scroll position.
2. After the change it picks the entry to keep (`steadyEntry`). The entries
   seen are grouped by how many places each moved. Five entries listed just
   above the view and five just below it are remembered too, and the group
   that moved as most of them did is kept: the entries that kept their
   place in the list around them.
   - Entries added or removed above the view move the entries seen and
     their neighbours alike, by any number of places: that group is kept.
   - Entries renamed so that they now sort far away (a colleague's batch
     rename, an edit under the Modified sort) leave their neighbours.
     However many of them there are, the view does not follow them; it keeps
     the entries that stayed among their neighbours.
   - One entry renamed to land near its old index while entries were added
     above does not take the view with it either.
   - An entry added or removed within the view leaves the entries on each
     side with their neighbours above or below: the larger side is kept, so
     as many entries as possible stay put.
   - Without neighbours to go by (the list is that short, or they all changed
     too), the largest of the groups that moved by no more places than the
     view holds is kept, or, when every group moved further, the one that
     moved least.

   Within the group, the first entry still rendered after the change is
   kept, so its place is measured rather than computed.
3. It finds that entry's new top in the content (from the DOM, or from its
   index when so much changed above that it is no longer rendered), and sets
   the scroll position to the old one plus the difference.

Both tops are in content coordinates, so they do not depend on the scroll
position: the browser clamping it at the end of a shorter list is not
mistaken for the user scrolling, and nothing is inferred from scroll deltas.
The user's own scrolling never moves an entry in the content, so it is never
corrected. After a correction the virtualizer is told the new position at
once and renders the rows there before the paint (it would otherwise learn
it from the scroll event after the paint).

The browser's own anchoring must not move the rows a second time, so rows,
cards and gaps have `overflow-anchor: none`. Chromium then anchors on the
table body (or the grid), which does not move when the list changes but does
move when content above the list changes height (the Starred section on the
Drive home page, for example); that case stays with the browser, as on main.

Nothing is kept while the top of the list is in view: an entry added at the
top shows there, as on main.

**The grid's column count.** The grid has 5, 4, 3 or 2 columns at window
widths above 1024, 768 and 640 px. When the window crosses one of these, the
browser reflows the cards into the new columns at once, before the grid
renders again with the line count for them, so the places of the cards on
screen no longer say which were in view. `KeepInView` stands aside for that
render (`layoutKey`); the grid instead takes the first line in view from the
scroll position and the layout before the change, finds its first entry by
id in the list now (a refresh may arrive in the same render), and puts the
line that entry starts or falls in at the same place.

**At the end of the list.** A refresh refetches as many pages as were
loaded. When entries were added above, the refetched pages end before the
last entries, which move to the next page; at the end of the list those
entries are in view, and the list got shorter below the entries kept in
place, so the browser would stop the scroll position short and every row in
view would move down (77 px in the smoke's case before this was handled).
While another page is to come, `KeepInView` asks the view to hold the
missing height below the entries (`onShort`), keeps the scroll position on
the next render, and the infinite-scroll sentinel, now in view, loads the
page; the space held goes when the entries change. When the refresh leaves
every entry in view (and possibly many above it) for the next page, none of
the entries seen is listed any more: an entry above the view that is still
listed is kept instead, the nearest of the eleven nearest such entries that
moved as most of them did (so not one renamed to sort elsewhere). Entries removed in or
below the view at the end of a complete list still let the rows above them
move down, as on main.

## Limits

- Find-in-page, printing and a screen reader's browse mode see only the
  rendered entries; Drive search finds files by name on the server.
- Rows are `role="button"` (dnd-kit's draggable attributes, as on main), so
  the table does not carry `aria-rowcount` / `aria-rowindex`.
- The windowing applies to the Drive page's list and grid (folders, team
  folders, the home page's "My Files" and search results); trash and the
  shared-with-me / shared-by-me views still render every loaded entry.
- A refresh still refetches every loaded page of the folder one after
  another (100 requests for 5,000 entries), so refreshing a folder that
  large reaches the server's 100 requests a minute per address; the entries
  then stay listed with "Couldn't refresh this folder". The limit is not
  changed here.
- Only Chromium was measured. Browsers without CSS scroll anchoring (Safari)
  keep the rows in place through list changes by `KeepInView` alone; content
  above the list changing height moves them there, as on main.
- The anchoring helpers (`KeepInView`, `steadyEntry`, `useDriveWindow`) are
  local to Drive. The project List (P01b) has its own; the two could share one
  once both are merged.
