# Durable recurring tasks, reminders and notifications

## Recurring tasks

The scheduler created a task in one transaction and advanced the schedule's
`nextRunDate` in another, and it advanced even when the task could not be
created. A failed creation lost that occurrence. A crash between the two
writes, two server instances, or a run that overlapped the previous one
generated it twice. Editing a schedule's frequency or day on a day it had
already run also generated that day again. Catch-up generated one missed
occurrence per run, with a due date counted from the day it was generated
instead of the occurrence (DAT-018).

Each occurrence is now one transaction. It locks the project row (key share)
and then the schedule row, records the date in `RecurringTaskOccurrence`
(primary key: schedule and date), creates the task, and advances
`nextRunDate`. The writes commit together or not at all:

- A failure or crash at any point leaves the schedule on the same date. The
  next run (every 15 minutes) generates it. An occurrence is never skipped
  because generation failed. It is retried on every run and logged each time
  until it succeeds.
- A date is generated at most once. A second instance skips a schedule that
  another instance holds (`FOR UPDATE SKIP LOCKED`) and re-reads it under the
  lock. The occurrence key rejects a date that was already generated, even when
  an edit or a resume moved `nextRunDate` back to it. Deleting a generated task
  keeps its occurrence row, so the date is not generated again.
- The template's `dueOffset` counts from the occurrence date. Manual
  instantiation from a template still counts from today.

Catch-up and skip policy:

- An active schedule generates every date it missed (the server was down, or
  generation kept failing), oldest first, each with its own due date. A run
  generates at most 31 dates per schedule. A longer backlog continues on the
  next run.
- Dates up to `endDate` are generated even when `endDate` has already passed.
  The schedule is then deactivated. Before, those dates were dropped and the
  schedule stayed active.
- Resuming a paused schedule moves `nextRunDate` forward on its own cycle to
  the first date on or after today that has not been generated. Dates that
  passed while it was paused are not generated. Before, they were generated
  late, one per run.
- A schedule whose project is archived skips its due dates. An archived
  project gets no tasks. Before, the dates piled up and were generated one per
  run after the project was unarchived.
- Editing a schedule's frequency or day still sets `nextRunDate` to the first
  occurrence on or after today. If that date was already generated, it moves
  on to the next one.

A schedule written by the old monthly arithmetic can hold a first run one month
late ([dat-007.md](dat-007.md)). Each run moves such a row back. The run checks
active MONTHLY schedules whose next run is later than the first occurrence on
or after today. An occurrence in the future cannot have been generated yet. An
occurrence due today counts as missing unless a scheduler run advanced the row
on this exact day. A run that generated today's date or skipped it for an
archived project records that in the schedule's `lastRunDate`; edits never
write it. Moving a row back onto a date a run did generate is harmless, because
its occurrence row stops a second task.
The move is a compare-and-set on the row as it was read, so an edit in between
keeps its own result. Rows written by the current code never match.
BIWEEKLY rows keep their stored phase, as before. The check pages through
those schedules and stops when the run is stopped.

Lock order: an occurrence takes the Project row first (`FOR KEY SHARE`, which
does not block project updates such as archiving), then the schedule row, then
the status, member and label rows and the task rows that task creation
touches. Project and workspace deletion lock the Project row before they
cascade to its schedules, so either can run alongside an occurrence. One waits
for the other instead of deadlocking.

## Due-date reminders and notifications

Reminders inserted their "sent" markers, then sent a notification for every
candidate, including ones another run had just marked. Two overlapping runs
both sent. A failed notification left its marker behind, so it was never
retried. `createNotifications` used `Promise.allSettled` and dropped failed
inserts without an error (DAT-020). A task, comment, template or file-share
notification that failed was lost, and so was a title over 255 characters.

These notifications now go through an outbox (`NotificationDelivery`), on the
same lease and backoff design as the separate chat delivery outbox:

- Producers enqueue required intents in their domain transaction, then make
  the first delivery attempt after commit (see below). A reminder run writes
  its markers and their outbox rows in one transaction. Only markers that this
  run inserted get a row, so overlapping runs send each reminder once.
- An attempt creates its notifications in the same transaction that marks the
  row as notified. A retry never creates them twice. All recipients get one or
  none do, and a failure is recorded on the row instead of being dropped.
- Recipients are filtered as before: the actor is excluded, along with
  recipients without project access and recipients whose preferences turn the
  type off. Recipients must also still be members of a workspace named in the
  data (file shares and reminders carry one), as the notification list
  already requires. The filter runs when the notifications are created, so a
  retry never reaches someone who lost access in the meantime. Titles and
  bodies are shortened to the stored limits.
- The attempt that created the notifications pushes `notification_new` (shown
  as a toast). A retry after they were created sends only
  `notification_created`, which refreshes the list without repeating the
  toast.
- A failed attempt is retried by a worker every 30 seconds, with exponential
  backoff from 5 seconds up to one hour, for up to 20 attempts. A crashed
  attempt is retried after its 60-second lease expires. A delivered row is
  deleted. An exhausted row keeps `lastError` with no next attempt.

### Producer transactions

The current application producers commit their required intents with the
changes that trigger them:

- [Task status updates, moves, assignments and duplication](task-notification-outbox.md)
  enqueue in their existing service transaction, including calls through the
  original direct service exports. Status changes are decided from the status
  reread under the Project lock; a same-status update or same-column move
  creates no transition intent.
- [Task-comment creation](comment-notification-outbox.md) commits its comment,
  activity and assignee/mention intents together.
- [Manual template creation](template-notification-outbox.md) commits its task,
  subtasks, activity and assignment intent together.
- [Member file sharing](file-share-notification-outbox.md), when called with
  the server, commits new shares and one batch intent together. An all-existing
  batch creates no intent; a partly new batch retains all requested nonactor
  recipients, including existing grantees.

A required enqueue failure rolls back its domain transaction. Broadcasts and
first delivery attempts run after commit; an optional failure is logged and
does not turn a saved operation into a misleading HTTP error. Committed intents
remain available to the worker. These paths assume the normal nonthrowing
logger contract. Their bounded postcommit diagnostics retain stage/source IDs,
fixed error kinds and allowlisted network codes, without copying arbitrary
exception messages, stacks, causes or accessor properties. The central
delivery worker's logging is unchanged.

Ordinary task-create and bulk handlers gain no notification trigger. The pure
`createTaskFromTemplate` export, including recurring generation, retains its
no-assignment-notification contract. Internal file-share calls without the
server also remain nonnotifying. Comment edit/delete activity writes are
unchanged and are outside the comment-create transaction described here.

The generic `notify()` convenience API remains available, but current
production producers use transactional enqueue directly. It writes an outbox
row and then attempts delivery, resolving with `completed`, `pending` (queued
for retry) or `skipped` (no one to notify). An enqueue failure rejects; ordinary
delivery failures resolve to pending under the normal logger contract. This
wrapper cannot atomically include a mutation its caller already committed.
Future producers that require that guarantee must enqueue with the transaction
client before committing, then deliver afterward.

## File-scoped notifications

File-share notifications retain file titles and snippets. Delivery previously
checked workspace membership without checking the file itself, and the list
and unread count had the same gap. Revoking just a file share left its old
notification readable and allowed a queued notification to be delivered.

Notification creation, listing and unread counting now use the same current
file-read predicate. It matches the normal file API's authority: current
membership in the file's actual workspace, a nontrashed existing file, valid
same-workspace team context, and ADMIN, personal owner, current team/group
membership or a valid explicit/inherited share. Team root relations take
precedence over legacy child relations. An inherited share crosses only active
folder parents in the same ownership/team/workspace scope. A direct share on
the leaf remains independent of inaccessible ancestors. `UNION` deduplicates
legacy cycles; the lookup walks only that file's ancestors.

The SQL predicate filters list rows before pagination and unread counting, and
filters delivery recipients inside the existing notification transaction.
Other named project/task/workspace scopes must also remain readable. A legacy
`fileId` without `workspaceId` resolves the file's actual workspace; a supplied
workspace must match it. Malformed non-null file IDs and `FILE_SHARED` rows
without a usable source are hidden and not created by a later retry. Ordinary
notifications without file scope retain their existing behavior. Preferences,
all-or-none creation, leases and exactly-once/retry behavior are unchanged.

Already-stored notifications are retained. Losing access hides their content
and excludes them from unread counts; restoring access can reveal them again.
A retry after creation sends only the existing content-free ID refresh, never
a second title/snippet toast. Authorization does not lock file/share rows:
work authorized before a concurrent revocation may finish. A delivery or read
started after that revocation commits uses current access and refuses the
content. This adds no global revocation-serialization guarantee.

The current multi-file sharing producer names only the first file in its
notification data and uses a generic batch-count title. This predicate checks
that named source; it does not invent metadata for every other batch file or
change the producer's notification contract.

## Shutdown

The scheduler timers were never stopped, and nothing kept a run from starting
while the previous one was still running. Token cleanup, due-date reminders,
recurring tasks and trash purge now run as stoppable jobs. Runs of one job
never overlap. Stopping a job clears its timers, signals the run in progress
and waits for it. Recurring tasks stop between occurrences, reminders and
notification deliveries stop between rows, and trash purge stops between
candidates. Token cleanup is a few single-statement deletes.

On SIGTERM or SIGINT, the scheduled jobs and the notification delivery worker
stop first, all at once, in one step with a 500 ms budget. The existing steps
follow: blob cleanup, chat deliveries, Dex and the HTTP server. The step
budgets add up to 7.5 s of the 8 s deadline. If a job is still running when its
budget ends, for example an occurrence waiting on a lock, the HTTP close waits
for that transaction when it disconnects from the database. The process then
exits with status 1 at the 8 s deadline, and the transaction rolls back. Any
work cut off by a budget or by the process exit is safe. Occurrences, reminder
batches and purge candidates are single transactions that roll back, and
deliveries are retried after their lease expires. A budget overrun is logged
and exits with status 1.

## Tests

`tests/integration/durable-scheduler-jobs.test.mjs` runs against PostgreSQL
with database triggers that inject failures and barriers:

- Two scheduler instances (separate connection pools) are held at a barrier
  until both are generating. The result is one task per occurrence, each with
  its own due date.
- A task-insert failure and a failure between task creation and the advance.
  Each is rolled back and generated once by the next run.
- A scheduler process killed (SIGKILL) while blocked before the task insert
  and while blocked between task creation and the advance. After a restart,
  exactly one task exists.
- An edit on an already generated day, a resume after a pause, a passed end
  date, an archived project, a 41-day backlog over two runs, and late monthly
  rows. These are a row whose missing occurrence is today (also after an
  end-date edit that day, or with a last run dated in the future by a clock
  that ran ahead), a row a run already handled today, and a row edited between
  the repair's read and its write.
- A shutdown during a running pass. It waits for the occurrence in progress
  and starts nothing new.
- Deleting a project or a workspace while one of its occurrences is in
  progress, in both orders: the deletion returns 204 and the occurrence does
  not fail. Before the project lock, these deadlocked, and either the deletion
  returned 500 or the occurrence failed.
- Two reminder runs held at a barrier send one reminder each. A failed
  reminder or comment notification is delivered once by the retry. A failure
  for one recipient stores no notifications, then all of them on the retry. A
  failed completion repeats neither the notification nor the toast. A
  file-share notification retried after a recipient left the workspace is not
  created for that recipient, and an overlong title is shortened. The suite
  also passes with every connection pool limited to one connection.

`tests/periodic-job.test.mjs` covers the job lifecycle: no overlapping runs,
stop waits for the run in progress and clears its timers, and a failed run is
logged without stopping later runs.

`tests/integration/notification-file-access.test.mjs` compares notification
list/unread/delivery with canonical file reads across owner/admin/team/group,
direct/inherited/cyclic/corrupt-scope cases. Real TCP requests and WebSockets
cover share revocation, stored private titles, deferred creation and repeat
content-free refresh. Metadata, pagination/type/unread filters and a database
insert barrier cover legacy data and the authorized-in-flight qualification.
The original scheduler workspace-leaver and realtime notification-list tests
now use real files and valid shares. Their fault/retry, current-member
delivery, before/after counts, cursor/type and peer assertions are preserved.

## Upgrade

Migration `20261030090000_add_durable_scheduler_jobs` adds both tables and
`RecurringTaskConfig.lastRunDate`. It sets `lastRunDate` on existing schedules
to the date of their last write, since the old code kept no separate record of
runs. Occurrences generated before the upgrade are not recorded. An edit on the
upgrade day of a schedule that already ran that day can still generate it once
more. On the upgrade day only, a late monthly row whose missing occurrence is
that day, and that was written earlier that day before the upgrade, is treated
as already handled.

## Limits

- Reminders still fire only on their reminder day (due date minus the
  timing). If every run on that day fails, for example because the server is
  down all day, that reminder is not sent later.
- A notification is pushed only to sockets connected to the instance that
  delivers it, as before.
- File-share batch notifications still name only their first file, and
  authorization does not cancel work admitted before concurrent revocation.
- A caller that uses generic `notify()` only after committing its mutation
  still has a crash gap before enqueue; the transactional producers above
  avoid that gap by writing their intents before commit.
- There is no general HTTP idempotency key. Deliberately repeated unkeyed
  comment, manual-template or duplicate requests can create distinct rows and
  intents. Retrying one committed delivery does not duplicate stored
  notifications; after creation it sends only a content-free refresh. This
  does not guarantee exactly-once network transmission or that every toast
  reaches its recipient.
