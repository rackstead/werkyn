# P02a: measured query fixes and an index for the hottest read paths

The audit listed performance candidates (task boards, chat, time reports,
schedulers) without measurements. This change adds a reusable fixture and
benchmark, measures the main read endpoints over HTTP, ranks the SQL they run,
and fixes what the plans showed. Most of the cost was in query shapes, not in
missing indexes: four local, behaviour-preserving query changes and one index.

## Fixture

`packages/backend/scripts/perf/seed.ts` fills an empty, migrated, disposable
database. It writes rows through Prisma `createMany` in foreign-key order, so
every constraint is checked. The data is the same for the same seed (dates are
relative to the day it runs), and it refuses to run unless `PERF_SEED_CONFIRM`
names the connected database and that database has no users or workspaces.
Every account gets an unusable random password.

```sh
PERF_SEED_CONFIRM=<db> DATABASE_URL=postgresql://.../<db> pnpm --dir packages/backend perf:seed
```

At the default scale it takes about 90 s and produces a 567 MB database:

| Area | Rows |
| --- | --- |
| Workspaces / users / memberships | 4 / 300 / 300 (60%, 25%, 10% and 5% of the data) |
| Projects / status columns / labels / custom fields | 50 / 250 / 500 / 200 |
| Tasks | 100,000 (60,000 in the largest workspace; largest project 11,733, of which 10,789 active; 8% archived) |
| Assignees / task labels / custom field values | 137,545 / 125,254 / 180,206 |
| Dependencies (acyclic, same project) / subtasks / comments | 9,974 / 59,853 / 62,347 |
| Activity log | 170,051 |
| Chat channels (public, private, DM) / members | 327 / 3,918 |
| Chat messages (12% thread replies, 2% deleted) / reactions / thread subscriptions / bookmarks | 200,000 / 30,557 / 36,689 / 2,060 |
| Wiki spaces / pages (trees up to four levels) / versions | 18 / 20,000 / 12,197 |
| Files (5,940 folders, 1,356 trashed, 13 team folders) / shares / share links / stars | 50,000 / 2,978 / 500 / 1,912 |

| Notifications (with the `data` scopes the app writes) / reminder markers | 200,000 / 7,615 |

## Method

- **Server:** the production build (`NODE_ENV=production`, `LOG_LEVEL=warn`)
  against a copy of the seeded database, restored from the same template for
  every pass. Each pass waits 140 s after start-up so the first runs of the
  due-date, recurring-task and trash-purge schedulers finish before measuring.
- **HTTP:** `scripts/perf/bench.ts` looks up actors and IDs in the database
  (a workspace admin and the member with the most assignments in the largest
  workspace) and times 37 read endpoints: task boards and lists, my tasks,
  dashboard, activity, search, chat history, threads and unread counts,
  notifications, drive listings, shared-with-me and shared-by-me, wiki trees and
  time reports. Each endpoint gets 3 warm-up requests, then 30 sequential timed
  requests; p50 and p95 are nearest-rank. The write benchmark times task create,
  task moves and chat sends (40 samples each).
- **Statements:** a separate pass with `log_min_duration_statement = 0` set on
  the benchmark database only (10 samples per endpoint).
  `scripts/perf/statements.ts` ranks the logged statements by total time
  (parse + bind + execute) and runs `EXPLAIN (ANALYZE, BUFFERS)` on the slowest
  call of each top statement with its logged parameters.
- PostgreSQL 16 (the CI image) with default settings (128 MB shared buffers).

1-3 ms, and the recurring and delivery queries under 0.3 ms.

## Changes

1. **Shared-file grants** (`files/file-access.ts`): the `scoped` CTE is
   `NOT MATERIALIZED`. Its conditions are unchanged; PostgreSQL now applies them
   to the shared rows (from `FileShare_sharedWithId_idx`) and their children
   (from `File_parentId_idx`) instead of to every file of the workspace. Same
   result rows; 27.9 ms → 1.6 ms for the same parameters (mean over the
   captured calls 13.2 ms → 0.19 ms). Covered by the existing
   `file-read-grants` and `file-tenant-boundary` suites.
2. **Dashboard counts** (`workspaces.service.ts`): one grouped SQL query
   returns each project's active, completed and overdue counts instead of
   loading every task. Overdue keeps the JavaScript definition exactly: a
   non-empty due date that sorts before today by code unit (`COLLATE "C"`), in
   a non-completion column. `dashboard-counts.test.mjs` compares the response
   with that per-task definition, including legacy empty, unpadded and
   non-date values, a column from another project, archived tasks and projects,
   and member visibility. It passes on main and on this branch.
3. **List counts** (`tasks.service.ts`, `chat.service.ts`): the task list and
   board, chat history and pinned messages compute `_count` for the returned
   rows only (`= ANY($ids)` on the existing `Subtask_taskId_idx`,
   `TaskDependency` unique index and `ChatMessage_parentId_idx`), with the same
   definitions: all subtasks, blockers in the same project, all replies
   including deleted ones. The response shape is unchanged.
   `list-relation-counts.test.mjs` compares the responses with Prisma's
   `_count` include and passes on main and on this branch. Single-row reads
   keep the include, since PostgreSQL pushes their ID into the grouped
   subquery.
4. **Index** `Task_projectId_archived_position_createdAt_idx` on
   `("projectId", "archived", "position", "createdAt")`: the task list's board
   order (`position, createdAt, id`) is read from the index with a small
   incremental sort on `id`, instead of a bitmap scan and sort of every active
   task of the project.

### Why the index has no `id` column

The first version indexed `(projectId, archived, position, createdAt, id)` to
match the ORDER BY exactly. That regressed the notification list from 2.2 to
11.9-12.6 ms in both passes with it. The visibility filter checks
`EXISTS (... "Task" t WHERE t.id = n.data->>'taskId' ...)`. With an index-only
source of all task IDs of a project, the planner switched that check from
per-row primary key lookups to hashing every readable task (54k rows). Without
`id` the plan stays on primary key lookups (0.4-0.7 ms with custom and generic
plans). The list keeps nearly all of the benefit (EXPLAIN on the largest
project):

| Task list query | No new index | `(…, createdAt, id)` | `(…, createdAt)` |
| --- | ---: | ---: | ---: |
| Page 1 (LIMIT 20) | 3.9 ms, top-N sort of 10,789 rows | 0.04 ms | 0.05 ms |
| Page 50 (OFFSET 980) | 4.3 ms | 0.42 ms | 0.5-0.75 ms |
| Board (all rows) | 8.7 ms | 8.8 ms (planner keeps the sort) | not used |

## Migration

`20261030150000_index_task_board_order` adds the one index with
`CREATE INDEX IF NOT EXISTS`. Applied to a copy of the populated fixture:

- `prisma migrate deploy` wall time 1.97 s, including CLI start-up; recorded
  execution 961 ms on a freshly copied (cold) database; the same build warm
  took 126 ms.
- Index size 5.8 MB. The Task table with its other seven indexes is 46 MB.
- `prisma migrate diff` from the migrations to the schema is empty.

Lock impact: `CREATE INDEX` takes a SHARE lock on `Task` for the build. Task
writes wait; reads do not. The shipped entrypoint runs `prisma migrate deploy`
before starting the server, so in that deployment nothing is waiting.

`CREATE INDEX CONCURRENTLY` was tested with Prisma 6.19.3. It works only as
the only statement of a migration; with two statements Prisma runs the script
as one implicit transaction and PostgreSQL refuses (25001). It is not used
because a failed concurrent build leaves an invalid index that has to be
dropped by hand before the migration can be retried. Operators who migrate while
an older version is still writing can build the index first:

```sql
CREATE INDEX CONCURRENTLY IF NOT EXISTS "Task_projectId_archived_position_createdAt_idx"
  ON "Task"("projectId", "archived", "position", "createdAt");
SELECT indisvalid FROM pg_index WHERE indexrelid = '"Task_projectId_archived_position_createdAt_idx"'::regclass;
```

Then upgrade. If `indisvalid` is false, drop the index and build it again.

## Write path

Over HTTP (p50 / p95 ms). Task create, move and chat send run the same code on
main and on this branch, so the middle column also shows run-to-run noise:

| Operation | Main | Branch, no index | Branch |
| --- | ---: | ---: | ---: |
| Create task (largest project) | 14.3 / 17.3 | 14.4 / 19.4 | 14.5 / 17.6 |
| Move task to the end of a column | 37.7 / 47.4 | 39.4 / 54.6 | 38.5 / 45.7 |
| Move task to the top of a column (renumbers about 1,000 rows) | 614.3 / 714.5 | 641.6 / 718.8 | 642.1 / 683.0 |
| Send chat message | 21.6 / 23.3 | 21.0 / 25.1 | 19.7 / 23.5 |

The index's own cost, measured in PostgreSQL in three alternating rounds of
rolled-back transactions on the largest project:

| 2,000 single-row statements | Without the index | With the index |
| --- | ---: | ---: |
| `UPDATE "Task" SET position = position + 1` | 36.9-41.4 ms | 60.7-88.6 ms |
| `INSERT INTO "Task"` | 33.0-34.1 ms | 35.5-37.2 ms |

A position change can no longer be a HOT update, so each renumbered row costs
about 15-25 µs more. That is a few percent of a column renumber, which is
dominated by one round trip per row (about 0.6 ms per row over HTTP).

## Considered and not added

- `Task("projectId", "statusId", "archived", "position", …)` for the column
  reads of create and move: 1.07 → 0.20 ms for a column read and 0.42 → 0.06 ms
  for the next position. That saves about 1 ms per write and would add a second
  position index to maintain on every renumbered row.
- Trigram (pg_trgm GIN) indexes for search: see below. They need
  `CREATE EXTENSION`, which needs a separate decision on database privileges.
- Partial indexes: Prisma 6 cannot represent them in `schema.prisma`, so a
  later `prisma migrate dev` would generate a migration that drops them.
- Scheduler queries (due-date reminders, trash purge, recurring tasks, delivery
  workers) and chat history after the count change already run on existing
  indexes in under 2 ms.
- No index was removed.

## Follow-ups for later P02 changes

Measured on this fixture and left unchanged here (pagination, API shape or
larger query rewrites):

1. **Search** is now the largest statement cost: the task title and
   description and chat content `ILIKE '%term%'` scans take 28-79 ms per query.
   A rolled-back trial with pg_trgm GIN indexes took the description no-match
   query from 78.9 to 0.07 ms and the title query from 39.6 to 8.6 ms. Chat
   content was unchanged because the planner kept the per-channel scan. The
   indexes were 5.6 MB (title), 11 MB (description) and 25 MB (content), built
   in 0.4, 1.6 and 3.0 s. This needs `CREATE EXTENSION pg_trgm` and a write-cost
   check for chat sends.
2. **Cursor pages without LIMIT.** With `cursor` and an ORDER BY on a
   non-unique column, Prisma omits the LIMIT and trims the rows in memory. An
   older chat history page read 12,235 rows to return 50, and the cost grows
   with the channel. The same pattern appears in thread replies, message search,
   bookmarks, shared-with-me, wiki versions and the drive listing. A unique
   tie-breaker (`id`) in the ORDER BY should let the LIMIT through.
3. **Board payload:** 10,789 tasks, 20.9 MB, about 1.05 s for the largest
   project. Per-column cursors (planned).
4. **Task move renumbering** issues one UPDATE per task in the column: 614 ms
   to move a task to the top of a column of about 1,000. A single
   `UPDATE … FROM (VALUES …)` would remove the per-row round trips.
5. **Workspace activity** spends 32-42 ms of its 39-48 ms on an exact
   `COUNT(*)` for the pagination total.
6. **Time report** is unbounded: 17,808 entries, 4.8 MB, about 580 ms for 90
   days.
7. **My tasks** returns all 841 assigned tasks (1.2 MB). Its main query
   sequentially scans Task because the planner prefers a hash join to 1,824
   primary key lookups (24 ms).
8. **Chat channel list** returns every member of every visible channel (620 KB).
   Unread counts still run one COUNT per channel (15 here, about 0.4 ms each).
9. **Other `_count` includes on lists** have the same whole-table aggregate,
   small at this scale: projects list (tasks), wiki spaces (pages), channel and
   DM lists (members), and wiki tree (children).
10. **Notification visibility plans are fragile.** Any index that offers an
    index-only list of a project's task IDs makes the planner hash every
    readable task for each page (above). Restructuring `visibleNotification`
    would remove that sensitivity.
11. API key `lastUsedAt` write throttling was not measured here; the benchmark
    uses access tokens.

## Reproducing

```sh
pnpm --dir packages/backend perf:seed                      # once, into an empty migrated database
ALTER DATABASE <db> SET log_min_duration_statement = 0;    # capture passes only
pnpm --dir packages/backend perf:bench read --out=read.json
pnpm --dir packages/backend perf:bench write --out=write.json
pnpm --dir packages/backend perf:statements <postgres.log> --top=25 --explain=15
```

`perf:bench` needs `BENCH_URL` and the server's `JWT_SECRET`. It signs access
tokens for the fixture users, and it rotates 127.0.0.x source addresses so the
per-address rate limit does not throttle the run.
