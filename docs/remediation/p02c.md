# P02c: text search with trigram indexes

P02a measured search as the largest remaining statement cost (follow-up 1) and
P02b left it open (remaining item 1): every text search filters with Prisma's
`contains` and `mode: "insensitive"`, which PostgreSQL runs as
`"column" ILIKE '%term%'`. A B-tree index cannot serve a pattern that starts
with a wildcard, so each search read the whole table, or every message of the
searched channels. This change adds `pg_trgm` GIN indexes for the searched
columns and keeps every search statement planned for its own term.

## Search paths

| Path | Endpoint | Column | Who sees what | Order |
| --- | --- | --- | --- | --- |
| Global search (command palette): tasks | `GET /api/workspaces/:wid/search?q=` | `Task.title`, then `Task.description` for the rest of `limit` | members: active tasks of their non-archived projects; admins: of every non-archived project | `updatedAt DESC` |
| Global search: wiki pages | same request, 10 pages | `WikiPage.title` | the workspace's pages | `updatedAt DESC` |
| Global search: messages | same request, 10 messages | `ChatMessage.content` | messages of the caller's channels | `createdAt DESC, id DESC` |
| Chat search | `GET /api/chat/:wid/messages/search?q=`, `.../channels/:channelId/messages/search?q=` | `ChatMessage.content` | the caller's channels; one channel the caller may read | `createdAt DESC, id DESC`, cursor pages |
| Drive search | `GET /api/workspaces/:wid/files?search=` | `File.name` | the files the caller may read (`fileReadWhere`) | the listing's sort, cursor pages |
| Task list and board filter | `GET /api/projects/:pid/tasks?search=` (also `view=board`) | `Task.title` | one project, after its access check | the list's sort |
| Project list | `GET /api/workspaces/:wid/projects?search=` | `Project.name` | members: their projects | `createdAt DESC` |

Pickers (members, users to mention or message, labels, task dependencies,
share recipients) filter lists the browser already loaded; they send no search
to the server. The command palette starts searching at two characters.

## Change

- **Migration `20261105180000_search_trigram_indexes`** creates the `pg_trgm`
  extension and GIN `gin_trgm_ops` indexes on `Task.title`,
  `Task.description`, `ChatMessage.content`, `WikiPage.title` and `File.name`
  (`IF NOT EXISTS` throughout). `schema.prisma` declares the same indexes, so
  `prisma migrate diff` from a migrated database to the schema is empty.
  `Project.name` is not indexed: a workspace has few projects, and the
  project list's cost is its `_count` include, not the name filter.
- **Search statements keep a plan per term** (`src/utils/text-search.ts`).
  The global, chat, Drive and task list searches run their filtering
  statements through `withSearchPlans`, a Prisma batch transaction that first
  sets `plan_cache_mode = force_custom_plan` for that transaction only.
- **Queries are unchanged.** The SQL Prisma writes is already a plain
  `"column" ILIKE $n` on the indexed column (`varchar` columns are cast to
  `text`, which the index matches), so no query shape had to change. The
  index returns candidate rows holding every trigram of the term and
  PostgreSQL rechecks the original `ILIKE` on each, so the rows, their order,
  the access conditions and the case handling are those of the table scan.
  The only difference in the SQL a request sends is `BEGIN`,
  `SELECT set_config('plan_cache_mode', 'force_custom_plan', true)` and
  `COMMIT` around each search statement; the task list's page query and count,
  which ran in parallel, now run one after the other in one transaction.

### Why every search statement needs its own plan

Prisma prepares its statements and reuses them per connection. After five
executions PostgreSQL may switch a prepared statement to one generic plan,
made without the parameter values, when its estimated cost is not above the
average of the custom plans. Without trigram indexes that plan scans as the
custom plans do. With them, the generic plan uses the trigram index for every
term, and a term that yields no trigram (one or two letters, which the
command palette sends first) then reads the whole index and rechecks every
row. Measured on one pool connection (`round14-r18b-plancache-*.json`): the
same chat search for `in` took 48 ms for the first five requests and then
1,857 to 1,917 ms; the global search 1.8 to 2.3 s; the task list search 15 ms,
then 87 to 91 ms; Drive 45 ms, then 62 to 70 ms. The main build without the
new indexes already switched these statements to generic plans (9 generic, 5
custom), with no harm because every plan scanned. With `force_custom_plan`
every execution is planned for its term (0 generic plans in the same
sequence), and terms without trigrams keep the scan.

### LIKE semantics are kept, including `%`, `_` and `\`

Prisma 6.19's `contains` does not escape LIKE metacharacters: the search term
is bound as `%term%`. On main and with this change alike, `%` in a term
matches any text, `_` any one character, and `\` escapes the next character
(so `\%` and `\_` are literal, and a term ending in `\` makes the appended `%`
literal: the text must end with `%`). Trigram extraction understands the same
wildcards and escapes and the recheck applies the original pattern, so results
are identical; the integration tests pin this behaviour. Treating `%` and `_`
as literal characters would be a separate, visible behaviour change.

Case handling is `ILIKE`'s: the database's lowercasing (its `LC_CTYPE`) on
both sides. `pg_trgm` lowercases trigrams the same way, and the recheck decides.

## Measurements

Fixture: `scripts/perf/seed.ts` at the default scale, 4 workspaces, 100,000
tasks, 200,000 chat messages, 50,000 files and 20,000 wiki pages (see
`p02a.md`). Actors as in P02a: the workspace admin and the member with the
most assignments in the largest workspace (member of 20 projects and 15
channels). PostgreSQL 16 with default settings. Main is 40a6e43.

Its text comes from a 40-word vocabulary, so any word occurs in a large share
of rows: `warehouse` in 4.5% of task titles and a third of messages, and both
words of `webhook audit` in 12% of messages (1% contain the phrase). That is
the worst case for trigram indexes (many candidates to recheck) and for
searches of common words; real text has far rarer words. Terms: `in` (two
letters, no trigram), `upl` (three letters), `warehouse` (a common word),
`webhook audit` (two common words) and `qzxv` (no match).

Reading the tables:

- **No match** is the biggest change: no candidate row, so the global search
  reads 453 rows instead of 267,806 and its SQL takes 0.3 ms instead of
  155 ms; chat, Drive, task list and board searches drop to well under 1 ms.
  These were full scans that grow with the table (or with the caller's
  channels); now they do not.
- **Three letters and longer terms** read 68% to 98% fewer rows in the
  global, Drive and task list searches, and their SQL takes 29% to 93% less
  time. What the global search still reads is mostly its chat part (below).
- **Two letters** yield no trigram: the custom plan scans exactly as before
  (same rows read, same time within noise).
- **Chat with common words** keeps the per-channel scan: `upl` and `warehouse`
  match a third of the messages, and the planner rightly reads the caller's
  channels. Messages of one channel (`#general`) were already fast and are
  unchanged.
- **Two common words in chat** is the one case that got slower. For
  `webhook audit` the planner estimates few matches (its histogram holds none;
  1% of messages match) and reads the index: 24,523 candidate messages hold
  every trigram of both words, 1,867 the phrase. Searching all of the caller's
  channels is about as fast as before (37 → 40 ms, reading the candidates
  instead of the caller's 44,559 messages, but 8,606 buffers instead of
  1,822), while searching one channel takes 38 ms instead of 14 ms
  (`#general`, 16,171 messages), because the candidates come from every
  channel. This fixture's 40-word vocabulary puts any two words
  together in one message in eight; in natural text such pairs are much rarer,
  and the phrase then behaves like any rare term. A channel-first composite
  index (`btree_gin`) avoided it in a trial (`#general` 3.7 ms) but cannot be
  declared in `schema.prisma` without `prisma migrate diff` reporting it as
  changed on every run, so it is not used.
- **Board search** results are large (every matching task with its relations),
  so the rows read are mostly the relation loads; the filter itself now uses
  the index.
- **Project list** search is unchanged (no index; 50 projects).

**Plans.** Before: a sequential scan of `Task` (title, then description),
`WikiPage` and `File` for every term, and one bitmap scan of
`ChatMessage_channelId_createdAt_idx` per channel of the caller with the
`ILIKE` as a filter. After, for terms with trigrams: a bitmap scan of the
column's `*_trgm_idx` and a recheck, joined to the access conditions as
before (`BitmapAnd` with the project index for the task list). Two-letter
terms keep the old plans; chat searches for common words keep the per-channel
scan.

## Migration

Applied with `prisma migrate deploy` to the seeded fixture (100,000 tasks,
200,000 messages, 49,345 files, 20,000 pages; `round14-r18b-migrate-seed.log`):
6.3 s wall time including CLI start-up, 5.3 s recorded for the migration.
Built one at a time (`round14-r18b-index-build-times.log`):

| Index | Build | Size |
| --- | ---: | ---: |
| `Task_title_trgm_idx` | 0.37 s | 5,624 kB |
| `Task_description_trgm_idx` | 1.58 s | 11 MB |
| `ChatMessage_content_trgm_idx` | 3.38 s | 25 MB |
| `WikiPage_title_trgm_idx` | 0.12 s | 2,672 kB |
| `File_name_trgm_idx` | 0.16 s | 3,352 kB |

47 MB in total, a quarter of the four tables with their other indexes
(185 MB); both grow with the amount of text. `prisma migrate diff` from the
migrated database to `schema.prisma` reports no difference
(`round14-r18b-migrate-diff.log`).

What operators need to know:

- **Extension.** `pg_trgm` is a trusted extension on PostgreSQL 13 and later:
  the database owner, or any role with `CREATE` on the database, can install
  it; no superuser is needed. PostgreSQL 12 and older need a superuser. It is
  part of PostgreSQL's contrib modules, included in the official `postgres`
  images (the bundled Compose database needs nothing) and offered by the
  managed services (Amazon RDS and Aurora, Google Cloud SQL, Supabase, Neon);
  Azure Database for PostgreSQL Flexible Server allows it after `pg_trgm` is
  added to the `azure.extensions` server parameter. Distribution packages may
  ship contrib separately (`postgresql-contrib`, Alpine's
  `postgresqlNN-contrib`).
- **If the application role cannot create it**, an administrator runs
  `CREATE EXTENSION IF NOT EXISTS pg_trgm;` in the Werkyn database before the
  upgrade; the migration then skips it. The migration is one transaction: if
  `CREATE EXTENSION` fails, nothing is created, `prisma migrate deploy` exits
  with P3018 and the container does not start; later deploys stop with P3009
  until the migration is marked rolled back. Install the extension (or grant
  `CREATE` on the database), then run
  `prisma migrate resolve --rolled-back 20261105180000_search_trigram_indexes`
  and deploy again. Both recoveries were run as a non-superuser application
  role (`round14-r18b-migration-privileges.log`).
- **An existing `pg_trgm` in another schema** (Supabase installs extensions in
  `extensions`) is kept; that schema must be on the role's `search_path` for
  `gin_trgm_ops` to resolve.
- **Locks.** Each `CREATE INDEX` holds a SHARE lock on its table while it
  builds: task, message, file and wiki page writes wait, reads do not. The
  shipped entrypoint migrates before the server starts, so nothing waits
  there. Build time grows about linearly with the text indexed.
- **Without downtime**, for instances that migrate while an older version keeps
  writing: create the extension and run the five
  `CREATE INDEX CONCURRENTLY IF NOT EXISTS` statements listed in the migration
  first, one at a time, check `pg_index.indisvalid` for each (drop and rebuild
  one that is not), then upgrade; the migration skips existing indexes. The
  migration itself cannot build concurrently: Prisma runs a script with more
  than one statement as one transaction, where `CONCURRENTLY` is refused, and
  a failed concurrent build leaves an invalid index behind (P02a).

## Tests

`tests/integration/search-trigram.test.mjs` (11 tests) against disposable
PostgreSQL:

- **Migration:** `pg_trgm` is installed; the five indexes exist on the right
  columns with `gin_trgm_ops` and are valid. For every path (global, one
  channel, Drive as member and admin, task list, board), each `ILIKE`
  predicate as Prisma writes it is served by its trigram index.
- **Parity, index against scan:** every path, for member and admin, over 32
  terms (wildcards `%`, `%%`, `_`, `50%`, `e_c`; escapes `\`, `\\`, `h\`, `\%`,
  `\_`; one and two letters; mixed case; non-ASCII `äpfel`, `ÄPF`; phrases;
  no match) returns the same IDs in the same order through a client whose
  plans use the trigram indexes as through one that cannot use them. The
  index client's plans are checked to read a trigram index on every path.
  Filler rows make the scans the planner would otherwise prefer expensive.
- **Results and access:** through the HTTP API, the IDs and order of each path
  equal those computed from the rows with `ILIKE` semantics: tasks only from
  the caller's projects (not archived projects, archived tasks or another
  workspace), title matches before description matches, wiki pages of the
  workspace, messages of the caller's channels (one public channel without
  joining; 403 for a private one), Drive files the caller may read (not
  trashed, not another workspace's) walked through cursor pages, task list
  and board inside the project (403 for a project the member is not in).
  `%`, `_` and `\` keep their LIKE meaning; upper and lower case, ASCII and
  non-ASCII, give the same results.
- **Plans per term:** ten rounds of every search on one connection leave no
  generic plan for any search statement, and `plan_cache_mode` is back to
  `auto` afterwards; a control statement outside `withSearchPlans` does switch
  to a generic plan.

On main (40a6e43) the same file fails 5 of its 11 tests (no extension or
indexes, no trigram plans, generic plans after five executions); the six
result and access tests pass, which shows the results are main's.

Parity on the fixture (`round14-r18b-parity.log`): 36 terms (the test terms
plus fixture words), member and admin, 9 lists each (global search at two
limits, chat in all channels and in `#general`, Drive search in two sorts,
task list pages, board, project list), every cursor and offset page followed:
648 lists, 4,965 responses, 462,112 items. The main build without the indexes
and this change with them returned byte-identical responses (one SHA-256 for
the whole dump).

## Remaining

- Two-letter terms still scan (no trigram); the command palette sends them
  first. A minimum of three characters, or debouncing, is a product decision.
- Chat searches for common words read the caller's channels, as before; the
  `ORDER BY createdAt` over several channels cannot stop early.
- `%` and `_` stay wildcards (unchanged behaviour); escaping them is a
  separate decision.
- Project name search is not indexed (small table).
- The other R18 items in `p02b.md` are unchanged.
