# P01a: route-level code splitting (FE-010)

The production frontend shipped as one 3.17 MB JavaScript file (870 kB gzip).
Every page, including the sign-in form, downloaded and evaluated the wiki
editor (BlockNote, Mantine, Yjs, ProseMirror), the task editor (TipTap), chat
markdown rendering, the emoji list, the admin and backup screens, drive,
time tracking and every other feature before it could render.

## What changed

- **Route components load with their route.** The TanStack Router plugin runs
  with `autoCodeSplitting` (`vite.config.ts`): each route's component (and
  what only it imports) is a separate chunk. Route guards (`beforeLoad`),
  search validation and the route tree stay in the entry, so redirects and
  the workspace membership check run before any route chunk is fetched. The
  root route is never split: the identity boundary that remounts the app on an
  account change, the toaster and the root error screen are in the entry.
- **Heavy panels load when opened.** Inside routes, these load on first use
  through `lazyNamed` (`src/lib/lazy-import.ts`), each behind a Suspense
  fallback:
  - the wiki editor (BlockNote, Mantine, Yjs) when a page opens; the page view
    starts fetching it on mount, in parallel with the page request;
  - the task panel (dialog and animation libraries, subtasks, comments,
    attachments) when a task opens; views that list tasks fetch it once idle.
    The description editor (TipTap) inside it was already split;
  - the drive file preview (PDF, image, video, audio) and the upload progress
    panel (framer-motion);
  - the emoji list (about 300 kB of data) when a picker opens, or when its
    trigger is hovered or focused;
  - the project calendar (FullCalendar) was already split and stays so.
- **Fewer, larger shared chunks for the workspace.** Splitting alone turned the
  workspace layout into dozens of tiny shared files (single icons, UI
  primitives). `scripts/chunking.ts` groups what every signed-in page loads
  anyway into a `workspace` chunk, keeps what the sign-in and shared-link
  pages also need in `common` / `share-common` (so those pages never load the
  workspace chunk), and puts all icons in one `icons` chunk.
- **Preloading.** `defaultPreload: "intent"` (already set) now matters: hovering
  or focusing a link fetches the target route's chunks before the click.
- **Loading UI.** A navigation still waiting for a chunk after a second shows a
  spinner (`defaultPendingComponent`); panels show a skeleton or spinner in
  place.
- **Stale deploy recovery.** After a deploy, a tab still running the previous
  build asks for chunk files that no longer exist. For a route chunk, TanStack
  Router reloads the page once (per chunk URL and tab session); if that does
  not help, or for a panel chunk (where an automatic reload could interrupt
  work), the error boundary shows "A new version of Werkyn is available" with
  a Reload button instead of "Try again", which could not succeed.
  `isChunkLoadError` recognizes the Chromium, Firefox and Safari messages and
  Vite's stylesheet preload failure.

## What did not change

- Route guards, the PR103 identity transition and remount boundary
  (`IdentityBoundary` in the root route), and the PR78/PR105 realtime provider
  placement: `RealtimeProvider` and `WorkspaceRealtime` are still rendered by
  the workspace layout component, now loaded with its chunk.
- Editor save behaviour (PR63/67/102): `WikiPageView` keeps the autosave,
  page lock and conflict handling; only the `WikiEditor` element is loaded
  lazily, with the same props and `key`. `TaskDescription` is unchanged.
- The PR107 single-version guard: Rollup places each module in exactly one
  chunk, so code splitting cannot load two copies of a package. `@tiptap/core`
  and every `prosemirror-*` package are in one shared chunk used by both
  editors.
- Error boundaries: the workspace `ErrorBoundary` and the root error screen
  are where they were; only their content for chunk-load errors changed.
- BlockNote's stylesheet now loads with the wiki editor. It contained two
  unscoped rule groups (ProseMirror tables and a drop-cursor transition); the
  task description editor has no tables, so only the drop-cursor animation in
  that editor differs until the wiki editor has been opened once.

## Size budget (CI)

`scripts/bundle-budget.ts` is a Vite plugin that fails `vite build` (and so
CI's `pnpm build` step) when the production bundle exceeds its budget. It reads
Rollup's chunk graph and checks:

- the entry's JavaScript (what `index.html` loads), and entry CSS;
- the initial JavaScript of the login page and of the workspace dashboard
  (entry plus their route component chunks and everything those import
  statically, not dynamic imports);
- that none of those include packages that must load lazily (BlockNote,
  Mantine, TipTap, ProseMirror, Yjs, FullCalendar, react-markdown/micromark,
  the emoji data, framer-motion);
- that no two chunks import each other.

| Initial resource set | Before, kB gzip | Recorded after, kB gzip | CI limit, kB gzip |
| --- | ---: | ---: | ---: |
| Entry JavaScript | 869.8 | 142.6 | 150 |
| Entry CSS | 47.3 | 13.9 | 15 |

The budgets are the measured sizes below plus about 5%. Raise one only with a
measurement that shows why.

## Recorded measurements

The before build is main `798637f`; the after build has the frontend changes
recorded in `cc084f4`. These measurements were collected on 2026-10-30 before
the later backend query and request-limit changes were incorporated. They are
retained measurements of that frontend comparison, rather than a new browser
benchmark of every subsequent commit.

Both builds used the same real local backend, seeded database and Chromium
fixture. Each result is the median of five cold-context loads at a
1400-by-900 viewport, with fourfold CPU throttling. Slow 4G used 150 ms latency,
1.6 Mbit/s download and 750 kbit/s upload. JavaScript was served uncompressed;
the transfer column therefore differs from the gzip bundle budgets. Requests
were paced beneath the existing per-address rate limit.

| Network | Page | Ready before → after, ms | LCP before → after, ms | JavaScript transferred before → after, kB |
| --- | --- | ---: | ---: | ---: |
| Local | Login | 2,668 → 2,379 | 2,724 → 2,432 | 3,167.9 → 605.8 |
| Local | Dashboard | 900 → 677 | 828 → 596 | 3,167.9 → 1,150.0 |
| Slow 4G | Login | 19,981 → 6,559 | 20,264 → 6,844 | 3,167.9 → 605.8 |
| Slow 4G | Dashboard | 18,074 → 6,108 | 17,800 → 5,828 | 3,167.9 → 1,150.0 |

"Ready" is the sign-in form appearing on login, and the populated project
list appearing on the dashboard. The sign-in page still waits for the same
signed-out refresh probes in both builds. This is a local fixture result, not
a production capacity or cross-browser claim.

The login loads eight JavaScript files. The dashboard's initial graph is
17 JavaScript files; its idle task-panel prefetch brings the observed load to
33 JavaScript files and 49 same-origin requests, compared with 17 requests
before. On Slow 4G, long tasks on the dashboard fell from 599 to 200 ms and
script evaluation from 419 to 188 ms. No 429 response occurred in these paced
runs. Signed-in routes initially load 242–340 kB gzip; opening a wiki editor
brings that page's JavaScript to about 648 kB gzip.

The recorded Chromium production-build smoke passed 15 application flows:
sign-in/dashboard, wiki open/edit/save, emoji picker, task open/description
edit/save, calendar, chat send, Drive PDF/image preview, time reports, settings,
admin backup and link-hover preloading. Three final forced-failure checks
passed for route JavaScript, editor JavaScript and editor CSS, including
recovery with Reload. Existing blocked Google Fonts and signed-out 401 probes
were present in both builds and are recorded separately from application
failures.

Raw measurement JSON, medians, build graph and smoke logs remain in the local
audit evidence under `round13-p01a-*`. Final PR validation identifies the exact
tested head separately from these retained browser measurements.

## Remaining scope

The backend's global request limiter and zero-age asset caching are handled by
the separate static-asset delivery change. Code splitting increases cold-load
request counts, so this frontend change alone does not establish that repeated
navigation avoids that limiter. Missing asset requests can also receive the
current SPA fallback's HTML until that serving policy is changed.

Virtualizing long task, board and Drive lists remains the rest of P01. Mobile,
other browsers and the broader release matrix still need their own checks.
