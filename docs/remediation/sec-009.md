# Backup export asset authorization

Workspace backup export now receives the authenticated actor and checks current
workspace ADMIN membership in the export service, including before each asset.
Embedded wiki JSON strings are references, not permission to open storage. The
existing nested media, link and textual reference formats remain supported.

Local `/storage/...` references first resolve the exact complete raw storage
identity, including accepted literal `%2f`, `%00`, `?` and `#` filename text.
Separately, a URI pathname and its at-most-once-decoded spelling may be considered.
Each candidate is authorized independently and is never decoded later by storage.
Only an interpretation containing actual dot/empty path segments, separators within
a decoded segment, backslashes or controls is discarded; a safe literal filename
is not lost because a different URI interpretation is unsafe. Raw existing paths
take precedence over URI interpretations. Real query/fragment suffixes still work
through authorized pathname candidates, and never grant access by themselves.
Any forbidden Drive identity in any safe candidate rejects the entire ambiguous
reference before stat or read, so another spelling cannot bypass a denied identity.
Authorization resolves the resource before any storage read:

- All matching Drive original/thumbnail records are checked first. Each must be
  an active file in the exported workspace and pass the existing current file
  access policy. File records, rather than old storage prefixes, establish their
  current workspace after moves. Foreign, trashed, duplicate foreign identities
  and invalid team relationships cannot fall back to an upload namespace.
- An unrecorded `<workspace>/uploads/wiki/<space>/...` asset requires a live wiki
  space belonging to that workspace. It may be referenced from another selected
  space because the export actor is a current workspace ADMIN. The explicit
  `<workspace>/uploads/wiki/imports/...` restore namespace is also eligible.
- Public avatars require an `avatars/<user>/...` or matching workspace upload
  avatar namespace, the exact current profile URL, and current membership of
  that user in the exported workspace. A mutable profile URL alone grants no
  access to arbitrary paths.

Other unrecorded general/legacy uploads and private paths have no established
workspace identity and are omitted. A legacy path with a valid current Drive
record remains eligible regardless of its old directory layout. Legacy
`/uploads/...` URLs and unrelated URL schemes are not newly followed.

Only successfully read authorized assets receive ZIP entries and URL rewrites.
Denied or unreadable references remain unchanged in backup JSON. Rewriting uses
complete extracted URL tokens, so an eligible prefix cannot rewrite a denied or
missing longer reference. `includeFiles: false` performs no asset reads or rewrites.
Export performs no database writes; the restore algorithm and its rewrite helper
are unchanged.

Run the bounded HTTP/PostgreSQL regressions against a migrated disposable database:

```sh
pnpm --filter @pm/shared build
TEST_DATABASE_URL=<disposable-url> pnpm --filter @pm/backend exec node --import tsx --test tests/integration/backup-asset-authorization.test.mjs
```

The twelve cases use benign local markers and inspect actual ZIP bytes, metadata,
storage read calls and database state. They cover valid wiki/import/Drive/avatar
assets, current and legacy paths, nested/text/link references, denied and missing
references, current workspace/role changes, immutable file paths, ambiguous records,
canonical URLs and `includeFiles: false`. The filename compatibility case uses
actual authenticated wiki uploads and Drive upload streams with twelve benign
percent-bearing and URL-delimiter extensions, checks raw and encoded references,
and verifies exact ZIP bytes/rewrites without database changes during export. It
also checks raw-identity precedence over an existing allowed URI prefix and denies
ambiguous references before stats/reads when an alternative identity is forbidden.

This fixes SEC-009's export resource boundary. It does not establish complete
disaster recovery or fix B03 basename collisions, restore completeness/rollback,
SEC-010 resource/streaming limits, symlink lifecycle, or serialized concurrent
membership/resource revocation. Current authority is checked before operations;
this change does not lock permission changes against an already admitted read.
