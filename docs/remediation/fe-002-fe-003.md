# FE-002 / FE-003: frontend identity transitions and the API base

## Identity transitions (FE-002)

The frontend held data for the signed-in account in several places that
outlived it: the React Query cache (profile, notifications, private file
lists, all under keys without a user id), pending mutations and their
optimistic rollbacks, the realtime socket, route contexts such as the
workspace membership, component state, and recently opened files in
`localStorage`. Signing out or switching accounts cleared none of them. A
refresh that finished after a sign-out also re-applied its result, so a slow
refresh, or a refresh announced by another tab, could sign the previous
account back in.

### One transition

`useAuthStore` runs `changeIdentity` (`lib/identity.ts`) whenever its user id
changes, from any source: sign-in, sign-out, a refresh that reports a
different account, a failed refresh, or another tab's announcement. A change
of token for the same account is not a transition. Each transition:

1. advances the identity generation;
2. aborts every `api` request still in flight, rejecting it with
   `IdentityChangedError` (an `ApiError` with status 409). The rejection is
   immediate even if the network layer ignores the abort, and ky does not
   retry it. A response that arrives anyway is rejected by the response hook;
3. runs the registered resets:
   - the React Query client removes every query and mutation (removing a query
     cancels its fetch);
   - the router drops cached matches and re-runs every route guard, so route
     contexts are recomputed for the new account;
   - an open realtime socket is closed at once; the provider opens a new one
     for the new account;
   - per-account stores switch to the new account (emoji usage);
   - toasts about the previous account are dismissed.

Mutations belong to the identity that started them. After a transition their
`onMutate`, `onSuccess`, `onError` and `onSettled` options are skipped (this
covers optimistic rollbacks), the default error toast is not shown, and a
mutation that had not sent its request yet (paused offline, or queued) fails
instead of running as the new account. The `useMutation` observers of pending
mutations are reset at the transition: they report idle and detach, so
callbacks passed to `mutate(variables, callbacks)` never run either.

Requests are bound to the identity with `AbortSignal.any`. Browsers without it
fall back to an equivalent combined signal.

Drive batches belong to the account that started them. Once the signed-in
account changes, queued uploads are not started, and bulk trash or move
requests not yet sent are not sent.

`IdentityBoundary`, around the routed UI, remounts everything below it each
time an account is left, and renders nothing until that transition's resets
(the route guards) have finished. No component state, open dialog or route
context created for the previous account renders for the next one. Signing in
from the signed-out state does not remount.

Other modules register their own resets with
`onIdentityChange(listener)`. The listener receives
`{ generation, previousUserId, userId }` and may return a promise.

### Generation and epoch guards

A refresh records the identity generation and the cross-tab epoch when it
starts. If either has changed when it finishes, its result is discarded. A 401
for a request that carried an access token triggers a refresh. If the identity
changes during that refresh, the request is rejected and not replayed. If the
refresh fails, `expireSession(generation)` signs out only if the identity is
still the one that failed.

Tabs announce identity changes over the `pm-auth` BroadcastChannel. Each
message carries an epoch (a time and the sending tab's id). A tab ignores a
message older than the newest change it knows of. The epoch is dated as
follows:

- sign-in and sign-out are dated by the user's action;
- a refresh that reports a different account is dated by when its request was
  sent, so it cannot outrank a sign-out made while it was in flight;
- a failed refresh announces a sign-out only just newer than the session that
  failed, so tabs that have since moved to a later sign-in ignore it.

Messages from tabs running an earlier build carry no epoch, so they cannot be
ordered against a sign-out. They may sign this tab out, or renew the token of
the account already signed in here. They never sign an account in or switch
accounts.

A page that is still loading treats any sign-out it sees, its own or one
announced by another tab, as final: it stops retrying and finishes signed out.
A refresh started without a session first waits, at most 10 seconds, for
cookie-setting requests still running in any tab (see "Sign-out"). A tab
opened while another tab's revocation is in flight therefore cannot restore
the session.

### Sign-out

`logout()` clears local state and announces the sign-out at once, before any
network call. It then revokes the session on the server and returns a promise
that settles after at most 10 seconds and never rejects. The revocation
requests use `keepalive`, so they still reach the server if the tab is closed
or reloaded immediately.

`/login` and `/register` redirect a signed-in user, to the invitation when an
`inviteToken` is present. Signing in over a signed-in account would switch
accounts without signing the first one out.

The server accepts a sign-out only with a current access token. If the stored
token has expired, the client exchanges the cookie for a new token. It does
not apply that token to the store. It signs out with it, unless the cookie now
belongs to another account. A 409 (another tab has just rotated the cookie) or
a 503 (session busy) is retried with the browser's current cookie, within the
deadline. These fallback steps stop as soon as another tab announces a newer
sign-in or sign-out, so a sign-out cannot end a session started elsewhere
while it runs.

A sign-out aborts this tab's refresh requests still in flight. The session
they would renew is being revoked, and their response could otherwise set a
cookie after the next sign-in's cookie.

While a refresh or a sign-out request is in flight, its tab records a
deadline in `localStorage` (`pm-auth-busy:<tab>`). A sign-in (password,
registration or SSO) in any tab first waits, through `whenLoggedOut()`, until
none of these remain or 10 seconds have passed. This way a late cookie-setting
or cookie-clearing response cannot replace the new session's cookie. A marker
left by a tab that closed mid-request expires at its deadline and is removed.

A 401 on a request sent while signed out (wrong password, public pages) no
longer triggers a refresh or a sign-out. Before this change it signed out
every other tab.

### Per-account local storage

- Recently opened files are stored under
  `drive-recent:<userId>:<workspaceId>`.
- Emoji usage is stored under `pm-emoji:<userId>`.
- Data stored by earlier builds without an owner (`drive-recent-<workspaceId>`
  and `pm-emoji`) is removed rather than shown to the next account.
- The theme and sidebar state are browser preferences and stay shared.
- Unsaved editor drafts were already kept per author by the autosave queues.

## API base (FE-003)

`lib/api-url.ts` builds every backend URL: ky's prefix, session refresh and
logout, the SSO redirect, uploads, downloads, previews, backup export, public
share downloads and the WebSocket. `VITE_API_BASE_URL` may be:

- empty (`/api`);
- a path on the frontend origin (`/custom/api`);
- an absolute URL (`https://api.example.com/api`).

Trailing slashes are ignored. The realtime URL switches to `ws:` or `wss:` on
the API's host.

The backend still issues the refresh cookie with `Path=/api/auth` and serves
its routes under `/api`.

- With a custom relative base, the reverse proxy must map `/custom/api` to the
  backend's `/api` and rewrite the cookie path (for example nginx
  `proxy_cookie_path /api/ /custom/api/`). Otherwise the browser does not send
  the cookie to `/custom/api/auth/refresh`.
- A cross-origin absolute base needs HTTPS, `COOKIE_SAMESITE=none` with
  `COOKIE_SECURE=true` (or a same-site subdomain with `COOKIE_DOMAIN`), the
  frontend origin in `CORS_ORIGIN`, and browser third-party-cookie support.
