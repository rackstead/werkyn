# Workspace admission through invitations

Registration with an invite token previously had its own join path. It ignored
disabled invites, allowed email domains, member limits and required approval,
did not require the restricted address to be verified, and increased the
invitation's use count without a guard, so parallel signups could exceed a
single-use invitation. Authenticated acceptance checked most settings but not
approval or email ownership, counted members without serializing different
invitations, and treated legacy zero limits as unlimited.

## One admission gate

`admitWithInvite` (`packages/backend/src/modules/invites/admission.service.ts`)
serves both registration and `POST /api/invites/:token/accept`. Administrator
approval uses the same decision. Under the workspace lock it reloads the
invitation, the account's email and verification flag, the existing membership
and the settings (or their defaults when no settings row exists), then:

1. an existing member is reported as joined without a role change or a use;
2. denies when invites are disabled, the invitation is expired (`expiresAt` at
   or before the check), used up (`maxUses` is compared explicitly, so a legacy
   `0` denies), restricted to another email, or the domain is not allowed
   (exact, case-insensitive; legacy entries are normalized when compared);
3. requires a verified address when the invitation names an email or the
   workspace restricts domains (`verification_required`). Open invitations keep
   admitting unverified accounts, and the first local account keeps its
   automatic verification;
4. when approval is required, creates or reuses the applicant's single pending
   request for that workspace (`approval_pending`). The request is bound to the
   invitation it was made through and reserves no seat or use. Asking again
   through the same invitation keeps it; asking through a different invitation
   replaces it with a new request id, so an admin decision on the request they
   reviewed (and the role it showed) cannot apply to the other invitation;
5. otherwise checks the member limit against actual membership rows, increments
   the invitation's use count with a guarded update, removes any pending
   request and creates the membership with the invitation's role, in one
   transaction. A failure at any step commits none of them.

Registration still commits the account first (the PR51 bootstrap/account
transaction is unchanged) and runs admission in a separate transaction. Its
response carries `data.admission` with the result; an unexpected admission
failure is reported as `unavailable` rather than hidden, and the account stays
usable. Verification mail is sent after admission, and only when verification
is what blocks joining does its link carry `?invite=<token>`. Resending
verification accepts an optional `inviteToken` and includes it only when that
invitation exists. The verification page then offers a link to the fixed
`/invite/:token` route; it never follows an arbitrary URL and never signs in or
joins on its own.

## Pending requests and review

`WorkspaceAdmissionRequest` holds pending requests only: approval and rejection
delete the row. A composite foreign key to `(WorkspaceInvite.id, workspaceId)`
makes it impossible to pair one workspace with another workspace's invitation;
revoking the invitation, deleting the workspace or deleting the user removes the
request. A pending row is not a membership and grants no workspace, project,
file, upload or realtime access.

Admins list requests with `GET /api/workspaces/:wid/admission-requests` and
decide with `POST /api/workspaces/:wid/admission-requests/:requestId/approve` or
`/reject`. Inside the locked transaction the service checks again that the
caller is still an ADMIN of that workspace, that the request belongs to it (a
foreign id is a 404 with no change), and repeats every invitation, applicant
and policy check. A refused approval changes nothing; repeated or competing
decisions on the same request have one effect and the other caller gets 404.

`GET /api/invites/:token/admission` evaluates the same rules read-only for the
signed-in account. It reports a current refusal (including a full workspace),
required verification, membership or the pending request. When approval is
required and there is neither a membership nor a request it reports
`not_pending`; when approval is not required (for example, it was turned off
while a request waited) and every rule admits the account it reports `ready`.
The invite page's status check uses it, so checking never creates a request or
revives one an admin declined; asking again or joining is an explicit
acceptance.

## Lock protocol

`packages/backend/src/utils/workspace-lock.ts` is the shared helper:

- `lockWorkspace(tx, workspaceId): Promise<boolean>` locks one Workspace row with
  `SELECT ... FOR NO KEY UPDATE` and reports whether it exists;
- `lockWorkspaces(tx, workspaceIds): Promise<Set<string>>` locks several rows in
  ascending id order;
- `withWorkspaceLock(prisma, workspaceId, work, { onMissing })` runs `work` in a
  READ COMMITTED transaction after taking the lock, throws `NotFoundError` (or
  returns `onMissing()`) for a missing workspace and maps abandoned
  transactions (P2034/P2028) to a retryable 409.

Order: Workspace rows first (ascending id when several), then the invitation,
pending request and member rows. `FOR NO KEY UPDATE` excludes every other lock
holder, workspace deletion and workspace updates, but not the key-share locks of
foreign-key checks, so unrelated inserts in the workspace are not blocked. READ
COMMITTED makes every statement after the wait read the previous holder's
committed changes.

Participants: registration admission, invitation acceptance, approval,
rejection, settings `PATCH` (which also rechecks ADMIN and normalizes domains),
invitation creation and revocation (both recheck ADMIN), member role changes and
member removal (which now recheck the acting ADMIN under the lock and use READ
COMMITTED instead of SERIALIZABLE, keeping the last-admin rules). Workspace
deletion takes the same row lock implicitly. Creating a new workspace with its
owner is unchanged. The settings `GET` still creates a default row if none exists;
that row means the same as no row. Seeding is not a runtime writer and must not
run concurrently with the application.

## Browser behavior

The invite page shows verification, pending approval, refusal and joined states
separately. After a joined result it stores the returned memberships for the
same signed-in account, shares them with that account's other open tabs (tabs
signed in as another account ignore them) and only then opens the workspace; a
response for an account that is no longer signed in changes nothing. A refusal
clears only the requesting account's earlier pending state; busy, server and
network errors keep it. When the public preview fails (for example, an expired
invite) a signed-in account can still check its access, so an existing member
is admitted. Sign-up routes to the workspace when joined
and otherwise back to the invitation. The invite token is kept when switching
between sign-in and sign-up, on the first-account form and through SSO using the
existing sanitized return URL. Admins see join requests above the invitation
list, with approve and reject actions.

## Tests

`packages/backend/tests/integration/workspace-admission.test.mjs` runs the real
application against PostgreSQL with a local mail stub (Ethereal and SMTP fail the
test). It covers registration and acceptance for every setting and invitation
state, role variants, verified, unverified and OIDC-style profiles, idempotent
retries, approval/rejection, scoped queues and foreign ids, live rechecks, forced
membership insert failures, concurrent last-use and last-seat races, competing
decisions, approval racing a request through a higher-role invitation (both
queue orders forced, plus unordered rounds), status after approval is turned off
or the workspace fills, the public preview limits, policy changes committed
while an admission waits, and writers that wait behind an in-flight admission. Concurrency fixtures use a separate
two-connection control pool and observe real lock waiters in `pg_stat_activity`
before releasing. The application pool defaults to five connections and
accepts any explicit `connection_limit` of four or more; at most two application
transactions wait on locks at once. Frontend tests cover the invite
states, the account-switch and same-account sign-in-again cases, registration
routing, the verification link and the review queue.

```sh
TEST_DATABASE_URL="$DISPOSABLE_DATABASE_URL" pnpm --filter @pm/backend exec node --import tsx --test --test-concurrency=1 tests/integration/workspace-admission.test.mjs
pnpm --dir packages/frontend exec vitest run src/routes/-invite-admission.test.tsx src/features/admin/components/admission-requests.test.tsx
```

## Not covered

Refresh-token family atomicity (SEC-011), wider session/cache isolation (B09)
and mail transport behavior (SEC-015) are separate. The public invite preview
applies the same expiry (`expiresAt <= now`) and use limits (a legacy zero limit
is used up) as the gate, but still reveals only the workspace and role. There is no history of decisions and no notification to the
applicant when a request is approved; they see the result when they open the
invitation again.
