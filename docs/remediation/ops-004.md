# Non-root container and the locked Prisma CLI

The image used to run the migrations, the server and Dex as root. They now run as the
unprivileged user `werkyn`, uid and gid 10001, which is the image's default user
(`USER 10001:10001`). The application files stay owned by root and read-only to that
user. Only the storage directory (`/app/storage`) and the Dex directory (`/app/data/dex`)
belong to it, and a new named volume mounted there takes that ownership from the image.
`docker exec werkyn-app id` now prints `uid=10001(werkyn) gid=10001(werkyn)`.

Dex is started by the server, so it runs as `werkyn` as well. `dex-config.yaml`, which
holds the Dex client secret and, with PostgreSQL storage, the database password, is still
written with mode 0600. A new Dex directory is mode 0700; an existing one keeps its mode.

## The Prisma CLI

The image used to install the Prisma CLI globally with `pnpm add -g prisma@^6.3.1`, which
took the newest 6.x release at build time instead of the version in `pnpm-lock.yaml`. An
image built from `c1b1560` on 2026-10-29 got Prisma 6.19.3, while the lockfile and the
generated client are 6.19.2. The lockfile resolves the optional `prisma` peer of
`@prisma/client` to the locked CLI, so the production install already contains it, and
the build links that copy to `/usr/local/bin/prisma`. The build fails if the CLI is
missing or its version differs from the lockfile or from `@prisma/client`. Every `pnpm install` in the image uses `--frozen-lockfile`.
`CHECKPOINT_DISABLE=1` stops the CLI's update check, so a start needs no network
access beyond the database.

The base images are pinned by digest as well as tag. To update one, change both
together, for example with the digest printed by
`docker buildx imagetools inspect node:20-alpine`.

## Upgrading an installation created by an older image

Older images wrote the volumes as root, and `werkyn` cannot change those files. Back up
the database and the storage volume first, as for any upgrade. Then follow the case that
matches your installation.

### With the bundled `docker-compose.yml`

```bash
git pull
docker compose up -d --build
```

Nothing else is needed. Before the app starts, the new one-off `werkyn-permissions`
service starts the same image as root, gives every file and directory owned by root in
the two volumes to `werkyn`, prints how many it changed, and exits. The app waits for it
to succeed. It runs with no network, a read-only root filesystem and only the `CHOWN` and
`DAC_READ_SEARCH` capabilities, and runs again on every `docker compose up`, which costs one directory
scan once nothing is left to change. To check the result:

```bash
docker compose logs werkyn-permissions   # "Giving N root-owned entries under ... to werkyn"
docker exec werkyn-app id                # uid=10001(werkyn) gid=10001(werkyn)
curl -fsS http://localhost:3000/api/ready
```

If you keep your own Compose file, copy the `werkyn-permissions` service and the
`depends_on` entry into it, or hand the files over once before starting:

```bash
docker compose run --rm --no-deps --user 0 werkyn fix-permissions
```

### With `docker run`

Hand the files over once, with the same volumes and the same `STORAGE_DIR` and
`DEX_CONFIG_DIR` (if you set them) as the app container:

```bash
docker run --rm --user 0 \
  -v werkyn-storage:/app/storage -v werkyn-dex-data:/app/data/dex \
  <image> fix-permissions
```

Then start the container as usual, without `--user`. Starting the app container itself
with `--user 0` also works once: the entrypoint hands the files over, then runs the
migrations, the server and Dex as `werkyn` (`docker exec` then defaults to root, because
it uses the container's configured user). Prefer the one-off command above, and do not
keep `--user 0` as the normal start.

A non-root start stops before migrating, with instructions, when a data directory is not
writable or holds anything owned by root, including a volume root or `lost+found` that
root created, even if it is group-writable.

### Host directories (bind mounts), other user IDs and Kubernetes

The handover (`werkyn-permissions`, `fix-permissions` or a `--user 0` start) always gives
root-owned entries to `werkyn`, uid 10001, and changes nothing else.

- To run as `werkyn`, give a host directory and everything in it to 10001:
  `sudo chown -Rh 10001:10001 /srv/werkyn/storage /srv/werkyn/dex`.
- To run as another user (`user: "1000:1000"`), first give the directories and all
  existing data, including files an older image wrote as root, to that user:
  `sudo chown -Rh 1000:1000 /srv/werkyn/storage /srv/werkyn/dex`. Do not use
  `werkyn-permissions` or `fix-permissions` with another user: they give older files to
  10001, which that user cannot write. Remove the service and its `depends_on` entry from
  your Compose file.
- On Kubernetes, the numeric `USER` lets `runAsNonRoot: true` verify the user. `fsGroup`
  alone is not enough, because the volume root and `lost+found` stay owned by root and
  the start check refuses them. Run `fix-permissions` in an init container as root, with
  the same volume mounts and the same `STORAGE_DIR` and `DEX_CONFIG_DIR` as the app.

### Safety of the handover

It acts only on the directories named by `STORAGE_DIR` and `DEX_CONFIG_DIR` (default
`/app/storage` and `/app/data/dex`), and only when the directory, with any symbolic link
resolved, lies under `/app/storage` or `/app/data`, where the volumes are mounted. A
directory configured elsewhere is left unchanged with a message: give it to uid 10001
yourself (for example `docker run --rm --user 0 -v <volume>:/data --entrypoint chown
<image> -Rh 10001:10001 /data`), or mount the volume under one of those paths. It changes
only entries owned by uid 0 and never follows symbolic links inside the directory: a link
is changed itself, so a link inside a volume cannot give away a file outside it. It does
not walk other mounts inside the directory, including bind mounts from the same
filesystem, and says so; hand such a mount over separately (the start check still refuses
root-owned entries in it). It
skips root-owned files with more than one hard link, since another link may lie outside
the directory, and reports how many it skipped; check and chown those yourself. It never
changes file modes. A downgrade to an older image keeps working, because root can write
the files; the next upgrade hands any new root-owned files over again.
