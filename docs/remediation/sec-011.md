# Refresh-token families

Refresh rotation previously deleted the presented token in one transaction and
created its successor afterwards, outside it. Reuse detection deleted the
family's tokens without any lock or durable record, so a replayed token could
revoke a family while a legitimate rotation was between those two steps, and
that rotation then created a valid successor in the revoked family. Logout,
password change, password reset and the session replacement on password login
had the same gap: each deleted the tokens it could see, and a successor created
a moment later survived. Two simultaneous refreshes of one cookie failed with a
500 (unique or missing-row errors), and the rotated-token check could then
revoke the session of a user who merely had two tabs open.

## Families

`RefreshTokenFamily` (migration `20261029090000_add_refresh_token_families`) is
one sign-in session: `id`, `userId`, `createdAt`, `revokedAt` and
`revokedReason` (`reuse`, `logout`, `login`, `password_change`,
`password_reset`). Every `RefreshToken` references its family through a
composite foreign key on `(familyId, userId)`, so a token can neither exist
without a family nor belong to another user's family. Deleting a user deletes
its families and tokens. `RotatedRefreshToken` records keep their `familyId`
without a foreign key; a record whose family no longer exists is rejected with
401 and nothing else.

`packages/backend/src/modules/auth/refresh-sessions.ts` owns every write:

- `createRefreshSession` creates a family and its first token in one
  transaction (registration, password login and OIDC sign-in) while holding
  the user row `FOR SHARE`. Password change and reset update that row before
  revoking every family, so a session being created concurrently either
  commits first and is revoked, or waits until the change has committed.
- `rotateRefreshToken` runs one READ COMMITTED transaction: it finds the
  presented token's family, locks the family row (`SELECT ... FOR UPDATE`),
  rejects a missing or revoked family, re-reads the token under the lock and
  then, in the same transaction, records the rotated hash, deletes the old token
  and creates the successor. An expired token (`expiresAt` at or before now) is
  deleted and rejected. Outcomes are returned rather than thrown so that a
  revocation or expired-token deletion commits.
- `revokeRefreshFamily` (logout) and `revokeUserRefreshSessions` (password
  login, password change and reset) take the same row locks, set `revokedAt`
  once and delete the family's active tokens. User-wide revocation locks the
  user's families in id order.

These transactions have a deliberate budget (`maxWait` 5 s, `timeout` 10 s;
Prisma's default timeout is 5 s). Prisma's timeout does not cancel a statement
that is already waiting on a lock, so each transaction also starts with
`SET LOCAL lock_timeout` of 8 s: any single lock wait fails with 55P03 within
that time instead of lasting as long as the holder keeps the lock. A rotation
that hits the lock timeout or the transaction budget is rolled back and
answered 503 ("busy") without waiting for the holder, and the client retries
the same cookie; nothing was minted or revoked. Logout and password login use
the same cap; for them a lock timeout is an error response (their changes roll
back) rather than a 503. Password reset and password change use it too and
answer a retryable 503 (see `sec-026.md` and `sec-027.md`).

Because every mint and every revocation of a family holds its row lock, a
revocation that arrives during a rotation waits for it to commit and then
deletes its successor, and a rotation that arrives after a revocation sees
`revokedAt` and mints nothing. No interleaving leaves an active token in a
revoked family.

Password login keeps its existing behavior of replacing the user's other
sessions. It now does so in one transaction with the new session, holding the
user row `FOR NO KEY UPDATE` and re-checking the verified password hash: a
concurrent password change or reset either commits first (the login is
rejected with 401) or waits and then revokes the login's new family.
Concurrent password logins run one after another, so only the last session
remains even on an account with no family to lock yet. The lock does not
conflict with the `KEY SHARE` checks of an in-flight rotation. Password change
takes the same lock and re-checks the hash its current password was verified
against in the same way, so a change that overlaps a reset or another change
cannot overwrite it (see `sec-027.md`).

## Concurrent use policy

Tabs share one refresh cookie. Within a tab the store already deduplicates
refreshes, but two tabs can send the same cookie at once (simultaneous page
loads, or every tab's access token expiring together). The rules are:

| Presented token                                                           | Result                                       |
| ------------------------------------------------------------------------- | -------------------------------------------- |
| Active, family not revoked, not expired                                   | 200, one successor (`Set-Cookie`)            |
| Rotated less than 30 s ago (`REFRESH_REUSE_GRACE_MS`), family not revoked | 409, nothing minted or revoked               |
| Family lock held past the lock timeout or the transaction budget          | 503 (busy), nothing committed                |
| Rotated 30 s ago or more                                                  | 401, whole family revoked (`reuse`)          |
| Any token of a revoked or missing family                                  | 401                                          |
| Expired active token                                                      | 401 (`Refresh token expired`), token deleted |
| Unknown                                                                   | 401                                          |

The grace window never mints: a replayed token gets nothing either way, and
reuse is detected once the window has passed. A stolen token used first by an
attacker still wins one successor, as with any rotation scheme; the victim's
next use of the old token after the window, or the victim's next password
login, revokes it. OIDC sign-in does not end other sessions, so it does not
revoke such a family.

The frontend (`packages/frontend/src/stores/auth-store.ts`) treats 409 as
"another tab won". It returns success as soon as the winning tab's
`BroadcastChannel` message delivers the new access token, and otherwise retries
with the browser's (by then replaced) cookie after 250, 500, 1000, 2000, 4000
and 6000 ms. A busy 503 is retried on the same schedule. A run of 409s is
tracked across refresh calls, because hydration repeats them: 15 s after the
first 409 the winning response is treated as lost and the old cookie is not
sent again until another tab broadcasts a refresh or this tab signs in. The old
cookie therefore stops being presented well inside the 30 s window, after which
the server would treat it as reuse. A 409 for a request sent before a newer
refresh landed, and a 503, do not start or extend that run. If the retries end
without success, the refresh fails and the tab signs out, as before.
(That forced logout carries the expired access token, so the server rejects it
before revoking anything; the next password login revokes the family.)

Logout revokes the cookie's whole family, whether the presented token is the
current one or an already rotated one; an unknown cookie is a no-op (204). The
response always clears the cookie. A database error during revocation is no
longer swallowed: it is reported (500) after the cookie is cleared, and the
family stays active until a later logout, reuse revocation, password login or
expiry. The endpoint still requires an access token.

## Credentials outside the family

Credential policy:

- Access tokens are HS256 JWTs valid for 15 minutes. They carry `sid`, the
  id of the family they were issued for. Every HTTP authentication checks
  the account and its owned, unrevoked family with an unexpired current
  refresh token. Logout, password change, password reset, replacement login
  and reuse revocation therefore refuse subsequent protected requests with
  `401`. Operational lookup failures return a safe `503`; programming and
  schema/query faults return a generic `500`. Legacy tokens without `sid`
  retain only their JWT expiry grace (at most 15 minutes after upgrading from
  a version that issued them); malformed present claims are refused.
  See `http-session-validity.md`. WebSocket authentication checks the family,
  and revoking a family closes its sockets (see `dat-006.md`).
- Personal API keys (`wk_...`) are looked up on every HTTP request. Revocation
  and expiry take effect on the next request. They are independent durable
  credentials: logout, password change, password reset and refresh-family
  revocation do not revoke them; the owner revokes them in Settings. Deleting
  the user deletes them.
- Refresh tokens expire seven days after their own issue, so an active session
  slides indefinitely while it keeps refreshing. There is no absolute session
  lifetime.

## Validation

`packages/backend/tests/integration/refresh-family-atomicity.test.mjs` runs the
application against PostgreSQL with separate actor and control connection
pools. Barriers are real database locks observed through `pg_stat_activity`: a
row lock on the presented token (any rotation must change that row), and a
trigger that makes the INSERT of a family's (or user's) next token wait on an
advisory lock held by the control transaction. The tests cover two overlapping
refreshes (one 200, one 409, one active token), a four-request burst, reuse
revocation racing an in-flight rotation, logout, password change, password
reset and login each racing an in-flight rotation, a reset racing a password
login with the old password and an OIDC-path session creation,
revocation/refresh storms, the grace boundary on both sides, expiry on both
sides, a family lock held past Prisma's default budget and one held past the
configured budget, logout that fails after clearing the cookie, logout scope,
the composite foreign key and cleanup. On the previous code 15 of the first 16
fail, including surviving successors after reuse, logout, password change,
reset and login. `auth-store-refresh.test.ts` covers the frontend retry,
including a broadcast arriving after five seconds and hydration that stops
sending a superseded cookie 15 s after the first 409.

Cleanup (`cleanupExpiredTokensAndAttempts`) removes families that have no
tokens left, a week after their revocation or, if never revoked, a week after
creation.

## Out of scope

- Canceling HTTP work already authorized before a concurrent revocation.
  Subsequent authentication checks read committed family state without a
  revocation cache (`http-session-validity.md`).
- Revoking API keys on password change or reset.
- An absolute session lifetime.
- Password-reset token double use: fixed separately; the reset transaction now
  locks the user row and claims the token before changing the password (see
  `sec-026.md`). Reset and change invalidate unused reset links before family
  revocation; their busy/rollback paths preserve those links.
