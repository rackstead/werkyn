# Backup restore archive budget

Backup preview and restore used to pass an uploaded ZIP straight to adm-zip.
When adm-zip reads an archive, it creates a folder entry for every parent path
of every entry name, so the memory it needs grows with the square of a name's
depth. A 120 KB upload with one entry name nested 30,000 levels deep aborted
the whole Node process, which took the server down for every workspace. The
route requires workspace ADMIN, but any signed-in user can create a workspace
and is its ADMIN. adm-zip also keeps about 9 KiB of heap for every entry and implied
folder, so archives with many tiny entries were expensive too. Malformed
archives answered with a 500, and outside production the response quoted
adm-zip's message, which can contain an entry name.

`backup-archive.ts` now reads the archive's end record, central directory and
local headers before adm-zip sees the buffer. It inflates nothing at this
stage, and it refuses the archive unless all of these hold:

| Limit | Value | Largest measured export |
|---|---|---|
| Entries, counting the parent folders adm-zip adds | 10,000 | 1,514 |
| Entry name length | 1,024 bytes | 53 bytes |
| Path segments per name, split on `/` or `\` | 16 | 2 |
| Declared uncompressed size of one entry | 512 MiB | 16.4 MiB (`backup.json`; SEC-028 limits it to 32 MiB) |
| Declared uncompressed size of all entries | 1 GiB | 273 MiB |

The measured export is a realistic large workspace built through the real
routes and exported over HTTP:

- 4 projects with 6,000 tasks, 12,000 subtasks and 6,000 comments;
- 2 wiki spaces with 500 pages;
- 1,512 embedded images totalling 256 MiB, including the percent, query,
  fragment and non-ASCII upload names covered by SEC-009.

The ZIP was 259 MiB. Exporting and restoring it in one process peaked at 1,760
MiB RSS, because both directions hold the whole archive in memory. The 1 GiB
total is therefore about as much as a server that can export a workspace can
also restore. The per-entry limit matches the longest string V8 can create
(about 512 MiB). It does not bound the cost of parsing `backup.json`, which
can need about 100 bytes of heap per byte. `backup.json` therefore has its own
limits, checked before it is inflated (see `sec-028.md`).

The limits are constants, like the other per-feature upload limits
(`WIKI_MAX_BYTES`, `AVATAR_MAX_BYTES` and the WebSocket payload limit).

The inspection also accepts only the ZIP features Werkyn's exports use.
archiver writes deflated entries with data descriptors and UTF-8 names (flags
`0x0008` or `0x0808`), version 20, and no extra fields, comment or zip64
records. An archive is refused when:

- it is zip64, spans several disks, has an encrypted entry or sets an
  unsupported flag;
- it uses a compression method other than stored or deflated;
- an extra field is malformed;
- two names decode to the same text;
- the central directory does not exactly fill the space before the end
  record, or there is data after the end record;
- a local header disagrees with its central record. Without a data
  descriptor, its checksum and sizes must match too;
- a stored entry's two sizes differ;
- two entries' bytes overlap;
- an end record or zip64 locator sits within the 20 bytes before the end
  record. adm-zip would pick that record instead, so both readers could see
  different entries.

Hand-made archives with directory entries, other folders, extra fields such as
timestamps, or an archive comment are still accepted.

After adm-zip parses the archive, its entry list must match the inspection's
name for name, with the same sizes and offsets. Only `backup.json` and files
under `assets/` are read, as before. adm-zip caps each inflation at the
entry's declared size, and the result must be exactly that size. A smaller
result means the archive lied about the size that the budget was checked
against.

Every refusal is a 400 with one of two fixed messages: the archive is damaged
or uses unsupported ZIP features, or it exceeds the restore limits. The missing
`backup.json` message is unchanged. Responses never quote entry names or
adm-zip errors. The server logs a fixed reason code, such as `name-length` or
`duplicate-name`, at warn level.

Export applies the same budget, so every export Werkyn produces can also be
restored. It counts each embedded file as it is read, and stops reading as soon
as the archive would exceed a limit. It then answers with a 400 asking the
admin to select fewer projects, channels or wiki spaces, or to leave out
files.

## Behavior changes

- Archives that declare more than the budget are now refused, even when the
  real data is small. Before, an honest 5-byte entry declaring 4 GiB was
  restored.
- A deflated entry that inflates to less than its declared size is refused.
- Trailing data after the end record, and overlapping entries, are refused.
- Malformed archives, and a JSON body uploaded with a `.zip` name, now get a
  400 instead of a 500.
- An export whose archive would exceed the budget gets a 400 instead of
  producing a backup that cannot be restored. Before, such an export
  succeeded whenever the server had enough memory.

## Tests

`tests/backup-archive.test.mjs` runs in `pnpm test`. It covers:

- every limit at its boundary, including implied folders and multi-byte names;
- each malformed and unsupported class, by its reason code;
- inflation stopping at the declared size;
- an archiver-built archive shaped like an export, read byte for byte.

It also runs the 30,000-level name, a 20,000-entry archive and an archive full
of implied folders in a child process limited to 1 GiB of data and a 256 MiB
heap. There, all three are refused with less than 300 MB RSS, while the old
adm-zip sequence aborts the same child on the deep name.

`tests/integration/backup-zip-budget.test.mjs` starts the real app in a child
process with the same memory limits and uploads 22 archives to preview and
restore. The parent creates and removes the database rows, so a crashed child
leaves nothing behind. On the previous code, the child aborted (SIGABRT) on the
deep name, and on a 520 MiB honest entry when that ran first. Several other
archives got a 500 or were restored. Now every hostile archive gets a 400 with
no files and no rows. A legitimate archive restores byte for byte, and an
archive exactly at the entry, name and depth limits previews.
`tests/integration/backup-zip-restore.test.mjs` keeps the existing export,
traversal, symlink, duplicate, checksum and declared-size cases, now expecting
400 responses. It also checks that an export exactly at reduced limits
succeeds and restores under those limits, and that one byte, one entry or one
name byte over them refuses the export.

## Remaining limits

The upload is still buffered whole up to `MAX_FILE_SIZE`, and accepted assets
are still held in memory until the restore finishes. A small deflated archive
can still expand to the 1 GiB budget. Export still builds the whole archive in
memory, though now only up to the budget. Workspaces with more than 1 GiB of
embedded images must be exported in parts. A streaming export and restore with
a concurrency limit (B03/P03) is the remaining fix for large backups. The public
backup documentation does not mention these limits yet.
