# P01b: windowed project List (FE-010)

[P01a](p01.md) split routes and panels and added bundle budgets. The other
half of P01 was that long collections render every item. This change covers
the project **List** view; the Board and Drive still render every card and
file (see [Remaining scope](#remaining-scope)).

The List loads every non-archived task of the project in one request and,
before this change, rendered a table row (with about 13 controls and three
popover triggers) for each of them. A 5,000-task project put 192,000 elements
and 65,000 table controls in the page, held 570 MB of JavaScript heap, blocked
the main thread for 5.5 s after opening and drew about three frames a second
while scrolling.

## What changed

`features/list-view/components/task-table.tsx`:

- **Only rows near the view are rendered.** The List's rows (one header row per
  status group, then that group's tasks unless collapsed) are windowed with
  `@tanstack/react-virtual`, which was already a dependency. The workspace
  `<main>` element is the scroller, as before: the project header and filter
  bar still scroll away with the table. Rows within the view plus 8 rows each
  side are in the DOM; one spacer row before and after them holds the height of
  the rest, so the scrollbar, wheel/keyboard scrolling and the table's column
  alignment are unchanged. Spacer rows are `aria-hidden`. The first and last
  rows of the List are always rendered as well, so Tab from the header
  checkbox reaches the first row and Shift+Tab from below the table the last,
  as with every row rendered.
- **Row heights are measured.** Rows can wrap (labels, multi-select values), so
  each rendered row is measured. Rows not rendered yet have fixed estimates
  (41 px for a task row, 33 px for a group header); changing the estimates
  would move every row not measured yet, including those above the view.
- **Rows in view stay where they are.** When rows above the view change, the
  rows in view keep their place: tasks created, deleted or moved in by others
  or by a bulk action, rows rendered at a height other than their estimate
  while scrolling up, an inline editor above the view opening or closing, or
  content above the table (the project header, the filter bar) changing
  height. The rows in view (those at least half in view) are remembered by
  key with their position and the scroll position. After each render of the
  table, when the table body changes size and when content above it does,
  `<main>` is scrolled by however far one of them moved other than by the
  user scrolling, before the browser paints:
  - The row kept is one that stayed. Among the rows seen in view, the set that
    kept its order and moved least in total is taken, each row counting
    1 / (1 + its change of index): rows only pushed along by others count
    nearly fully, a block moved far away (a bulk change to another group)
    almost nothing, however large it is. Rows of that set that moved much
    further than the least-moved ones are skipped; of the rest, those that
    every such set includes come first, and the first of them still rendered
    is kept (a short scroll can take the top rows seen out of the rendered
    range). So a row a colleague moved within the view (the top row moved
    three places down, say) is passed over and the rows after it stay, as
    with every row rendered; when two rows swapped places, the rows after
    them are kept; and when the top block of the view is moved away, the
    rows that stayed are kept rather than followed. When a block leaves the
    middle of the view, the rows above it are kept (as the browser's
    anchoring does) and the rows below close the gap. Indexes alone cannot
    tell a large block moved a short way from the smaller block it passed;
    there the larger block may be kept.
  - A sliver of a row at the edge of the view does not count: when the
    block of rows below it is bulk-moved away, keeping it would move the
    rows the user sees.
  - Until the List changes again or the user scrolls, the row kept last
    stays the one kept. Rows that a correction brought into view above it
    are rendered and measured only then, and settling to their heights
    they would otherwise move it.
  - When the List gets shorter at or near its end, the browser lowers the
    scroll position to the new end; that is not counted as the user
    scrolling (otherwise the rows would be moved a second time).
  - If none of them is rendered any more (a bulk change moved more rows above
    the view than the rendered range holds), `<main>` scrolls to the new
    position of one of them that belongs in view, from the virtualizer's
    measurements, and places it exactly once it is rendered. Until `<main>`
    has handled that scroll nothing else is corrected; after any other
    scroll, the rows in view are seen afresh.
  - This applies while the List was scrolled by less than half the view since
    those rows were seen (which keeps them in the rendered range); after a
    longer scroll (End, the scrollbar) there is nothing to keep. Nothing is
    kept at the very top of the List (scroll position 0).

  The browser's own CSS scroll anchoring is turned off for `<main>` while the
  List is windowed: in the List it did not keep rows still for these changes
  (a colleague's three new tasks above the view moved the rows in view by
  123 px; see the measurements), and with it on, it and this correction
  together moved rows twice when content above the table changed height. The
  virtualizer's own size correction is off for the same reason.
- **Fixed column widths.** The table used automatic layout, where column widths
  follow the content of the rendered rows. Once rows come and go while
  scrolling that made columns change width (by up to 97 px in the 5,000-task
  fixture) and row heights change with them. The table now uses fixed layout:
  every column has its defined size, except Title, which takes the rest of the
  width (at least 240 px). With many custom-field columns the table is wider
  than the view and scrolls sideways, as it already did when cells held long
  text. Long titles and text/URL custom-field values are cut with an ellipsis
  at the column edge instead of widening the column; the inline date editors
  are drawn above the next cell when wider than their column.
- **Focus survives scrolling.** The row that last held focus, and the rows
  before and after it, stay rendered while scrolled out of view. An open
  inline editor keeps its unsaved draft and still saves it for its own task on
  Enter or blur; a popover keeps its trigger; focus returns to the task title
  after the task panel closes; Tab and Shift+Tab from that row reach the next
  and previous rows, which the browser then scrolls into view. The retained row
  follows focus (not pointer-down), so an editor's blur-save runs before its
  row can be released.
- **Accessible row positions.** The table has `aria-rowcount` (the header row
  plus every group and task row of the List) and each rendered row its
  `aria-rowindex`, the ARIA pattern for tables with rows not in the DOM.
- **Rendering cost per scroll step.** Task rows are memoized, so scrolling
  renders only the rows coming into view, not every mounted row and its
  popovers.
- **Mounting keeps the scroll position.** The virtualizer starts from where
  `<main>` already is (by default it would scroll to the top when attached).
- Without a `<main>` ancestor (as in some tests), every row is rendered as
  before.

## What did not change

- Data loading: the List still fetches every non-archived task at once; the
  TanStack row model, selection state and group counts cover every loaded task.
  "Select all" selects every loaded task, including collapsed and off-screen
  ones; bulk actions keep their 50-task limit; selection is kept for rows
  scrolled out of view.
- Inline edits use the same cells and save paths (custom fields per PR97,
  dates per PR143/145).
- Realtime events refetch the task list as before; inserted and removed rows
  appear and disappear in place, and the row count and indexes follow.
- Group headers and collapse/expand work as before.
- The List has no drag-and-drop reordering (rows are ordered by status, then
  position); Board drag-and-drop (PR101 ordering, PR138 refresh after a refused
  move) is not touched by this change.
- The header row is `sticky` in the markup but did not stay in view before
  this change either, because the table's wrapper and the project layout are
  their own (non-scrolling) overflow containers; that is unchanged.
- There is no scroll restoration when navigating to another view and back,
  before or after (the List starts where `<main>` is). Opening a task and
  closing it keeps the List's scroll position and focus.

## Limitations

- **Find in page.** Ctrl+F / Cmd+F (and `/` quick find in Firefox) only find
  tasks whose rows are rendered. Use the List's search filter (title search on
  the server) to find tasks. Printing the page prints only the rendered rows.
- **Screen readers.** Browse mode reads the rendered rows only; row positions
  come from `aria-rowindex`/`aria-rowcount`. This was not verified with actual
  screen readers.
- Rows not yet rendered have estimated heights, so the scrollbar thumb can
  shift slightly as rows are measured, and jumping to the end (End key,
  scrollbar dragged to the bottom) can land a few rows short of the last row
  the first time; pressing End again reaches it. (Keeping the List pinned to
  its end instead was tried and dropped: it moved rows under the pointer when
  focus or a click scrolled the List at the same moment.)
- Only Chromium was checked. Keeping rows in view does not rely on CSS scroll
  anchoring, so browsers without it (older Safari) get the same behaviour, but
  that is untested.
- Still loaded in full: the task list request, JSON parsing and the row model
  for every task. At 5,000 tasks the request took about 0.65 s locally.

## Measurements

Same method before and after: `packages/backend/tests/browser/task-list-windowing.mjs`
with `TASK_LIST_MODE=measure`, three runs each in a fresh browser context
(medians below), against production builds of main at `433c6ac` and of this
change on it. Headless Chromium 141 with Playwright's bundled browser on a
shared Linux host, 1440×900 viewport, fonts off the loopback origin blocked.
The fixture project has 5,000 tasks in four status groups (2,000 / 1,250 /
750 / 1,000), eight labels and six custom fields (text, number, select,
multi-select, date, checkbox), so each task row has 13 columns; about half
the tasks have assignees, labels, due dates and custom values.

Each run starts on the project settings page and switches to the List in the
same document, as a user does. "Rows in the DOM" is the time from the click
until the first group's first task row exists; "settled" is when the main
thread has been free of long tasks (over 50 ms) for two seconds. Chromium's
`Performance.getMetrics` gives scripting, layout and style time and the
heap (after a forced garbage collection). The scroll test scrolls the
workspace `<main>` 120 px per animation frame for 240 frames (about 700
rows) and records frame intervals and long tasks; the realtime test renames
the first task as a second user and waits for the List to show it.

Scrolling now runs JavaScript (rows coming into view are rendered: about
3 ms of script and 2.6 ms of layout and style per frame here), where the
fully rendered table only had to paint, but each paint of 192,000 elements
took about 300 ms. The windowed List kept every frame at the display rate.

The List chunk grows from 6.0 kB to 11.9 kB gzip (`@tanstack/react-virtual`);
it is loaded with the List route, and the initial bundles are unchanged
(entry 145.3 kB, CSS 13.9 kB, sign-in 189.8 kB, dashboard 270.6 kB gzip,
within the P01a budgets).

In the same browser runs, before and after: the table was 1,784 and 1,740 px
wide in a 1,184 px view (it already scrolled sideways on main, because the
text column widened to 617 px for its longest value); median row heights in
view were 53 and 41 px (main wrapped dates and labels in squeezed columns);
the header row did not stay in view after scrolling on either.

The smoke on the same fixture passed all thirteen steps with no browser errors:
26 of 5,005 rows mounted at the top (with the last row) and 28 task rows at
the end; the second End press reached the last row; scrolling up 150 steps of
90 px through rows never measured moved rows in view by at most 0.94 px
(sub-pixel) and no column changed width; Tab and Shift+Tab crossed 45 rows
(13 stops each) and a group header with at most 37 task rows mounted, and Tab
from the header checkbox reached the first row; Enter opened task 45 and
Escape returned focus to its title at the same scroll position; three tasks selected at the top, middle and end were bulk-updated
and select-all selected 5,000; custom-field and due-date edits far down the
List were saved for the right tasks; a colleague's new task and deletion
appeared without reload; collapsing a 2,000-task group worked; rows in view
stayed within 0.5 px through a colleague's changes above them (below); on the Board
of the same project (rendered in 1.4 s, not windowed) dragging the first card
of a 2,000-card column below the third saved that order with positions
renumbered 0 to 1,999.

### Rows in view when the List changes above them

A first version of this change relied on the browser's scroll anchoring and
moved the rows in view when a colleague changed tasks above them; a click
where the pointer rested then hit another task. The smoke's `anchor` step
scrolls to a task in the last group, then a second user creates three tasks,
deletes two and moves one in from below the view, all in groups above it, and
the position of that task's row is compared after each refresh (cumulative,
from where it started). Then 50 tasks from below the view are moved into a
group above it in one bulk change, and the first three rows in view are
deleted. With the pointer resting on the row's checkbox, three more tasks are
created above and the pointer clicks without moving.

| Change above the view | main | first version | this change |
|---|---:|---:|---:|
| 3 tasks created (px) | 0 | +123 | −0.5 |
| then 2 deleted (px) | 0 | +40.5 | −0.5 |
| then 1 moved in from below (px) | 0 | +81.5 | −0.5 |
| then 50 moved in from below, bulk (px) | +0.22 | (not reached) | −0.19 |
| then the first 3 rows in view deleted (px) | +0.09 | (not reached) | +0.25 |
| click at the resting pointer after 3 more created | right task | task 3 rows above | right task |

An intermediate version that kept only the first three rows in view lost the
row entirely after the bulk change (it was no longer rendered); a later one
also corrected after long scrolls and made rows jump by up to 31 px when
scrolling up from the end, which the smoke's scroll step caught.

The smoke's `edges` step covers the edges of the same behaviour, against the
version after those (`bcff088`, reviewed) and this change:

The smoke's `bulk` step moves the top block of rows in view (14 of about 20)
to the last group, with the pointer resting on a row that stays:

- by a colleague, with the partly visible top row in the block;
- by a colleague right after a short scroll down (0.47 of the view in one
  step, which takes the rows seen before it out of the rendered range);
- by the user's own bulk status change, with the first row of the block
  1 px below the top of the view, so that a sliver (about 1 px) of the row
  above it, which stays, is in view.

| user's own, sliver above in view: rows that stayed (px) | −682.19 (slide up) | (not run) | −599.12 (slide up) | −0.06 |

Three things went wrong at `dc40e89`, the version with the rule above but
without the rest:

- After a scroll of less than half the view, the first row remembered could
  be outside the rendered range. The correction then scrolled to that row
  and from then on remembered only it, so the next change was not
  corrected. The full smoke reached this through its own positioning (a
  jump, then a 401 px adjustment).
- The sliver of the row above the block counted as a row in view. Its index
  did not change, so it was kept, and the rows below slid up by the
  block's height.
- After the large correction, the rows it brought into view above the kept
  row were rendered and measured, and the next passes kept those rows
  instead. Settling to their measured heights, they moved the rows that
  stayed by 0.88 to 1.38 px. Keeping the same row until the List changes or
  the user scrolls gives −0.06 px.

For the swap, the browser's anchoring on main keeps the second row and moves
the rows after the pair by one row; the List keeps the rows after the pair
and the two rows trade places (an intermediate version kept the first row
and moved the rest by −41.5 px). The smoke asserts that case for the
windowed List only.

The half pixel is the first correction rounded to a whole scroll position; it
does not grow with further changes.

## Tests

- `task-table-window.test.tsx` (Vitest, jsdom with a fixed layout): only rows
  near the view render, with the first and last rows, and ARIA describes the whole list; the scroll position
  `<main>` already has is kept; without `<main>` every row renders; select-all,
  group counts and selection of rows out of view; the focused row and its
  neighbours stay rendered and follow focus; an inline editor's draft survives
  scrolling away and saves for its own task; moving focus does not move the
  rows in view (rows of different heights, measured again after scrolling);
  realtime inserts and deletes (including the focused row) keep ARIA and the
  focused row; collapsing a group. Against main's table all eight of the
  original cases fail (no row windowing, ARIA row count or row markers).
- `steady-row.test.ts` (Vitest): which of the rows seen in view is kept when
  rows were added or removed above (also at the end of the List), when the
  top row or a later row was moved within the view, two rows swapped, the top
  row was deleted while the next one moved, rows moved to other groups, the
  top block of the view was moved far below or far above, a block left the
  middle of the view, and when rows left the List; and the order in which
  the rows that stayed are tried.
- `packages/backend/tests/browser/task-list-windowing.mjs` (Chromium, production
  build, 5,000 tasks, 13 columns): the measurements above (`TASK_LIST_MODE=measure`)
  and a smoke (`TASK_LIST_MODE=smoke`) of windowing and ARIA, scrolling to the
  end (End presses counted) and back up without rows jumping or columns changing width,
  Tab/Shift+Tab across 45 rows and a group header, keyboard open and Escape
  with focus and scroll kept, selection across distant rows with a bulk
  priority change and select-all, inline custom-field and due-date edits
  (including a draft saved on blur after scrolling away), realtime insert and
  delete from another user, collapse/expand, rows in view kept within 1 px and
  a click at a resting pointer still hitting its task when another user
  creates, deletes or moves tasks above the view (`anchor`), the same for the
  top row moved down, content above the table and deletions above at and
  near the end of the List (`edges`), a bulk move of the top block of rows in
  view by a colleague, by a colleague right after a short scroll and by the
  user with a sliver of the row above in view (`bulk`), Tab from the
  header checkbox reaching the first row, and drag reordering on the Board of
  the same project. A click that has no effect prints the List's layout at
  each step of the click.

Run the browser script from `packages/backend` with a migrated, disposable
loopback database whose name starts with `werkyn_audit_`, and an
installed Playwright:

```sh
TEST_DATABASE_URL=postgresql://…/werkyn_audit_… \
PLAYWRIGHT_MODULE=playwright \
node --import tsx tests/browser/task-list-windowing.mjs
```

`TASK_LIST_DIST` uses an existing frontend build (otherwise one is built first),
`TASK_LIST_MODE`, `TASK_LIST_TASKS`, `TASK_LIST_RUNS`, `TASK_LIST_STEPS`,
`TASK_LIST_REPORT` and `TASK_LIST_SCREENSHOTS` are described at the top of the
script. It creates and removes its own users, workspace and project.

## Remaining scope

- **Board** columns render every card. Each column could be windowed the same
  way, but drag-and-drop (dnd-kit sortable) needs the dragged card and its
  drop targets mounted, which needs its own design and checks of the PR101 and
  PR138 rules.
- **Drive** folders render every file.
- The task list request itself is not paginated.
