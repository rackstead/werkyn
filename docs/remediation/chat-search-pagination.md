# Chat search cursor pages

Global and channel message search order by `createdAt DESC, id DESC`. The ID gives equal timestamps a deterministic order. The existing default of 20 and maximum of 50 matches, raw message-ID cursor, extra sentinel row and response shape remain unchanged. Replies remain searchable; deleted messages and server idempotency fields remain excluded.

A cursor must match the same term and current visibility filters as the requested search. A missing, nonmatching, deleted or unrelated cursor produces an empty page. The message-page SELECT checks that eligibility together with the page, so a separate precheck cannot become stale between two reads. This is the message query's statement boundary; related user/channel loading and concurrent requests keep their existing behavior. Pages do not form a snapshot across requests.

Global search continues to require channel membership, including PUBLIC channels. Explicit-channel search continues to allow PUBLIC reads by workspace members without joining, while PRIVATE and DM searches require membership even for workspace admins. Existing authentication, workspace roles and case-insensitive substring matching do not change. The API accepts a one-character query; the current web search starts at two characters and displays only the first page, without following search cursors.

The pinned Prisma engine now applies `LIMIT` to cursor page output. A page query emits at most `limit + 1` messages, while the database may still scan and sort more rows. The eligibility predicate adds joins; this change does not establish a latency, IO, memory or capacity target. Existing indexes, schema, dependencies and request/transaction budgets are unchanged. Historical P02a search timings remain historical; wider search indexing and the other R18 query families remain separate.

`packages/backend/tests/integration/chat-search-pagination.test.mjs` exercises both search modes against disposable PostgreSQL with session-bound injected HTTP requests and separate same-service SQL capture. It checks complete ordinary/tied traversal at limits 1, 2, 20 and 50, SQL bounds, cursor eligibility, mutable search filters, visibility, limits and DTOs. Run it with a migrated disposable `TEST_DATABASE_URL` through the repository integration command. Actual loopback HTTP and bounded query plans are also retained in the audit evidence; no browser pagination feature is added.
