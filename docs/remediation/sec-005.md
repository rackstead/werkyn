# OIDC verified identity and account linking

SSO links a new provider to an existing local account only when automatic email
linking is enabled, the signed token affirms email verification, and the local
account is already verified. Disabling automatic linking rejects collisions.
Unverified local accounts retain their existing credentials and are not activated
by SSO. New SSO accounts also require a valid verified email and have no password.

Already linked subjects continue to identify the same account when email changes,
is unverified, or is absent, and when automatic email linking is disabled. New
provider bindings use an issuer-specific namespace while preserving the raw
subject separately. Existing `provider=oidc` bindings migrate transactionally on
successful sign-in. Their schema does not record an issuer, so this compatibility
path assumes this installation's existing embedded Dex issuer; changing issuers
requires explicit operator review rather than reusing a legacy subject namespace.

The callback validates ID-token issuer, audience, nonce, timestamps and JWS
signature before resolving accounts. Signature verification matters here because
the token/JWKS endpoints use loopback HTTP. Dex's signed actual connector claim
must match any initiating connector hint and an existing binding's connector,
and the actual connector and SSO configuration must currently be enabled. Account
and provider writes share a serializable transaction with bounded conflict retries.

The request adds `federated:id`, which Dex documents as supplying the signed
connector identity. See [Dex scopes and claims](https://dexidp.io/docs/configuration/custom-scopes-claims-clients/)
and [oauth4webapi's signature validation API](https://github.com/panva/oauth4webapi/blob/main/docs/functions/validateApplicationLevelSignature.md).
The installed locked library's implementation and type documentation were also
checked when extracting this change.

The tests run real Fastify handlers, PostgreSQL writes, installed oauth4webapi,
and a loopback-only disposable IdP serving JWKS and actual RSA-signed ID tokens.
They verify positive login/linking, unchanged credentials on rejection, missing
or malformed/unverified claims, connector status and mismatch, legacy migration,
issuer separation, invalid signatures/issuer/audience/nonce/expiry, and concurrent
first sign-ins. The IdP fixture checks client authentication, redirect URI and
PKCE verifier. Use an explicitly designated migrated disposable database:

```bash
pnpm --filter @pm/shared build
TEST_DATABASE_URL="$AUDIT_DATABASE_URL" pnpm --filter @pm/backend exec node --import tsx --test --test-concurrency=1 tests/oidc-identity.test.mjs tests/integration/oidc-identity.test.mjs
```

Browser-bound callback state/cookies, atomic state consumption, error-response
hardening and authorization-response issuer forwarding are a separate SEC-016
change. This patch deliberately leaves that existing controller/state flow for
the separate fix. Real Dex/upstream-provider browser flows and each connector's
verified-email semantics remain release gates. Enabling linking trusts the
operator's IdP assertions; old unsafe provider associations and session/credential
revocation require operator incident review. No deployment or data deletion is
part of this change.
