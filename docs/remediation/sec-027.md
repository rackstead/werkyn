# Password change re-checks the current password under the user row lock

`changePassword` (`PATCH /api/users/:id/password`) read the account's password
hash, verified `currentPassword` against it and hashed the new password, all
outside its transaction. The transaction then wrote the new hash without
looking at the stored one again. A change that had verified the old password
just before a password reset committed therefore still succeeded afterwards:
both requests returned 200 and the change's password replaced the one the
reset had just set, although the password the change proved was no longer the
account's. Two changes sent with the same current password likewise both
succeeded, and the last one decided the password. Password login already
re-checked the hash under its lock (SEC-011); the change did not.

## Behavior

- The change still verifies `currentPassword` and hashes the new password
  before its transaction, so bcrypt never runs while a row is locked.
- The transaction starts with the SEC-011 `lock_timeout`, then locks the user
  row with `SELECT "passwordHash" ... FOR NO KEY UPDATE`, the mode password
  login uses and the one the reset's update takes. It writes the new hash and
  revokes every refresh family only if the stored hash is still the one that
  was verified. Under READ COMMITTED the locking read returns the latest
  committed row, including one written by a transaction it waited for.
- If the hash changed in between (a reset, another change, or anything else
  that replaced the password), the request is refused with exactly the
  response a wrong current password gets,
  `400 {"message":"Current password is incorrect"}`, and writes nothing: the
  password, the families and the sessions created meanwhile are unchanged.
  The user can retry with the password that is now current.
- A change whose lock wait reaches the lock timeout, or whose transaction
  exceeds its budget, is rolled back and answered
  `503 This account is busy. Try again in a moment.` instead of `500` (lock
  timeout) or `409` (budget). The detection is `isBusy` from
  `refresh-sessions.ts` (55P03 or P2028), as for refresh rotation and
  password-reset links.

Resulting outcomes for requests that overlap on one account:

| Overlap                                                     | Result                                                    |
| ----------------------------------------------------------- | --------------------------------------------------------- |
| Reset commits, then a change that verified the old password | reset 200; change 400, nothing written                    |
| Change commits, then a reset with an earlier link          | change 200; reset 404; the changed password is kept        |
| Several changes with the same current password              | one 200; the others 400, nothing written                  |
| Login with the old password commits, then a change          | both 200; the change revokes the login's session          |
| Change commits, then a login with the old password          | change 200; login 401 (unchanged, SEC-011)                |
| Refresh rotation and change, either order                   | both complete; no token of the old session remains usable |

A change refuses whenever the stored hash differs from the verified one, even
if the new hash happens to encode the same password (for example a reset to
the same password). That is deliberate: comparing hashes keeps bcrypt out of
the locked section, and the user re-enters the current password.

## Reset links

A successful password change deletes every unused reset link of that account
in its transaction, after rechecking the password under the user lock and
before changing the password or revoking families. Used records and other
accounts are unchanged. Wrong-password, stale, busy and rolled-back changes
leave links and sessions unchanged. A new link inserted between deletion and
the remaining-row check can also conservatively make the password operation
return its retryable busy 503: the password transaction rolls back and that new
link stays usable. An insert committed after that check may leave a usable new
link even when the password operation succeeds, as with the existing concurrent
forgot-password/reset ordering. No issuance or account-response policy changes.

A successful password reset also deletes the account's other unused reset
tokens in the same transaction, right after it claims its own. A later use of
one of them is answered `404 Invalid reset token`, like a link replaced by
forgot-password.

For that to hold, resets of one account run one at a time: the reset
transaction locks the user row (`FOR NO KEY UPDATE`) before it claims its
token, instead of after (SEC-026 claimed first). No other reset can therefore
hold a link of the account while one reset deletes them, including a reset
that would later roll back (a lock timeout, an exhausted budget, an expired
token or any database error) and leave its link unused. When several links of
one account are submitted at once, exactly one reset succeeds and the others
get `404`. The delete still skips rows that are locked (`FOR UPDATE SKIP
LOCKED`): with the user row held, a locked token can only be one that
forgot-password or the cleanup job is deleting, and waiting for it could make
the two deletes wait for each other. Both reset and change then check for
remaining unused rows without waiting. If a skipped deletion has not committed,
its row is still visible and the password operation rolls back with its
existing busy 503. A deleter that aborts therefore cannot leave an old link
usable after a successful password operation. This closes the skipped-row
rollback edge in the earlier reset invalidation; the normal sibling
invalidation already existed.

## Lock order

- Password change: user row (`NO KEY UPDATE`), unused reset tokens (never
  waited for), then families in id order.
- Password reset: user row (`NO KEY UPDATE`), its token, other unused tokens
  (never waited for), families.
- Password login: user row (`NO KEY UPDATE`), then families.
- Refresh rotation: family, then the `KEY SHARE` foreign-key check on the user
  row, which does not conflict with `NO KEY UPDATE`.
- Session creation (OIDC sign-in, registration): user row `FOR SHARE`.

- Email verification: its token, then the user row.

Only the reset waits for a reset token while holding a user row, and the
statements that hold reset tokens without a user row (forgot-password and the
cleanup job, single deletes outside a transaction) never wait for a user row.
No path waits for a user row while holding a family. These transactions
therefore cannot deadlock with one another.

## Validation

`packages/backend/tests/integration/password-change-atomicity.test.mjs` runs
the application over HTTP (`inject`) against PostgreSQL with a separate
two-connection control pool. Barriers are real row locks observed through
`pg_stat_activity`. It covers:

- a single change (wrong current password, another user's account, an SSO
  account, success revoking every family);
- a change delayed after verifying the old password until a reset committed
  and the user signed in again: 400, the reset's password and the new session
  kept;
- a reset and a change queued on the user row in both orders;
- four concurrent changes with one current password: one 200, three 400;
- a password login and a change in both orders, and a refresh and a change on
  the session's family in both orders;
- a change blocked on the user row and on a family past a shortened lock
  timeout, and one that exhausts a shortened budget: 503, nothing changed, the
  retry succeeds;
- a mixed storm of changes, resets (duplicate and distinct links), logins and
  refreshes on two accounts: no deadlock or unexpected error (only the documented
  retryable busy 503), a temporary trigger
  logs every committed password write, every write belongs to a 200 response,
  and every successful change replaced the hash of the password it verified.

`single-use-auth-tokens.test.mjs` adds the reset-link cases: other unused
links of the account are removed by a successful reset (used links and other
accounts are untouched); a reset with another link queued behind a successful
reset gets 404 and changes nothing; bursts of resets with distinct links of
one account give exactly one 200 and leave no unused link; and a reset that
claimed its link and then rolled back (paused on a real advisory lock by a
temporary trigger, then failed) leaves that link refused with 404 once the
other reset succeeds.

On the previous code 11 of the new tests fail: the change after a reset, the
reset-first queue order and the concurrent changes all returned 200; the two
lock-timeout cases answered 500 and the budget case 409; the storm found
changes that replaced a hash they had not verified; and every other link of
the account was still usable after a reset. With reset links deleted but
claimed before the user row (an intermediate version of this change), the
distinct-link burst gave two 200s and the rolled-back link still reset the
password, which is why the reset now locks the user row first.

```sh
TEST_DATABASE_URL=<disposable-url> pnpm --filter @pm/backend exec node --import tsx --test --test-concurrency=1 tests/integration/password-change-atomicity.test.mjs tests/integration/single-use-auth-tokens.test.mjs tests/integration/refresh-family-atomicity.test.mjs
```

## Out of scope

- Password login still answers a lock timeout with `500` rather than `503`.
- Personal API keys can call the password-change endpoint (with the current
  password), and a password change or reset does not revoke API keys or
  issued access tokens (SEC-011, DAT-006).
- Account-link digests and the coordinated data migration are documented in
  `sec-026.md`; personal API-key and refresh policy are unchanged.
