# Environment validation, log redaction, health probes and shutdown

Startup now rejects configuration that the server could not use correctly, with one
message per variable that never repeats the supplied value:

- `PORT`, `SMTP_PORT` and `DEX_INTERNAL_PORT` must be whole numbers from 1 to 65535;
  `MAX_FILE_SIZE` must be a positive whole number of bytes.
- `COOKIE_SECURE` and `SMTP_SECURE` accept only `true` or `false`. Values such as `1`
  or `TRUE` were previously read as `false` without warning.
- `FRONTEND_URL` must be an absolute http(s) URL without credentials, query or
  fragment; a trailing slash is removed. `CORS_ORIGIN` is a comma-separated list of
  http(s) origins; entries are trimmed and normalized, and `*` is rejected.
- `DATABASE_URL` must be a PostgreSQL connection URL. `COOKIE_DOMAIN` must be a bare
  domain name.
- `COOKIE_SAMESITE=none` requires secure cookies, because browsers discard insecure
  SameSite=None cookies. Production still defaults `COOKIE_SECURE` to `true` when it
  is unset.
- An empty value (`PORT=`) means "use the default".

The local HTTP install in `docker-compose.yml` keeps working: it sets
`COOKIE_SECURE=false` explicitly with `http://localhost` URLs. A production server whose
`FRONTEND_URL` uses https but whose cookies are not Secure still starts and logs a
warning. The production signing-secret checks are unchanged.

Logs no longer contain credentials. Request URLs in access logs keep their path and
harmless query parameters, but these values are replaced with `[REDACTED]`: link tokens
in reset, verification, invitation and public-share paths (API and browser routes),
and credential-like query parameters such as `token`, `code`, `state` and `hmac`.
Authorization, cookie and API key headers, and fields such as `password`, `token` and
`pass`, are censored in structured logs. The same applies to messages, error messages
and the standalone startup/mail logger.

`GET /api/health` is the liveness probe. It answers while the process is serving and
does not touch the database. `GET /api/ready` is the readiness probe. It returns 200
only when the database answers within three seconds and every migration shipped with
the build has been applied. Otherwise it returns 503 with `database` and `migrations`
check states (`unavailable`, `pending`, `failed` or `unknown`). Details are logged on
the server, not returned. Neither probe is cached, and probes do not count against the
client rate limit.

On SIGTERM or SIGINT, a failure to stop Dex or close the HTTP server is now logged and
the process exits with status 1. Shutdown is limited to eight seconds, under Docker's
ten-second stop timeout. A second signal forces exit. A startup failure is logged
through the application logger.

Run `pnpm --filter @pm/backend test` for the configuration, redaction, probe and
shutdown tests. The readiness test against a migrated database is in
`tests/integration/health-readiness.test.mjs`.

Not included here: authenticated `?token=` access JWTs are still accepted on any route
(the PDF preview uses them). The URL is redacted in logs, but browser history and
proxies can still record it. Scheduler timers are not drained on shutdown (OPS-005).
Static assets still count against the rate limit (OPS-011).
